# Audio engine & transport

The realtime core: `AudioEngine`'s render pass and device lifecycle, and `TransportService` — the one clock every timeline-aware module reads.

Part of the architecture docs — start at [`architecture.md`](architecture.md) for the
layer map, signal flow and the index of the other topic docs.

## AudioEngine

`Source/AudioEngine/AudioEngine.h/.cpp`

Manages audio device I/O (via `juce::AudioIODeviceCallback`), the `juce::AudioProcessorGraph`, and modulation-matrix routing. Key responsibilities:

- **Audio callback** — `audioDeviceIOCallbackWithContext` drives `mainProcessorGraph.processBlock`, then applies master-mute zero-fill **after** `processBlock` so sequencers, LFOs, and envelopes keep advancing even while muted. `masterMuted_` is `std::atomic<bool>`. Last, unconditionally, `renderNextBlock` scrubs any remaining non-finite sample (NaN/Inf) to `0.0f` in place across the graph's declared output channels — the one point both host modes always funnel through, so it catches a runaway patch or an upstream divide-by-zero regardless of whether `MasterModule` is even in the graph (the default patch has none) or is bypassed/muted; see `scrubNonFiniteOutput` in `AudioEngineRenderPass.cpp`.
- **Audio input** — the callback renders through **one** buffer of `max(numIn, numOut)` channels, and the device's input is **copied into it before the graph runs**. That copy is not an optimisation to remove: a `juce::AudioProcessor` renders in place, so channels `[0, numIn)` (what a `juce::AudioGraphIOProcessor(audioInputNode)` reads, if a patch still holds one) and channels `[0, numOut)` (what its *Audio Output* node writes) are **the same memory** — the input block is `const` and the graph is about to overwrite those channels with its result. The *Audio Input* **module** does not read this buffer at all; it reads the separate snapshot described below. Channels the device's outputs don't cover (a device with more inputs than outputs, or an output pointer the device hands us as null) come from `deviceScratch_`; it and the channel-pointer array are sized in `audioDeviceAboutToStart` (`prepareDeviceScratch`, on `max(in, out)` — `prepareSliceScratch` is sized the same way for the same reason), so the callback never allocates. If a block ever arrives wider or longer than prepare sized for, the callback serves the output channels alone rather than allocating. This is `juce::AudioProcessorPlayer`'s pattern; `AudioEngine::getDeviceScratchInfo()` exposes the sizing so `Tests/Engine/AudioInputTests.cpp` can assert it. Live input makes a mic → speaker loop *possible*, but only once the user patches the Audio Input node onward — this copy itself stays unconditional (it is the capture path, not the safety mechanism); see [Input monitoring & feedback guard](#input-monitoring--feedback-guard) for what actually gates it.
- **The per-block device-input context** — how the *Audio Input* module actually gets those samples, and the one part of the input path that is **not** the render buffer:
  - Each callback the engine copies the input a **second** time, into `deviceInputSnapshot_` — storage the graph never renders over — and `renderPass` parks pointers into it on the playhead (`TransportService::setDeviceInputForBlock`), clearing them again the moment `processBlock` returns. `AudioInputModule` downcasts `getPlayHead()` and copies from there. This is the same "the playhead is the only handle every module already has" carrier the timeline snapshot uses; device input reaching modules through it is unrelated to the timeline feature proper — it is not a timeline feature.
  - The second copy is the whole point. The copy into the render buffer exists so the graph's `max(numIn, numOut)` channels start out holding the input; the graph then **overwrites those very channels** with its result, so a node running mid-graph would read partly-rendered output where the input used to be. Hosted mode has the identical problem in a sharper form — the host hands us one buffer that is both its input and its output — so `processHostBlock` takes the same snapshot before `renderNextBlock`, and the module behaves the same in both modes (`AudioInputModuleTest.HostedInputFlows`).
  - Sized in **both** prepare paths (`prepareDeviceInputSnapshot`, `TransportService::kMaxDeviceInputChannels` = 8 channels × twice the block size), never from the audio thread. A block longer than that publishes **no** input rather than allocating or truncating — the module renders silence for it, the same degraded-but-safe posture as `deviceScratch_`. With automation slicing on, `renderPass` takes an `inputSampleOffset` so each 64-sample slice publishes *its* slice of the capture instead of replaying the block's first one.
  - `AudioEngine::getDeviceInputChannelCount()` is the message-thread half: the input channel count the graph is currently prepared for (0 before either prepare path has run). `GraphEditor::refreshIoModulesAfterDeviceChange()` pushes it into every Audio Input module on a device change so the card's jacks resize immediately instead of one rendered block later. See [Audio Input](../modules/modules.md#audio-input).
  - **No-playhead caveat.** A module reads the transport only through `getPlayHead()`; when nothing has installed one — a bare unit test constructing the module directly, or a foreign host that never calls `setPlayHead` — the module finds no transport and renders silence rather than crashing.
- **Device state persistence** — inputs are **opt-in**, and the opt-in is the persisted device setup:
  - *Out:* in Standalone mode the engine registers as a `juce::ChangeListener` on its `AudioDeviceManager` and, on every change, hands `deviceManager.createStateXml()` to the owner-installed `onDeviceStateChanged` callback. The engine stays `ApplicationProperties`-free — Core never touches settings — so `MainComponent` (owning path only; the plugin's host owns the device) stores the string under `"audioDeviceState"` and calls `saveIfNeeded`. The payload is legitimately **null** until the user has explicitly chosen a setup: JUCE does not treat its own startup defaults as explicit, so an untouched install persists nothing.
  - *In:* `MainComponent::initialiseCommon` parses that string and calls `audioEngine.setSavedDeviceState(...)` **before** `initialise()`. With a state, `initialise()` restores it via `deviceManager.initialise(0, 2, savedState, selectDefaultDeviceOnFailure=true)`; with none it takes exactly the old `initialiseWithDefaultDevices(0, 2)` path, which is why there is no migration step — *absent state is the legacy behaviour*. The **0** input channels *needed* is load-bearing and deliberately not 2: JUCE falls back to that count whenever the saved setup doesn't pin its input channels (saved after changing only the output device) and whenever the saved device can't be opened at all, so asking for 2 would silently switch a microphone on for a user who never asked. It costs nothing when the state *is* explicit — `setAudioDeviceSetup` re-derives the needed count from the saved channel mask, which the Audio tab writes the moment the user ticks an input channel. macOS also needs `MICROPHONE_PERMISSION_ENABLED` on the app target (top-level `CMakeLists.txt`), since the OS kills any process that opens an input stream without `NSMicrophoneUsageDescription`.
  - *Test seam:* `AudioEngine::initialiseDevices(const juce::XmlElement*)` is a protected virtual holding **everything** in `initialise()` that touches hardware (device open, callback attach, change-listener subscribe, MIDI inputs). A test subclass overrides it to assert which branch was chosen with none of the side effects.
- **Device latency** — `getInputLatencySamples()` and `getOutputLatencySamples()` are symmetric siblings: both read a value **cached at `audioDeviceAboutToStart`** (cleared at `audioDeviceStopped`) rather than asking the device manager. That's the latency of the stream actually *running* — an engine whose callback is detached is not being clocked by any device, and JUCE re-runs `audioDeviceAboutToStart` on every device change or restart so the cache can't go stale while it is attached — and caching is what makes both assertable headlessly against a fake device. 0 in Hosted mode and 0 when no device has started. `getRecordingLatencySamples()` sums them with the graph's: see [Latency alignment](app-wiring.md#latency-alignment).
- **Module lifecycle** — dynamic addition/removal of modules and connections in the graph.
- **Preset load/save** — delegates to `PresetManager`.
- **Modulation-matrix view** — `getModulationRoutings()` returns a `std::vector<ModulationRouting>` derived on demand from the live graph. Never serialized. `RoutingKind` values: `AttenuverterChain`, `DirectCV`, `PolyBus`. `getActiveModRoutings()` and `getModulationDisplayInfo()` are thin adapters over it.
- **Voice count / mute API** — `getDisplayVoiceCount()`, `setMasterMute(bool)`, `isMasterMuted()`.
- **Host modes** — `HostMode::Standalone` (default) vs `HostMode::Hosted` (used by the audio-plugin wrapper). Both funnel through one private `renderNextBlock` (which delegates to `renderPass`, once per callback or once per slice) so master-mute semantics can't drift between them. See [Plugin Layer](plugin-layer.md) below.
- **Device-callback attachment** — `isReceivingDeviceCallbacks()` / `suspendDeviceCallback()` / `resumeDeviceCallback()`. "Is something else clocking this graph right now?" is the precondition every offline renderer needs, and the host mode alone can't answer it — a Standalone engine whose callback has been detached is just as quiescent as a Hosted one. Suspending mirrors exactly how `initialise()` attached the callback; JUCE calls `audioDeviceStopped()` on the way out (so the caller owns re-preparing the graph) and `audioDeviceAboutToStart()` on the way back in (so re-attaching re-prepares at the *device's* rate on its own). Used by [Bounce/export](#bounceexport).
- **Transport** — the engine owns a `synth::TransportService` (`getTransport()`) and installs it as the graph's playhead once, in the constructor (`mainProcessorGraph.setPlayHead(&transport)`); JUCE re-applies it to every node on every render pass, so nodes re-created by a preset load or an undo restore need no re-injection. `transport.tick(numSamples)` runs as the first thing in `AudioEngine::renderPass` — before the graph — so it happens exactly once per **render pass** in both host modes (one pass per callback normally; one per 64-sample slice when control-rate slicing is enabled, which advances the transport in smaller steps but by the same total), and `transport.prepare(...)` runs before the graph's `prepareToPlay` in both `audioDeviceAboutToStart` and `prepareForHost`. `getGraphLatencySamples()` **reports** the graph's aggregate latency (JUCE's graph already compensates parallel paths internally); the engine adds no compensation of its own. `getOutputLatencySamples()` reports the open output device's buffering the same way — 0 in Hosted mode (the host owns the device) and 0 when no device has started; the playhead subtracts it so the drawn line matches what is *heard* (see [`docs/timeline/playhead.md`](../timeline/playhead.md#latency-offset)), and `getRecordingLatencySamples()` folds it into the round trip a recorded take is shifted back by.
- **Timeline snapshots** — the engine also owns a `synth::TimelineSnapshotExchange` (`getTimelineSnapshots()`) and opens exactly one block on it per render pass, immediately after the tick, so the snapshot reclamation epoch advances in lockstep with the clock. `shutdown()` calls `reclaimAllUnsafe()` last, once nothing can read it. See [TimelineSnapshot](timeline.md#timelinesnapshot-the-audio-threads-view-of-the-timeline).
- **Automation** — alongside the snapshot exchange the engine owns an `EpochExchange<AutomationBindingTable>` (`getAutomationBindings()`) and an `AutomationApplier`. `publishTimeline(doc)` is the single message-thread entry point that feeds both; `renderPass` applies one pass' worth of automation between the MIDI capture point and `graph.processBlock`. `setAutomationSlicingEnabled(bool)` (default **off**) turns the whole per-block sequence into a per-64-sample-slice sequence. `setAutomationRecorder(AutomationRecorder*)` (null by default) hands the applier the recorder's audio-visible half — the per-lane record modes and the in-flight gesture claims it must yield to. The engine also owns a `synth::AutomationUiFeed` (`getAutomationUiFeed()`), passed into every `applyBlock` call so automation-driven writes can reach the UI without a notifying parameter write. See [Automation applier](timeline.md#automationapplier-writing-automation-into-live-parameters), [Automation recorder](timeline.md#automationrecorder-record-modes-and-gesture-capture) and [UI reflection](timeline.md#ui-reflection-automated-parameter-changes-shown-in-the-ui-without-a-feedback-loop).
- **MIDI Remote sink** — `AudioEngine::setRemoteMessageSink(synth::midi::RemoteMessageSink*)` stores a `std::atomic<RemoteMessageSink*>` (null by default) with the same borrowed-pointer handshake as `setMidiCaptureSink`: publish, then `drainAudioCallbacks()`, and the owner clears it before the engine is destroyed. `handleIncomingMidiMessage` consults it **before** the `ExternalMidiModule` fan-out and before the `midiMessageCollector` push; a message the sink reports as consumed goes nowhere else, so a CC bound to a knob never lands in a recording take or an External MIDI node (see the MIDI Remote docs). The source key is the `juce::MidiInput`'s **identifier** (not its name — the name is what the `ExternalMidiModule` binding matches on, and the two are deliberately different keys). `handleIncomingMidiMessageFromSource(key, message)` is the real implementation and the `juce::MidiInputCallback` override is a thin forwarder, so a test can drive the whole path without a hardware device. In `HostMode::Hosted` the same sink is called per message from `processHostBlock`'s input buffer — on the **audio thread** — and consumed messages are filtered out into a pre-allocated scratch `juce::MidiBuffer` before `renderNextBlock`; the sink is built for that (no lock, no allocation).
- **MIDI recording** — `synth::MidiRecorder` (`Source/Timeline/MidiRecorder.h/.cpp`) records external MIDI into a new timeline clip as one undo step. `AudioEngine::setMidiCaptureSink(MidiRecorder*)` stores a `std::atomic<MidiRecorder*>` (null by default); `AudioEngine::renderPass` calls `recorder->captureBlock(midiMessages, transport.getCurrentBlockInfo())` unconditionally, right after the snapshot is opened and just before the automation applier. This is the **single** capture point, and deliberately so: `handleIncomingMidiMessage` forwards every external MIDI message to two places — a direct `pushMidiMessage()` into any bound `ExternalMidiModule`, and `midiMessageCollector`, which is what `midiMessages` here actually is (collector-drained in standalone mode, delivered directly by the host in hosted mode). Recording from the `ExternalMidiModule` push-path copies too would double-record any note whose source also has an ExternalMidi node bound to it — those copies stay internal to that module's own `processBlock` and never reach this buffer, so capturing only here is what makes "recorded once, from the single collector-merged stream" true. `captureBlock` is lock-free and allocation-free: it pushes a POD `{beat, pitch, velocity, channel, isNoteOn}` per NoteOn/NoteOff into a fixed 4096-slot `juce::AbstractFifo` ring (dropping and setting an atomic overrun flag if full, never blocking); `stopAndCommit` (message thread) drains the ring, pairs NoteOn/NoteOff by `(pitch, channel)`, and commits a single new "Take" clip via `AppUndoManager::recordTimelineChange`. See [`docs/control/midi-input.md`](../control/midi-input.md) for the two-paths detail this taps into.
- Requires `#include <bit>` for `std::popcount` (C++20).

## TransportService (the one clock)

`Source/Transport/TransportService.h/.cpp`, `Source/Transport/TempoMap.h`, `Source/Transport/BlockTimeInfo.h`

The timeline's transport spine: play state, sample position, BPM, time signature, and loop bounds (in beats), headless-testable with no device dependency.

- **Beats are canonical.** All musical-time conversion goes through the two-method `TempoMap` seam (`beatFromSample`/`sampleFromBeat`), implemented by `ConstantTempoMap` for v1. A BPM change preserves the beat position and re-derives the sample position; so does a sample-rate change (`prepare`).
- **Command FIFO, never a lock.** The message thread posts POD commands (`play`/`stop`/`locateBeat`/`setLoop`/`setBpm`/`setTimeSignature`) through a lock-free SPSC `juce::AbstractFifo`, drained in posting order at the top of `tick()`. Posts are non-blocking and return `false` when the FIFO is full (dropped, caller may re-post). Commands take effect at sample 0 of the next block.
- **`tick(numSamples)` once per callback** computes an immutable POD `BlockTimeInfo` (block start/end ppq, loop-wrap sample offset, bpm, time sig, play/loop state) describing the block *before* the graph renders it, then advances the position, wrapping at the loop end (a wrap landing exactly on the block boundary reports `loopWrapSample == -1`; tiny loops wrap by modulo). Zero allocation on the audio path.
- **It is a `juce::AudioPlayHead`.** The engine installs it with `graph.setPlayHead(...)`; `juce::AudioProcessorGraph` re-applies the playhead to every node processor on every render pass, so every module — however created (fresh drop, preset load, undo restore) — reads the transport via the standard `getPlayHead()->getPosition()` API with no per-node injection bookkeeping. Sample-accurate consumers on the audio thread use `getCurrentBlockInfo()` instead. `AudioEngine` is the owner that wires this up: it calls `setPlayHead(&transport)` in its constructor, `transport.prepare(...)` ahead of the graph's `prepareToPlay`, and `transport.tick(...)` as the first statement of `renderPass` — the single site both Standalone and Hosted modes clock the graph from.
- **Cross-thread reads** (UI playhead, status bar) go through `getPositionSnapshot()`, a seqlock over individual atomics — consistent multi-field reads, no locks, no tearing. The snapshot reflects the start of the current block (what's audible now).
- **The playhead also carries this block's `TimelineSnapshot`.** `setCurrentTimelineSnapshot` / `getCurrentTimelineSnapshot` park a *borrowed* pointer on the transport; `AudioEngine::renderPass` sets it from `timelineSnapshots.beginAudioBlock()` immediately after `tick(...)`. The playhead is the only thing every module already has a handle to, so this is how a module reaches the timeline without per-node injection: downcast `getPlayHead()` to `synth::TransportService*` and read `getCurrentBlockInfo()` and the snapshot together, off one object. Two rules, both load-bearing: the pointer is **written and read on the audio thread only** (hence a plain pointer, no atomic), and it is **valid for the current block only** — caching it in a module member and reading it next block is a use-after-free, since the exchange frees a superseded snapshot two callbacks after retiring it. It is legitimately null (nothing published yet, a bare transport in a unit test), so every reader null-checks.
- **Permanent, unconditional integration.** The playhead install, the engine's per-block tick, and the sequencer sync dispatch are ordinary, always-compiled engine code — there is no build-time flag and no alternate configuration to keep in sync. `AudioEngine::setTransportEnabled` is a separate, purely runtime API (no persisted setting drives it; nothing calls it outside `AudioEngineTransportTests.cpp`) that freezes/resumes the transport without a rebuild.
- **Offline rendering** — `synth::OfflineTransportDriver` (`Source/Transport/OfflineTransportDriver.h/.cpp`) clocks an `AudioEngine`'s graph at a fixed sample rate / block size with **no audio device**: it drives the engine through `prepareForHost` / `processHostBlock` and offers `renderBlocks(n)` and `renderToBeat(beat)`, the latter rendering whole blocks until the just-rendered block's `endPpq` reaches the target, so it may overshoot by up to one block and returns an empty buffer rather than spinning if the target isn't ahead of a *playing* transport. `streamBlocks` / `streamToBeat` are the same two loops with **nothing accumulated** — the per-block `BlockCallback` is the only way to see the audio and the return value is a block count; that is what bounce/export renders through, since handing it a contiguous buffer of a ten-minute take (~230 MB at 48 kHz stereo) would be pure waste. `renderBlocks`/`renderToBeat` are implemented on top of the streaming pair, so there is exactly one loop per shape. Both streaming calls take an optional pre-block `BlockGate`: a predicate consulted *before* each block that ends the loop without rendering it — the seam a consumer both cancels through and blocks in (bounce/export waits there for `AudioClipStreamer`). The precondition is **"nothing else is clocking this graph"**, asserted as `!engine.isReceivingDeviceCallbacks()` — a `HostMode::Hosted` engine satisfies it by construction, a Standalone one only after `AudioEngine::suspendDeviceCallback()`. This is the headless harness every engine-level timeline test uses. Allocation happens once per accumulating render call on the message thread; the per-block path allocates nothing.

### Bounce/export

`Source/Transport/BounceExporter.h/.cpp` — `synth::BounceExporter::bounce(engine, outFile, BounceOptions, progress)` renders a beat range of the **current patch** to a WAV file, faster than realtime, through the same graph the app plays through. Message thread, blocking. There is no second offline-only signal path to keep in sync: the loop is `OfflineTransportDriver`, the clock is the app's own `TransportService` driven through its normal stop/locate/play commands, and the modules are the live nodes. The only difference from playback is that nobody is waiting for a device — there are no sleeps and no device on the path, it just renders. (Order of magnitude: `BounceExporterTest.EnergyWhereNotesAre` builds its patch, bounces 4 seconds of audio and reads the file back in well under 100 ms.)

- **Device suspension.** A Standalone engine with a live device is detached for the duration via `AudioEngine::suspendDeviceCallback()` (the exact inverse of `initialise()`'s `addAudioCallback`), so nothing else clocks the graph while the render owns it. JUCE calls `audioDeviceStopped()` on the way out and `audioDeviceAboutToStart()` on the way back in, so **re-attaching re-prepares the graph and the transport at the device's rate by itself** — `resumeDeviceCallback()` must not do that by hand. A Hosted engine is used as-is (its host owns the clock; there is no portable way for us to quiesce it). `AudioEngine::isReceivingDeviceCallbacks()` is the tracked bool behind all of this and the property the driver asserts on.
- **Choreography.** Save the position snapshot (position, play state, loop state) and the graph's prepare format → suspend the device *and* external MIDI delivery (`AudioEngine::suspendDeviceCallback()` + `suspendExternalMidi()`, the latter via `synth::ExternalMidiSuspendGuard`, `Source/Transport/BounceGuards.h` — shared with `StemSession`, see [Stem export](#stem-export) below) → construct the driver (which re-prepares the graph at the render format) → `stop()`, `setLoop(..., enabled=false)` (a bounce renders the range **linearly**; a live loop would make "render until `endBeat`" unreachable), `locateBeat(startBeat)`, `play()` → render one block on its own, then `streamToBeat(endBeat)`. The lone first block is load-bearing: `streamToBeat` decides whether the target is ahead of the playhead by reading the *cross-thread position snapshot*, which the queued locate has not reached yet, so bouncing bars 1–2 while the playhead sits at bar 40 would otherwise bail out instantly. It is not a throwaway — a command takes effect at sample 0 of the block that drains it, so that block *is* the first block of the range.
- **Length.** Whole blocks only: `ceil(rangeSamples / blockSize) × blockSize`, up to one block past `endBeat`, plus `ceil(tailSeconds × sampleRate / blockSize)` tail blocks.
- **Tail semantics.** The tail is rendered with the transport **stopped**, so time-locked sources (clips, sequencers) fall silent while reverbs and delays ring out. That is the difference between a tail and simply bouncing a longer range.
- **Restore.** External MIDI delivery resumed first (before the device, so nothing depends on ordering between the two), loop state restored, playhead located back to where it was, and left **stopped** — bouncing from a playing transport leaves you stopped at the prior position, which is what every DAW does. Transport commands only take effect on a tick and nothing is going to tick the engine again, so the restore renders one throwaway block to make them real; that is what lets a caller read the restored position straight after `bounce()` returns. The prepare format goes back too (the device's on re-attach, otherwise the previous hosted format).
- **Streamed audio clips.** A bounce outruns `AudioClipStreamer`'s prefetch thread by orders of magnitude, and constructing the driver re-prepares the engine, which runs `invalidateAllStreams()` — so with no handshake every Track Audio clip would start with a silent head and drop out at the disk's whim. Each block therefore waits, **before it is rendered**, on `AudioClipStreamer::waitUntilPrimed(beat, bpm, sampleRate, framesAhead, timeoutMs)`: it steers every open stream to the frame that clip will be asked for at `beat` (through `synth::sourceFrameForClipBeat`, the one beat→file-frame mapping playback also uses) and blocks until each ring covers it. The beat comes from the last block's `BlockTimeInfo::endPpq`, not from the position snapshot, which lags a block behind. Cheap once primed; a wait that times out counts one `BounceResult::streamDropouts` and renders anyway, so a starved disk is *reported*, never silently mixed in. With the prefetch thread paused for a test the priming call fills synchronously on the calling thread, which is what keeps offline renders deterministic and sleep-free.
- **Cancellation.** The progress callback returns `false` to cancel. Two things end the render: the callback posts `transport.stop()` (a stopped transport reaches no beat, so `streamToBeat` gives up one block later), and the driver's pre-block `BlockGate` refuses the next block outright. The gate is what stops the **tail**, which renders with the transport already stopped and would otherwise run to its full length with nobody writing the blocks.
- **Atomicity.** The render goes to a sibling `juce::TemporaryFile` and is moved into place only on success, so a failed or cancelled bounce never leaves a truncated file and never touches a file that was already there. An unwritable or nonexistent destination fails when the stream is opened — before a sample is rendered.
- **Determinism.** Two bounces of the same project are byte-identical. Nothing on the render path reads the wall clock (that is what driving the graph from the transport rather than a device bought), voice allocation is deterministic, and block boundaries are a function of the options alone. The qualifier is *the same project*, not *the same session*: bouncing twice in a row from one live engine starts the second render from whatever DSP state the first left behind (free-running oscillator phase, an un-decayed delay line), because `prepareToPlay` resets rates and ramps but not phase.
- **Non-render-safe modules.** Every offline block is handed an **empty** `juce::MidiBuffer`, and the engine's `midiMessageCollector` is never drained offline (no device callback is running to drain it). Live-input modules therefore contribute silence to a bounce **by definition, not by accident** — External MIDI, and any future hardware-input module, have nothing to emit. `ExternalMidiModule` is the one module that doesn't wait for that path: it keeps its own collector fed straight from `handleIncomingMidiMessage`, which a real MIDI driver thread calls independently of the device callback `suspendDeviceCallback()` detaches. `AudioEngine::suspendExternalMidi()`/`resumeExternalMidi()` (an atomic flag checked at the top of `handleIncomingMidiMessage`, not a `juce::MidiInput::stop()`/`start()` — the latter only narrows the race against a callback already in flight, it doesn't close it) closes this the same way `suspendDeviceCallback` closes the audio side; `BounceSession` (and `StemSession`, see [Stem export](#stem-export) below) pairs the two behind one shared RAII guard (`synth::ExternalMidiSuspendGuard`, `Source/Transport/BounceGuards.h`) so a note physically played while a render is running is dropped. The one residual gap: a message the driver thread had already queued a moment before the interlock engaged can still drain into `ExternalMidiModule` on the render's first block — `juce::MidiMessageCollector` has no message-thread flush in its contract, so this is narrowed, not eliminated.
- **The metronome** is summed *after* the graph (see the subsection below), which keeps it out of any in-graph tap by construction — but a bounce captures exactly that post-graph buffer, so `bounce()` forces it off explicitly (`synth::MetronomeForceOffGuard`, `Source/Transport/BounceGuards.h`) rather than relying on the summing point alone.
- **Formats.** WAV or AIFF (`BounceOptions::format`), 16 / 24-bit integer PCM, or 32 = IEEE-float **WAV only** — `juce::AiffAudioFormat` has no float variant, so `validate()` rejects `Aiff` + 32-bit before a file is touched rather than let `createWriterFor` fail later with a generic message. A 32-bit WAV bounce (`WavAudioFormatWriter` sets `usesFloatingPointData` for 32-bit) is a bit-exact copy of what the graph produced, with no clipping and no dither decision to make. `sampleRate` is free to differ from the device's.
- **The choreography lives in `BounceSession` (`Source/Transport/BounceSession.h/.cpp`), not in `bounce()` itself.** `bounce()` is `BounceSession` driven to completion in one call — construct, then `stepRange`/`stepTail` in a loop with an unbounded chunk size, then `finish()`. This is what lets the exact same render loop back both the synchronous, test-covered path and the chunked one below, with no second copy to drift.
- **Arrangement length.** `TimelineDoc::getArrangementEndBeat()` is `max(clip.startBeat + clip.lengthBeats)` across every track's clips, 0.0 with none — the "whole arrangement" default the Export Audio dialog offers. It is deliberately blind to automation lanes and markers, which have no audible length of their own.

### Stem export

`Source/Transport/StemExporter.h/.cpp` (see [`docs/mixer/stem-export.md`](../mixer/stem-export.md)) — `synth::StemExporter::exportStems(engine, destinationFolder, BounceOptions, progress)` is stem export's counterpart to `bounce()`: ONE render pass through the exact same offline path (`OfflineTransportDriver`, the app's own `TransportService`), writing one audio file per mixer channel strip instead of one file for the whole mix. Message thread, blocking, same options/progress/cancel contract as `bounce()`.

- **The tap.** `ChannelStripModule::setStemTapBuffer(buffer)` arms a non-owning pointer to a caller-preallocated stereo buffer, null outside an export. Armed, the strip copies its FINAL output — post gain, pan, mute *and* solo, i.e. exactly what it hands to `Master` — into the tap at the end of *every* `processBlock` exit path (bypass, mute, solo-gated silence, normal), via one `finishBlock` helper the branches all funnel through. No allocation, no locks: an atomic pointer load/store and, when armed, one `copyFrom` per leg. `StemSession` preallocates one tap buffer per strip, sized to the render's block size, before arming any of them, and disarms every one on the way out (success, cancel, or setup failure) — a subsequent normal render never writes into memory the session already freed.
- **The choreography lives in `StemSession` (`Source/Transport/StemSession.h/.cpp`), a deliberate sibling of `BounceSession` rather than one class generalised over "one writer vs N".** Both classes' shapes are identical — validate → suspend device+external-MIDI → construct the driver (reprepares the graph) → stop/unloop/locate/play → stream blocks → restore — and the genuinely shared pieces (`synth::validateBounceOptions`, declared in `BounceExporter.h`; the metronome/external-MIDI RAII guards, `Source/Transport/BounceGuards.h`) are factored out so neither duplicates them. `BounceExporter`'s own behaviour and test suite are unchanged by this. Where `BounceSession` owns one `juce::AudioFormatWriter` and writes the graph's own rendered block, `StemSession` owns a `std::vector` of writers (one per strip) and, after each block, writes every strip's tap buffer to its own writer — the mix itself is never written anywhere.
- **Enumeration and naming.** Strips are found by scanning the graph for `ChannelStripModule` nodes (`synth::collectStemStrips`), ordered by ascending node id — the "else node id" stable-order fallback [`docs/mixer/stem-export.md`](../mixer/stem-export.md) allows, since `Source/Transport` has no dependency on the timeline/track model. Files are named `"NN - <strip name>.<ext>"`; `<strip name>` is the node's own `getName()` (there is no user-editable per-strip display name today), so distinct strips read as `"01 - Channel Strip.wav"`, `"02 - Channel Strip.wav"`, etc. — the `NN` prefix alone already makes every name unique.
- **No strips.** `StemExporter::hasChannelStrips(engine)` is a cheap pre-flight scan `MainComponent::promptExportStems` calls before even opening the dialog, so a patch with nothing to export gets `StemExporter::kNoChannelsMessage` ("No mixer channels yet - use Create channels in the mixer first.") immediately; `StemSession`'s own setup fails with the identical message as a defense-in-depth backstop for any other caller.
- **Atomicity.** Every stem renders to its own sibling `juce::TemporaryFile`; all of them are moved into place only once *every* one of them finished writing successfully. A failed or cancelled export leaves no stem files behind and never touches a file that was already in the destination folder — the folder itself is created (if missing) only after the strip scan succeeds, so a no-strips failure never creates it.
- **The two design decisions that make "the stems sum back to the pre-Master mix" true in every case** (muted/soloed strips still write a file — the tap sits after the strip's own gating, so a silenced strip's stem is silence, never an absent file; `Master`'s Direct input is not a stem, since Direct is not a channel), plus the caveat that both assume every enumerated strip is actually routed into Master's Mix bus (an orphaned or differently-wired strip still gets a stem, and that stem is outside the sum identity), are recorded in [`docs/mixer/stem-export.md`](../mixer/stem-export.md), not repeated here.
- **`StemRunner` (`Source/Transport/StemRunner.h/.cpp`)** is `StemSession`'s chunked, timer-driven twin — `BounceRunner`'s counterpart, same shape, same reason (see the next subsection). `MainComponent::promptExportStems` opens `ExportAudioDialog` in its stems mode (destination is a folder, not a file) and drives a `StemRunner` from it exactly the way `promptExportAudio` drives a `BounceRunner`, sharing `isBounceInProgress_` with Export Audio (the offline render path is exclusive regardless of which of the two is running) and the same `exportDialog_` progress polling in `timerCallback()`.

### Export Audio dialog and BounceRunner — chunked, not threaded

The Export Audio dialog (`Source/UI/Chrome/ExportAudioDialog.h/.cpp`, wired up by `MainComponent::promptExportAudio`) needs a responsive progress bar and a Cancel button that actually works, but `bounce()`'s "message thread, blocking" contract above is load-bearing, not incidental — `AudioEngine::suspendDeviceCallback`/`resumeDeviceCallback`/`prepareForHost` are message-thread only, and `OfflineTransportDriver`'s constructor calls `prepareForHost` too. Running the render on a second thread would call every one of those off the message thread.

The fix is **`synth::BounceRunner`** (`Source/Transport/BounceRunner.h/.cpp`): it drives the *same* `BounceSession` a synchronous `bounce()` would, but from a repeating `juce::Timer` instead of one blocking call — each tick renders a small chunk (64 blocks by default) via `stepRange`/`stepTail`, then returns, letting the message thread's own event loop run in between. There is no second thread anywhere in this path; `BounceSession` never leaves the message thread, so every one of its message-thread-only calls stays exactly where the invariant above requires. At 64 blocks/tick on a 10 ms timer that is on the order of 70x realtime — chunking costs nothing anyone would notice.

This has two consequences a synchronous bounce never had to worry about:

- **The message thread's own timer keeps running mid-render.** `MainComponent::isBounceInProgress_` is what used to be true "for free" (a blocked message thread cannot fire its own timer) and now has to be tracked explicitly. `maybeAutosave()` checks it exactly like `isRecordingActive()`; `guardUnsavedChanges()` (New Patch/Open/Load preset/Quit) checks it too and refuses rather than mutating or replacing the graph out from under a live render.
- **The progress window must be genuinely modal**, not merely visible — `promptExportAudio()` calls `enterModalState(true, ...)` on the launched `DialogWindow`, so the rest of the app cannot be interacted with while a bounce is in flight even though the message thread is technically free to do so. `MainComponent::exportDialog_` (a `SafePointer`) is what `timerCallback()` polls (`BounceRunner::getProgress()`) into the dialog's progress bar, on the app's existing 10 Hz driver rather than a second timer just for this — and it is a SafePointer specifically so a `BounceRunner` completion firing after the window somehow closed early degrades to a no-op instead of a dangling call; `isBounceInProgress_`/`bounceRunner_` are cleared unconditionally in that same callback either way, so the command is never permanently locked out.

`promptExportAudio()` re-publishes the timeline (`publishTimelineAndRebindRecorder()`) unconditionally right before every render rather than gating on "was it ever published" — `AudioEngine::publishTimeline`'s own contract says re-calling it with an unchanged doc is cheap and always correct, which makes a stale-automation-binding bug impossible instead of merely detected.

**Destination defaults and the file-name field.** `promptExportAudio()`/`promptExportPatchOnly()` both resolve their starting folder through `resolveExportSubdirectory(currentBundleDir_, subFolderName)`: a real, saved bundle gets `<bundleDir>/Exports` or `<bundleDir>/Patches` (created on demand), an unsaved project falls back to the same `ProjectBundle::getDefaultProjectsDirectory()` root every other save/open dialog uses. Neither subfolder is a `ProjectBundle`-reserved name — unlike `Audio/`/`Peaks/` they carry no asset-integrity contract, and `AssetManager::cleanUnusedAssets` never walks past `Audio/`, so nesting them inside the bundle is safe. `ExportAudioDialog` shows the unsaved case as a one-line, non-blocking tip ("save first") rather than refusing — exporting into an unsaved project's `Music/AgentSynth` root is a legal, permanent choice, not an error state. The dialog's own file-name field defaults to `currentPatchName_` (not a fixed "Bounce"), is user-editable, and is kept separate from the folder picker (`chooseDestinationFolder()`, directory-only) so the two rows can never disagree about what the export is actually called. A destination that already exists on Export triggers a three-way prompt (Overwrite / Save as Copy — appends " 2", " 3", ... before the extension / Cancel) rather than a plain overwrite-or-cancel.

Two smaller fixes ride along with the destination defaults above: `ExportAudioDialog` now overrides `paint()` to fill `findColour(juce::ResizableWindow::backgroundColourId)` (see [`Source/UI/CLAUDE.md`](../../Source/UI/CLAUDE.md)) — without it the window showed through as the OS's default light background regardless of theme, since a plain `juce::Component` paints nothing on its own. And the tail control now has a Seconds/Bars toggle (4/4 assumption, the same one the metronome's downbeat detection uses — this app has no time-signature concept anywhere else) backed by a small `ExpandingRangeSlider` subclass whose text box grows the slider's range instead of clamping a typed value away. Cmd+Shift+E (`"exportAudio"` in `ShortcutManager`) opens the dialog — see [`shortcuts.md`](../control/shortcuts.md).

**The loop range as a range source, decoupled from the loop arm.** The dialog's "Range" row offers two radio options — *Whole arrangement*
(`TimelineDoc::getArrangementEndBeat()`) and *Current loop range* — and the loop locators became the second of these. The locators are the
range source, not a live-loop property: `PositionSnapshot` carries `loopStartPpq`/`loopEndPpq` independently of the `looping` flag (a
`setLoop(start, end, false)` writes all three), so a merely *disengaged* loop still names a real span. The *Current loop range* option is
offered whenever that region is non-degenerate (`loopEndPpq > loopStartPpq`), whether or not looping is armed — `promptExportAudio()` decides it from
the snapshot's region alone, and `ExportAudioDialog` never sees an arm flag (its `hasLoopRange` constructor argument is the decision, not the flag).
There is deliberately no auto-fallback to the whole arrangement and no separate "locators unset" state to detect: `TransportService` always carries a
valid `[start, end)` (its own default is `[0, 4)`), so only a *collapsed* region (`end <= start`) disables the option. The exporter needs no change:
it already renders whatever `[startBeat, endBeat)` the caller hands in and unloops for the duration, so an armed and a disengaged region at the same
locators bounce byte-identically — pinned by `BounceExporterTest.LoopRangeWithLoopDisabledBouncesTheLoopSpan` and
`ArmedLoopBouncesByteIdenticallyToADisengagedOne`.

### Metronome + count-in

`Source/Transport/Metronome.h/.cpp` (`synth::Metronome`) — a click generator that is a pure audio-thread synth, not a graph module: `AudioEngine` owns one (`metronome_`, exposed via `getMetronome()`) and calls `renderClicks(buffer, transport.getCurrentBlockInfo())` directly from `renderPass`, **after** `mainProcessorGraph.processBlock` and **before** `renderNextBlock`'s master-mute zero-fill.

- **Why post-graph, and why the ordering matters.** Nothing inside the graph — no module, no future in-graph recording tap — can ever see the click, because it is summed into the buffer only after the graph has already finished with it. Master mute clears the *whole* buffer after this call runs, so it silences the click along with everything else the engine produces — deliberate, mirroring how master mute already treats the graph's own output. A bounce (`BounceExporter::bounce`) is the one place this "post-graph" property is *not* automatically enough: a bounce captures exactly the post-graph buffer, which is the click's insertion point, so it cannot rely on the summing order to keep the click out — see below.
- **Beat-crossing scan.** Mirrors `TimelineMidiSourceModule`'s loop-wrap-aware scan exactly: a block that doesn't cross the loop end is one beat range `[startPpq, endPpq)`; one that does is two — `[startPpq, loopEndPpq)` at offsets `[0, loopWrapSample)`, then `[loopStartPpq, ...)` for the remainder. Every integer beat inside a range fires a click (a range beginning exactly on an integer, e.g. transport start, still fires — no beat is ever skipped or double-fired across two blocks that tile exactly). A beat is a **downbeat** (bar start) when `fmod(beat, beatsPerBar) == 0` (`beatsPerBar = timeSigNumerator * 4 / timeSigDenominator`, the same "a beat is always a quarter note" convention `TimelineTransportBar`/`TransportService::getPosition()` use) — 1600 Hz / amplitude 0.35, vs. 1050 Hz / amplitude 0.25 for every other beat, each an exponentially-decaying sine burst to −60 dB over ~4 ms.
- **Clicks span block boundaries.** A fixed pool of 4 voices (`{samplesRemaining, phase, phaseInc, amp, decayMul}`) persists across calls rather than resetting per block, so a click starting 5 samples before a block ends continues into the next call with no phase or amplitude discontinuity (`MetronomeTests.cpp`'s `ClickSpansBlockBoundary` proves this by comparing a two-call split render against an uninterrupted single-call render of the identical click). Overflow (a 5th click while all 4 still ring) steals the voice with the **fewest samples remaining** — every voice starts with an identical countdown, so that is the one that has rung the longest. Zero allocation, zero locks, zero logging.
- **Enabled vs. forced-on.** `setEnabled`/`isEnabled` is the user-facing toggle (message thread writes, audio thread reads, both relaxed atomics). `setForcedOn`/`isForcedOn` is OR'd with it — the count-in pre-roll (below) forces the click audible through the pre-roll bars regardless of the user's own toggle. With **neither** set, `renderClicks` is a complete no-op: it does not touch the buffer and does not advance any voice state, so a disabled metronome costs two atomic loads and nothing else (`DisabledMetronomeIsSilentAndFree`).
- **Bounce force-off.** `Source/Transport/BounceGuards.h`'s `synth::MetronomeForceOffGuard` (RAII, shared by `BounceSession` and `StemSession`) saves `isEnabled()`/`isForcedOn()`, forces both off, and restores them in its destructor — unwound on every exit path (success, cancellation, every early-return failure), constructed right after the session obtains its `transport`/`graph` references so it is alive for the rest of the render. This is the explicit mechanism the post-graph-summing paragraph above says is needed: summing order alone keeps the click out of anything *inside* the graph, but an offline render reads the post-graph buffer, so nothing structural saves it there.
- **Count-in choreography.** A persisted setting, `"timelineCountInBars"` (0/1/2, default 0, restored/persisted by `TimelineTransportBar` alongside `"timelineMetronomeEnabled"`), read by `MainComponent`'s `onRecordToggled` handler (the record flow) at the moment Record is clicked:
  - **Stopped, count-in > 0:** `punchInBeat = current ppq`; `preRollStart = max(0, punchInBeat − countInBars × beatsPerBar)`; `transport.locateBeat(preRollStart)`; `metronome.setForcedOn(true)`; `transport.play()`; `midiRecorder.startRecording(armedTrack, punchInBeat)` — the SAME `punchInBeat` is both the recorder's bookkeeping value and (see below) its audio-thread filter threshold.
  - **Already playing, or count-in off:** no pre-roll, no forced-on — `punchInBeat` is simply the current position, matching the transport's original "record implies roll" behaviour exactly (`RecordWhilePlayingSkipsCountIn`).
  - **Clearing forced-on.** `MainComponent`'s existing 10 Hz poll clears `setForcedOn(false)` once `position.ppq >= midiRecorder.getPunchInBeat()` (gated on `midiRecorder.isRecording()`, idempotent once already false). `commitMidiRecording()` also clears it unconditionally on every stop (explicit or auto-committed) — a take that was never in a pre-roll simply clears an already-false flag.
- **The punch-in filter.** `MidiRecorder::captureBlock` drops any event whose computed beat is before `punchInBeat` (a relaxed `std::atomic<double>`, written by `startRecording` before `recording` flips true and never mutated again until the next `startRecording`) — this is what makes a count-in's pre-roll audible (the performer hears the click and can play along) but never committed to the take. `startRecording`'s `punchInBeat` parameter therefore does double duty: informational bookkeeping for every existing caller that passes "now" (the filter is then a no-op, which is why no pre-existing test needed updating when the filter was added), and the actual audio-thread cutoff for the count-in's pre-roll callers.
- **UI.** `TimelineTransportBar` gains a metronome toggle (a drawn "quarter note" `juce::Path`/`juce::Rectangle` glyph, no assets — see [`docs/timeline/transport.md`](../timeline/transport.md#metronome-and-count-in)) and a 3-item count-in `juce::ComboBox` ("Off"/"1 bar"/"2 bars"), both persisting themselves via the bar's own `setApplicationProperties` (the same restore/persist-on-change idiom `TimelinePanelComponent` uses for its snap combo) rather than routing through the panel, which has no other reason to know either setting exists.

### Input monitoring & feedback guard

Live device input reaching the graph makes a mic → speaker loop *possible* the moment a user patches *Audio Input* onward — a resonant filter or a delay with feedback turned up is a genuinely dangerous loop, not a hypothetical one. Two mechanisms, both **ungated** (input-path safety, not a timeline feature):

- **The monitoring gate.** `AudioEngine::setInputMonitoringEnabled(bool)` / `isInputMonitoringEnabled()` is an `std::atomic<bool>` (default **false**), published once per render pass to the transport carrier — `TransportService::setInputMonitoringEnabledForBlock`/`isInputMonitoringEnabledForBlock()`, the same "the playhead is the one handle every module already has" pattern the device-input snapshot and the timeline snapshot use. `AudioInputModule::processBlock` reads the carrier (never the engine atomic directly) and **clears its own output** when it reads false — the engine's device-input *capture* (`captureDeviceInput`) is completely unaffected, so a track recording straight off the device input still works even with monitoring off; only what this module hands the rest of the graph is gated. Recording *taps the graph*, so "monitoring enabled" **is** the record path for input chains — gating anything upstream of the module would break recording, not just monitoring.
- **The feedback guard.** `AudioEngine::runFeedbackGuard`, called from `renderPass` **post-graph, pre-master-mute** — right beside the metronome click, after it sums in, so the guard sees exactly what would reach the speakers. Only evaluated while monitoring is enabled (a loud synth alone, or a loud device input the user never wired anywhere, can never trip it): each render pass it takes the peak sample magnitude across the graph's **output** channels only (`mainProcessorGraph.getTotalNumOutputChannels()` — a device with more inputs than outputs parks the extra input channels past the output count in the same render buffer, and a hot mic sitting there unconnected to anything is not feedback) and accumulates a **consecutive-samples** run (not a block count, so the timing is block-size-agnostic — control-rate slicing evaluates the same total elapsed samples in smaller steps) for every pass whose peak is at or above `kFeedbackPeakThreshold` (**0.97**), resetting the run to 0 the moment a pass falls under it. Once the run's elapsed time reaches `kFeedbackSustainSeconds` (**0.25 s**), the guard: disables monitoring (the *same* flag the gate above reads), latches `feedbackGuardTripped_` for the UI, and **zeroes that render pass's entire output immediately** — it does not wait for the disabled flag to take effect on the next pass, which could be a whole device block away. It cannot pin an exact in-block trip sample (the peak is measured over the whole pass), so it clears the whole pass rather than guessing an offset. The run also resets whenever monitoring is off, so a loud stretch that happened before monitoring was enabled can never count toward a trip the moment it's switched on.
- **UI surfacing + the re-arm rule.** `MainComponent`'s existing 10 Hz poll derives the gate's input: `isInputMonitoringEnabled` should be true exactly when some `TrackKind::Audio` track has `armed == true` (mirroring the audio-recording armed-track lookup, but existence rather than first-wins — the gate does not care which armed track would host the take). `consumeFeedbackGuardTripped()` (an atomic exchange, consumed **exactly once** per trip) shows `statusBar.showMessage("Input muted — sustained clipping (feedback protection)")` and latches `feedbackGuardLatched_` — a `MainComponent`-side bool, **not** part of the engine — which keeps monitoring off on every subsequent poll for as long as the **same arm state** persists, even though the Audio track is still armed. The latch clears only on the arm set's **false → true edge**: disarming every Audio track and then arming one again is the explicit reset gesture; simply *staying* armed after a trip must not silently re-enable monitoring.
- **Thresholds are public `constexpr` on `AudioEngine`** (`kFeedbackPeakThreshold`, `kFeedbackSustainSeconds`) rather than buried in the `.cpp`, so a test asserting the guard's timing does not have to duplicate the numbers by hand. 0.9 and 0.95-amplitude signals both sit under the 0.97 peak margin and must never trip however long or bursty they run (`FeedbackGuardTest.FalsePositiveCorpus`); a 3-block loud transient is far short of the 0.25 s sustain margin (`BriefTransientDoesNotTrip`).

### Mixer solo gate

Solo on a `Channel Strip` is a **render-time gate, never a parameter write** ([`docs/mixer/mixer.md#solo-is-a-render-time-gate`](../mixer/mixer.md#solo-is-a-render-time-gate)). Each strip keeps its own `soloed_` flag (an atomic, persisted only in trusted extra state); the engine owns `soloedStripCount_`, "how many strips are soloed?", and publishes `count > 0` once per render pass through the same carrier as the monitoring gate above — `TransportService::setMixerSoloActiveForBlock` / `isMixerSoloActiveForBlock()`, set in `renderPass` before the graph runs. While it is set, every non-soloed strip (bypassed or not) and `Master`'s Direct input output silence.

- **The count is recounted on the message thread by scanning the graph** (`AudioEngine::refreshSoloGate`), never incremented/decremented by hand. It runs inside `publishTimeline`, which every graph change already has to reach (see [App wiring](app-wiring.md#app-wiring--who-owns-the-timeline-and-every-hook-that-keeps-it-in-step)'s hook inventory), so a deleted, replaced or undone soloed strip can never leave the mix stuck silent. The plugin's `setStateInformation` replaces the graph without publishing, so it calls `refreshSoloGate()` itself. **A new path that changes the graph without reaching `publishTimeline` must do the same.**
- **`AudioEngine::setChannelStripSoloed(nodeId, bool)`** is the one call a UI makes: it flips the strip's flag and recounts, ordered so no render pass ever sees the gate closed with nothing soloed (solo raises the flag first; un-solo drops the count first).
- **Offline renders honour solo today.** A bounce drives the same `renderPass` (via `OfflineTransportDriver` -> `processHostBlock`), so a soloed strip silences the rest of an exported mix exactly as it does live. Stem export must decide whether a render forces the gate open, the way the metronome is forced off.
- **Known quirks, inherent to extra-state persistence**: a solo toggle does not move the undo edit serial (no dirty flag, no autosave on its own), and because solo rides in the graph snapshot, undoing an unrelated earlier graph edit restores the solo state that snapshot held.
