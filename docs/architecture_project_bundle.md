# Project bundle (.agsproj)

The on-disk project format and everything the app does with it: open/save, recent projects, dirty state and the unsaved-changes guard, autosave and crash recovery, the welcome screen.

Part of the architecture docs — start at [`architecture.md`](architecture.md) for the
layer map, signal flow and the index of the other topic docs.

## 5. ProjectBundle (.agsproj)

`Source/ProjectBundle.h/.cpp`

The on-disk project format that pairs a patch with a `TimelineDoc`. A bundle is a directory named `*.agsproj` containing `project.json` plus two asset subdirectories, `Audio/` and `Peaks/` (created empty; the audio-recording flow is the first thing to write into them). `project.json` is everything `AIStateMapper::graphToJSON` writes (nodes, connections, modulations, schemaVersion, any keys `PatchDocument` had stashed from a prior load) with one addition: a top-level `"timeline"` key holding `TimelineDoc::toVar()`.

- **`"timeline"` is reserved everywhere else, meaningful only here.** A plain `.json` preset that happens to carry one only ever stashes it inertly via `PatchDocument` (see §3 above); `AIStateMapper::validatePatch` refuses it outright from provider-authored output (`PatchValidationError::TimelineNotAllowed`) so a model can never author automation. `ProjectBundle` is the one place a `"timeline"` key is actually interpreted.
- **Fixed, all-or-nothing load order**, mirroring `SnippetManager::insertSnippet`'s trusted/untrusted pairing:
  1. Parse `project.json` — unparseable or non-object is rejected.
  2. **Detach `"timeline"` from the root before anything else.** This has to happen *before* the gate in step 3: the untrusted validator refuses any patch carrying a `"timeline"` key, and a bundle's `"timeline"` is this format's own dialect, not provider output smuggled in — pulling it out first means it's validated on its own terms in step 4 instead of tripping a check meant for a different threat. The remaining root is "the patch".
  3. **Gate:** `AIStateMapper::validatePatch(patch, graph, clearExisting=true, trusted=false)`. `project.json` is a file on disk, hand-editable exactly like a preset or a snippet — a malformed patch is rejected whole, never partially applied.
  4. Validate the timeline into a **local** `TimelineDoc` via `fromVar` (already all-or-nothing). A missing `"timeline"` key is not an error — it means a plain patch is being opened as, or upgraded into, a bundle, and the timeline starts empty. A present-but-malformed one is rejected whole.
  5. Only once *both* validations pass does anything mutate: `applyJSONToGraph(patch, graph, clearExisting=true, trusted=true)` — trusted, so node `"uuid"`s are honoured and parameter values aren't rescaled by the untrusted-input heuristic, the same reasoning as the snippet insert path; `patchDocument.loadFromVar(patch)` on the timeline-stripped root, so `"timeline"` is never double-stored in the stash; then the live `timeline` is brought to the validated state (`fromVar` on the same var already proven valid against the local doc, or `clear()` when the key was absent).
  6. **Binding pass — never delete.** `TimelineReconciler::reconcile(timeline, graph)` recomputes every track's `bindingUuid` and lane's `nodeUuid` against the freshly-loaded graph's live node uuids (see §3's "Orphaned bindings" for the full policy). A binding that no longer resolves is retained and flagged `orphaned`, never deleted; one that resolves is (re-)confirmed. Running this at the end of `load` means a freshly opened project shows correct orphan state immediately, before the user touches anything.
  - On any failure before step 5, `graph`, `timeline` and `patchDocument` are left exactly as they were.
- **Save order matters too.** `graphToJSON(graph)` → `patchDocument.toVar(...)` (re-merging whatever unknown top-level keys were stashed on this bundle's last load) → **then** `"timeline"` is set to `timeline.toVar()` **last**, so a live timeline always overwrites a stale one sitting in the stash (e.g. a bundle that started life as a plain `.json` carrying an old `"timeline"`).
- **Asset policy (enforced since audio recording arrived).** Any asset reference stored in the document (`Clip::assetRef`) is a path *relative to the bundle root* (`Audio/foo.wav`) — an absolute or escaping path is rejected, the same restriction as `ModuleBase::setExtraState`'s trusted-only file paths. The check is `TimelineDoc::isValidAssetRef`, applied by both `setClipAsset` and `fromVar`. The record flow writes takes into `Audio/take-<n>.wav` + `Peaks/take-<n>.agpk`.
  - **Unsaved projects — adopted on save.** A take recorded before the project has ever been saved has no bundle to go into: it lands in `<user app data>/<settings folder>/Recordings/` and its clip carries the reserved prefix `Recordings/take-<n>.wav` — still relative in form, so the one path rule holds, but resolved against app data rather than a bundle root. `synth::AssetManager::adoptRecordingsAssets` (see the "Asset management" section below) moves those files into `Audio/` on the first save and rewrites the refs. `Recordings/` is therefore a reserved subdirectory name inside a bundle.
  - **Nothing is ever auto-deleted from `Audio/`/`Peaks/`.** Undoing a take removes the clip, not the recording. Reaping unreferenced files is `synth::AssetManager::cleanUnusedAssets`'s job.
- **Plain `.json` save/load is unaffected.** `GraphEditor::savePreset`/`loadPreset` are untouched by this class — a `.agsproj` is a parallel format, not a replacement.

### Opening and saving one from the app

The toolbar's existing Save and Load-from-file dialogs carry both formats (`"*.json;*.agsproj"`), and `MainComponent::saveToFile()` / `openFromFile()` — the dialog callbacks' whole bodies, and the two `…ForTest` hooks tests drive instead of a dialog — branch on the `juce::File` they are handed:

- **Save.** A name ending in `.agsproj` writes a bundle (`ProjectBundle::save(dir, graph, timelineDoc, graphEditor.getPatchDocument())`, creating the directory and its `Audio/`/`Peaks/` subdirectories). Anything else is `GraphEditor::savePreset` exactly as before — a plain `.json` preset carries no `"timeline"` key.
- **Open.** A `.agsproj` is a **directory**, so the open dialog also sets `canSelectDirectories`; the handler confirms `ProjectBundle::isBundle()` before doing anything. The load is bracketed the way `GraphEditor::loadPreset` brackets its own (detach module components *before* the graph's processors are freed, `updateComponents()` after, whatever the outcome), wrapped in a programmatic-apply scope, and followed by the standard reconcile+publish pass. Anything else goes down the untouched `loadPreset` path, which leaves the live timeline alone.
- The `PatchDocument` is the graph editor's own (`GraphEditor::getPatchDocument()`), so a bundle re-merges the very same unknown-top-level-key stash a plain preset load filled.
- Both branches always exist — the dialog offers both formats unconditionally, since `.agsproj` bundles are a permanent part of the app rather than something a build configuration could omit.
- **Cmd+S / the Save button** (`MainComponent::performSaveProject`) defaults toward the bundle format rather than always prompting: with a bundle already open (`currentBundleDir_` set and `ProjectBundle::isBundle` true) it resaves straight to that path with no dialog, and otherwise it prompts with the suggested filename defaulting to `<patch name>.agsproj` under `ProjectBundle::getDefaultProjectsDirectory()` (`<userMusicDirectory>/AgentSynth`, created on demand). "Save Project As" (Cmd+Opt+S) always prompts, and "Export Patch Only" writes a legacy plain `.json` via `GraphEditor::savePreset` directly — without touching `currentBundleDir_` or the window title — as the explicit escape hatch for a patch-only snapshot. Open/save/export dialogs all start in that same directory.
- **Autosave** periodically writes a separate `autosave.json` sidecar next to `project.json` for the open bundle — it never overwrites the canonical file, and it is not itself a save (see "Autosave and crash recovery" below).

### Recent projects

`Source/RecentProjects.h/.cpp` — the Load menu's "Projects" section (`MainComponent`'s `loadButton.onClick`), a first-level submenu alongside the "Patches" submenu (P8-31 split the former single "Load from file..." item — a combined `.json;*.agsproj` + directory browser that conflated a patch with a whole project — into two explicit first-level entries: **Patches** holds the default/factory patches, grouped by category under that submenu, plus an "Open Patch..." leaf; **Projects** holds the recent projects plus an "Open Project..." leaf). A small settings-backed list, same owner-drives-persistence shape as the plugin scan list (`"pluginScanList"`, see below): `RecentProjects` never touches `juce::ApplicationProperties` itself, `MainComponent` restores it from `kRecentProjectsSettingKey` (`"recentProjects"`, `Source/UserSettings.h`) on startup and rewrites it (`saveRecentProjects()`) after every change. Single-owner, unlike the scan list — the plugin editor shares the same `MainComponent`, so there is no second copy to keep in step.

Loading a `.json` patch (the "Open Patch..." leaf, and by extension its "Patches → factory preset" siblings) offers to either **replace** the current patch or **add it on top** (`PatchLoadMode::Replace` / `Append`). An **append** routes the loaded patch through `SnippetManager::insertSnippet` — the same machinery a pasted group uses: `prepareForInsert`/`nextFreeIdBase` renumber its node ids to a free base, so the import **coexists with** rather than matching-and-overwriting the live graph (two separately-saved patches share a small uid space, so a plain `clearExisting=false` merge would clobber it); the imported patch's Audio Output is deduped onto the graph's existing one in `AIStateMapper::applyJSONToGraph` (so no second output node); and, being a trusted user file, it is inserted on the trusted path so a Sampler's loaded sample / a Wavetable's table carry where the untrusted validator a dropped snippet runs would refuse them. The freshly added modules are left selected so the user can nudge the dropped group. A **replace** is a `applyJSONToGraph(clearExisting=true, trusted=true)` rebuild that preserves each node's saved uid (stable across undo/redo) and so raises the `guardUnsavedChanges` prompt. Both arms are wrapped in `undoManager->recordGraphAndMacroChange`, so an import is one reversible step — undo returns to the pre-import patch, redo restores it — and `GraphEditor::loadPreset` finishes either arm with a `fitViewToModules()` pass: a loaded patch keeps its saved coordinates, which often fall outside the current viewport, so the view scrolls + zooms (clamped to the wheel-zoom range) to bring every just-loaded module on-screen instead of landing off-canvas.

- **Entries are absolute bundle paths, most-recent-first, capped at `RecentProjects::kMaxEntries` (10).** `addProject()` dedupes an existing entry for the same path (removed, then reinserted at the front) rather than adding a second one, then drops anything past the cap.
- **Recorded on every successful bundle open/save**: `saveToFile`'s `.agsproj` branch, `loadBundleFromFile`, and `loadAutosaveFromFile` (recovering a sidecar still counts as opening that bundle). A plain `.json` preset load/save and `loadFactoryPresetAtIndex` do not touch the list — they have no bundle path to record.
- **Pruned lazily, at menu-build time.** `pruneMissing()` drops entries whose directory no longer exists on disk and is called right before the Load menu is built, not on a timer or on startup — a bundle deleted or moved outside the app disappears from the list the next time the user opens the menu, and the pruned result is only re-persisted if something was actually dropped.
- **Picking an entry goes through the same `guardUnsavedChanges` + `openFromFile` path** as "Open Project...", so an unsaved document still gets the discard/save/cancel prompt, and a successful open re-adds the same path (moving it back to the front) exactly like any other bundle open.

### Dirty state, and the unsaved-changes guard

`MainComponent::isDirty_` is the app's one document-modified flag, and **the undo manager is its single funnel**. Every graph edit and every timeline edit already goes through `recordStructuralChange` / `recordTimelineChange` / `recordCombinedChange`, so one listener on `AppUndoManager`'s `juce::UndoManager` covers both domains without a listener web of its own. That broadcast is JUCE's **async** `sendChangeMessage()`, so the flag moves on the next message-loop pass, not inside the edit — which is why the tests pump `runDispatchLoopUntil` before asserting on it.

Because the notification is async it is also **always potentially stale**, and that is why the flag is derived from a counter rather than set on arrival. `AppUndoManager::getEditSerial()` counts every action actually pushed onto the undo stack, plus every successful undo/redo; `MainComponent::markDocumentClean()` — the one place `isDirty_` is ever cleared — captures that serial as `savedEditSerial_`, and the listener recomputes `isDirty_ = (serial != savedEditSerial_)`. The case that forces this: **New Patch clears the timeline and the graph as two real undoable steps and only then resets the document**, so a notification for those steps is still queued when the reset runs. A listener that simply set the flag on arrival would re-dirty a brand-new "Untitled" document one message-loop pass after creating it — and the guard below would then interrogate the user about discarding a document they had just created. Comparing serials makes the late notification a no-op, since the baseline was captured *after* those steps. `AppUndoManager::performAction` is the single private wrapper every push goes through, so the serial cannot drift from what the stack holds.

It is deliberately **not** driven from `TimelineDoc::Listener::timelineChanged` (hook 1 in §8). That hook is the audio-thread publish seam, and it fires for doc mutations that are not user edits — most importantly the reconcile pass, whose binding-flag flips are themselves doc mutations. The post-restore hook in `undoManager.setRestoreHooks` pops the programmatic-apply scope *before* it reconciles, so a suppression gate there would leak and a freshly *loaded* project would come up already marked dirty.

The flag is cleared by exactly three things, all of which mean "the document on screen now matches something on disk, or is brand new": a successful `saveToFile` (both branches), a successful `openFromFile` (both branches), and `newPatch()`. All three go through `markDocumentClean()` rather than writing `isDirty_` themselves — a raw `isDirty_ = false` would clear the flag without rebasing the serial, and the next stale notification would undo it. Each clears **before** calling `setCurrentPatchName`, because that is what fires `notifyDocumentTitleChanged()` — the notify has to see the settled state, or the window title keeps a stale ` *`.

**Undoing back to the saved state leaves the document dirty**, and that is the chosen semantics rather than an oversight — the edit serial is a monotonic *count*, deliberately not a position on the stack, so undo moves it forward just as an edit does. Making it a position would need `juce::UndoManager` to expose a stable save-point index, which it does not, and the two failure directions are not symmetrical anyway: a false *clean* loses work silently, a false *dirty* costs one extra prompt. So the flag only ever falls on a real save, load, or new document.

**`guardUnsavedChanges(actionLabel, proceed)` is THE gate**, and every path that replaces or destroys the open document goes through it: New Patch, Open (the guard runs *before* the file chooser opens), the Load menu's factory-preset branch, and application quit (`AppApplication::systemRequestedQuit`, which `closeButtonPressed` already funnels through — one site covers the window's close button, the Dock/taskbar and Cmd+Q). On a clean document it simply runs `proceed`. On a dirty one it asks, and runs `proceed` only on **Discard** or on a **Save that actually succeeded** — a failed write or a cancelled save dialog aborts the destructive action rather than continuing into it. Cancel does nothing at all.

The gate is **asynchronous by nature**: `proceed` may run later, or never. A caller must therefore hand the destructive work *to* the guard rather than doing it and asking afterwards — which is why `newPatch()`, `launchOpenPresetChooser()` and `launchOpenProjectChooser()` exist as separate methods at all, and why `perform()`'s New Patch case returns `true` immediately while the work is still pending.

The dialog is split in two — `promptUnsavedChanges` (an async `juce::AlertWindow`, never a modal loop, `SafePointer`-guarded because the answer can outlive the component) and `applyUnsavedChangesAnswer` (what each arm actually does) — for the same reason `PianoRollComponent::promptExtendClipToFitNotes` is split from `applyExtendPromptAnswer`: a headless test has no message loop to answer a real modal with, so the answer logic has to be reachable without one. The public `unsavedChangesPrompt` `std::function` replaces the real dialog outright when set, the same seam idiom as `onDocumentTitleChanged` on the same class. In every arm that continues, `proceed()` is the **last** statement — the quit continuation destroys the very component whose method invoked it.

`loadFactoryPresetAtIndex()` deliberately does **not** clear the flag, even though it is guarded like the other three. It replaces the *graph* and leaves the live timeline exactly where it was, so "matches something on disk" would be false the moment the timeline holds anything — an unsaved arrangement would survive the load with the flag cleared, and quitting after that would discard it without asking. It records no undo transaction of its own either (it goes through `PresetManager`, not `AppUndoManager`), so leaving the flag untouched is accurate in both directions.

**The bundle-target rule that rides along with it:** any path that replaces the open document with something that is not a bundle must also drop `currentBundleDir_` (and call `refreshAssetRoots()`). Since Cmd+S resaves silently to that path, a stale one means the next save quietly overwrites a project the user is no longer looking at — with the *old* project's timeline still attached, since a factory preset and a plain `.json` both leave the live timeline alone. `newPatch()`, `loadFactoryPresetAtIndex()` and `openFromFile`'s plain-preset tail all reset it, so those documents prompt for a location on their first save.

### Autosave and crash recovery

`MainComponent::maybeAutosave()` runs once per tick of the **same** shared 10 Hz `timerCallback()` — no second `juce::Timer` — right after the three commit-on-stop checks (a take that just committed on this tick may autosave immediately; one still in flight must not). It fires `performAutosave()` only when every one of these holds: enabled in Preferences (`autosaveEnabled`, default on), `currentBundleDir_` is a real bundle (an unsaved project is inert — there is nowhere to put a sidecar until the first explicit save), no take is recording (`isRecordingActive()`, both the audio tap and `MidiRecorder`), the undo edit serial has moved since the last autosave, and the configured interval (`autosaveIntervalMinutes`, default 2) has elapsed.

**The gate is the edit serial, deliberately not `isDirty_`/`isProjectDirty()`.** Autosave never clears `isDirty_` — it is not a save, and never calls `markDocumentClean()` — so gating on the flag alone would rewrite an unchanged sidecar every interval forever. `lastAutosavedEditSerial_` is a baseline **separate** from `savedEditSerial_`: it rebases on a successful autosave write, and again (alongside `lastAutosaveMs_`, the wall-clock baseline) inside `markDocumentClean()` itself — an explicit save/load/new-patch means the sidecar has nothing left to capture, and resetting the elapsed-time baseline stops the very next qualifying tick from firing off a stale gap. Neither baseline is ever read by, or written from, the `isDirty_`/`savedEditSerial_` pair.

**This guarantee no longer holds — P8-5 built exactly the progress dialog this paragraph warned against, and `MainComponent::isBounceInProgress_` is the flag that replaces it.** The synchronous `BounceExporter::bounce()` path above still blocks the message thread for its entire render, but the Export Audio dialog drives a bounce through `synth::BounceRunner` instead (see "Export Audio dialog and BounceRunner" in §2 above), which ticks a `juce::Timer` between chunks specifically so the UI stays responsive — meaning `timerCallback()` (this one included) now CAN run mid-render. `maybeAutosave()` and `guardUnsavedChanges()` both check `isBounceInProgress_` explicitly rather than relying on the message thread being unavailable.

**The sidecar** (`ProjectBundle::saveAutosave`/`loadAutosave`/`hasAutosave`/`discardAutosave`) is `<bundleDir>/autosave.json` — the exact same JSON shape `save()`/`load()` use for `project.json`, built by a shared private helper (`ProjectBundle::buildProjectJson`) so the two can never drift apart. `project.json`, `Audio/` and `Peaks/` are untouched by an autosave write.

**Backup history (Cubase-style).** Before each autosave write, `ProjectBundle::rotateAutosaveBackups` shifts the previous sidecar into a numbered history — `autosave-1.json` (most recent prior state), `autosave-2.json`, ... up to the configured `autosaveBackupCount` (default 5, 0-50). Classic logrotate order: evict `autosave-<count>.json` first, then shift every `autosave-<k>.json` up to `autosave-<k+1>.json` from the oldest kept slot down to 1, then move the old `autosave.json` into `autosave-1.json`, and only then write the new content to `autosave.json`. `autosaveBackupCount == 0` skips rotation entirely (plain overwrite, the original behavior). This history is a **disk-only** safety net: `discardAutosave()` only ever deletes the live `autosave.json`, never the numbered backups, and the in-app recovery prompt only ever offers the live sidecar — recovering from an older numbered backup is a manual (outside-the-app) operation, not part of the recovery UI.

**Preferences are exact-entry, not fixed choices.** `autosaveIntervalMinutes` (1-120) and `autosaveBackupCount` (0-50) are each a `juce::Slider` in `IncDecButtons` style in `PreferencesSettingsTab` — any integer in range, not a preset dropdown — replacing an earlier fixed-choice `ComboBox` for the interval.

**Recovery** happens in `MainComponent::openFromFile`'s bundle branch, *before* either file loads: if `ProjectBundle::hasAutosave()` is true, an async prompt (`promptAutosaveRecovery`, same `AlertWindow::showAsync` + test-hook-seam idiom as `promptUnsavedChanges`) asks Restore vs. Discard rather than silently loading `project.json` over a possibly-newer sidecar.
- **Restore** (`loadAutosaveFromFile`) loads `autosave.json` in place of `project.json` and deliberately does **not** call `markDocumentClean()` — the recovered state diverges from what's on disk, so the document must read as dirty. `isDirty_` is set `true` directly here, the one sanctioned exception to "never write `isDirty_` outside the recompute-from-serial path" documented above: there is no undo action to derive dirtiness from, since this mutates the graph/timeline the same programmatic way `ProjectBundle::load` always has. It also rebases both autosave baselines (`lastAutosavedEditSerial_`, `lastAutosaveMs_`) to this instant — the just-recovered state has nothing new to capture yet, so the next autosave should wait for a further edit rather than fire on the very next qualifying tick. `discardAutosave()` runs only **after** the load succeeds; on failure (a corrupt or hand-edited sidecar failing the same untrusted `validatePatch` gate `project.json` goes through) it falls back to `loadBundleFromFile` instead and the sidecar is deliberately left on disk — a load failure must not strand the user on the previous document *and* destroy the only copy of the data that failed to load.
- **Discard** (`loadBundleFromFile`) loads `project.json` exactly as if there had been no sidecar at all, then discards it.
- A subsequent **explicit** `saveToFile` on a bundle also discards any pending sidecar — a fresh save supersedes it. So does choosing **Discard** on the unsaved-changes guard (`applyUnsavedChangesAnswer`) — that sidecar holds exactly the content the user just said to throw away, and leaving it behind would prompt to "recover" it again the next time the bundle is opened.
- A bundle with no sidecar takes the exact same synchronous path `openFromFile` always has; the async prompt is reached only when `hasAutosave()` is true.
- **P8-11** (startup preference: welcome screen / last project / empty), when it lands, must run this same `hasAutosave`/recovery check before its own auto-open — it is not wired into that path today.
- **T114/P8-10 landed the welcome screen** (below); its Open-Existing and Recent-Project actions both route through `openFromFile`, so this recovery check already runs for those two user-initiated actions with no extra wiring. That does **not** close the P8-11 gap above: P8-11 is a *silent, no-interaction* auto-open on startup, which T114/P8-10 does not implement (every welcome-screen action requires an explicit click) — a future auto-open path still needs its own `hasAutosave` check.

### Welcome screen (T114/P8-10)

`Source/UI/Chrome/WelcomeScreenComponent.h/.cpp` — an **app-only** startup overlay replacing the old "always silently auto-load the factory Default preset" behavior (`AudioEngine::initialise()` still loads it, unconditionally; the overlay just sits on top, offering a real choice before the user does anything else with it). It is not a separate window: `MainComponent` adds it as a full-bounds child, last (`addAndMakeVisible` order controls JUCE z-order), so it also occludes the toolbar while visible — none of the toolbar actions make sense until a choice is made.

- **Gating.** `MainComponent` constructs `welcomeScreen_` only when `ownedAudioEngine != nullptr` — the same idiom `initialiseCommon()` already uses for every other app-only branch (audio-device-state restore, the permissions-gated `AudioEngine::initialise()` call). The plugin ctor is the only one where `ownedAudioEngine` stays null; a hosted plugin's document is host-owned via `getStateInformation`, so this overlay must never exist there. `getWelcomeScreenForTest()` returns null on that path, which is what `WelcomeScreenTests.cpp`'s `NeverConstructsInHostedMode` pins.
- **Four actions**, each a `std::function` callback the component fires and `MainComponent` interprets — the component itself knows nothing about `AudioEngine`/`PresetManager`/`RecentProjects` beyond the `juce::File` list it's handed:
  - **New empty project** → `AppCommands::newPatch` (same guarded path the toolbar's New button uses).
  - **Open our default project** → `MainComponent::loadPresetGuarded(0)`, a helper factored out of the Load menu's own factory-preset branch so both call sites share one guarded body.
  - **Open an existing project** → `openProjectFromFile()` (the project half of the P8-31 split; it already guards before opening the directory chooser for a `.agsproj` bundle).
  - **Pick from Recent** → `MainComponent::openRecentProjectGuarded(file)`, likewise factored out of the Load menu's "Recent Projects" submenu handler; both go through `openFromFile`, so the autosave-recovery check above applies unchanged.
- **The guard runs before the overlay is ever hidden.** `MainComponent::hideWelcomeScreen()` (a safe no-op when null or already hidden) is called only from inside each guarded action's `proceed` continuation — `loadPresetGuarded`'s own lambda, `openFromFile`/`loadBundleFromFile`/`loadAutosaveFromFile`'s success tails, and `newPatch()`'s own body — never unconditionally before or after `guardUnsavedChanges()`. A Cancel answer therefore leaves the overlay exactly as it was; this is the property `WelcomeScreenTests.cpp`'s `DirtyDocumentIsGuardedBeforeWelcomeScreenReplacesIt` pins.
- **Persisted key**: `"showWelcomeScreenAtLaunch"` (default `true`), read/written directly by `MainComponent` — a bare literal, same as `"librarySidebarVisible"`, deliberately **not** added to `Source/UserSettings.h` (that file is reserved for keys more than one owner touches; this one is `MainComponent`-only). The overlay's own toggle ("Show this screen at launch") writes it live via `onShowAtLaunchChanged`.
- **Recent projects** are re-pruned (`RecentProjects::pruneMissing()`) and re-pushed every time the overlay would show — both at construction and from `showWelcomeScreen()` (the reopen path, `AppCommands::showWelcomeScreen`, Help menu on macOS) — so a bundle moved or deleted since the app last built the Load menu's own submenu doesn't leave a stale, dead row.
- **Reopening**: `AppCommands::showWelcomeScreen` (unconditional registration, `setActive(ownedAudioEngine != nullptr)`, no shortcut-table entry — same "menu-only" treatment `checkForUpdates` gets) puts it back on screen without touching the persisted preference.

#### What's New (build-time, no network)

A cheap companion feature, gated on nothing but a successful `git` invocation at CMake **configure** time (not build time): the root `CMakeLists.txt` runs `git describe --tags --abbrev=0` and `git log --pretty=format:%s -n 15` against `CMAKE_SOURCE_DIR`, sanitizes the output (ASCII-range only, `"`/`\` escaped for a C string literal — the CLAUDE.md non-ASCII-literal invariant applies here defensively even though `${CMAKE_BINARY_DIR}/generated` sits outside `Source/` and the lint script's reach, because the generated header still reaches `juce::String` at runtime), and writes `${CMAKE_BINARY_DIR}/generated/WhatsNewData.h` (`synth::whatsnew::kReleaseTag`, `kHighlights[]`, `kHighlightsCount`). A failed/missing `git` (shallow clone, no tags, source tarball) falls back to `"development build"`/`"No release history available."` rather than breaking the configure. `MainComponent::showWhatsNewDialog()` renders it as a synchronous `juce::AlertWindow` — no network client, no offline-handling complexity. **Sensitive-info boundary**: commit **subject lines only** (never the body, never author name/email) — see `docs/distribution.md`'s "What's New" section for the full rationale. The welcome screen's version label and its `whatsNewButton` (wired to the same dialog) both read `kReleaseTag`/the dialog as their one source of truth for "what version is this."
