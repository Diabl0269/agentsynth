# Architecture Overview

Agent Synth is built on a modular graph architecture using JUCE's `AudioProcessorGraph` (implicitly managed by `AudioEngine`).

---

## Project Structure

The build produces four CMake targets:

| Target | Kind | Contents |
|---|---|---|
| `Core` | Static library | All audio modules, `AudioEngine`, `PresetManager`, `AppUndoManager`, theme system, `LayoutUtil`. Headless-testable — no audio device or GUI window required. |
| `AppUI` | Static library | `MainComponent` plus everything under `Source/UI` not already in `Core` (`GraphEditor`, `ModuleComponent`, `AIChatComponent`, `SettingsWindow`, `ModMatrixComponent`, etc.). Links `Core` PUBLIC. Shared by `AgentSynth` and `AgentSynthPlugin` so the app and the plugin build **one** copy of the editor UI from **one** source list — a plugin whose UI drifts from the app's is the exact failure this library exists to prevent. Deliberately not folded into `Core`: `Core` is the headless-testable layer, and the `Tests` target still compiles these sources itself with `JUCE_MODAL_LOOPS_PERMITTED=1`, which `AppUI` is not built with. |
| `AgentSynth` | JUCE GUI app | Links `AppUI` + `Core`. Adds only `Source/Main.cpp` — the standalone `JUCEApplication` entry point (and the generated `JuceHeader.h`), which has no meaning inside a plugin and so stays out of `AppUI`. |
| `AgentSynthPlugin` | Audio plugin — VST3 on every platform, + AU on macOS | Links `AppUI` + `Core`. Wraps the same `AudioEngine`/`MainComponent` in a `juce::AudioProcessor` (`Source/Plugin/`). Built when the `ENABLE_PLUGIN` CMake option is on (default `ON`). Standalone format is deliberately excluded from its `FORMATS` list — JUCE would emit a second "Agent Synth.app" that collides with the `AgentSynth` target's own release artifact. See [Plugin Layer](#plugin-layer) below. |

`Assets` is a separate binary-data target that embeds font files and SVG icons; it is linked into `Core` (and therefore `AppUI`, `AgentSynth`, and `AgentSynthPlugin`) so every target resolves `BinaryData` symbols.

## Core Components

### 1. AudioEngine

`Source/AudioEngine.h/.cpp`

Manages audio device I/O (via `juce::AudioIODeviceCallback`), the `juce::AudioProcessorGraph`, and modulation-matrix routing. Key responsibilities:

- **Audio callback** — `audioDeviceIOCallbackWithContext` drives `mainProcessorGraph.processBlock`, then applies master-mute zero-fill **after** `processBlock` so sequencers, LFOs, and envelopes keep advancing even while muted. `masterMuted_` is `std::atomic<bool>`.
- **Audio input** — the callback renders through **one** buffer of `max(numIn, numOut)` channels, and the device's input is **copied into it before the graph runs**. That copy is not an optimisation to remove: a `juce::AudioProcessor` renders in place, so channels `[0, numIn)` (what a `juce::AudioGraphIOProcessor(audioInputNode)` reads, if a patch still holds one) and channels `[0, numOut)` (what its *Audio Output* node writes) are **the same memory** — the input block is `const` and the graph is about to overwrite those channels with its result. The *Audio Input* **module** does not read this buffer at all; it reads the separate snapshot described below. Channels the device's outputs don't cover (a device with more inputs than outputs, or an output pointer the device hands us as null) come from `deviceScratch_`; it and the channel-pointer array are sized in `audioDeviceAboutToStart` (`prepareDeviceScratch`, on `max(in, out)` — `prepareSliceScratch` is sized the same way for the same reason), so the callback never allocates. If a block ever arrives wider or longer than prepare sized for, the callback serves the output channels alone rather than allocating. This is `juce::AudioProcessorPlayer`'s pattern; `AudioEngine::getDeviceScratchInfo()` exposes the sizing so `Tests/AudioInputTests.cpp` can assert it. Live input makes a mic → speaker loop *possible*, but only once the user patches the Audio Input node onward — this copy itself stays unconditional (it is the capture path, not the safety mechanism); see [Input monitoring & feedback guard](#input-monitoring--feedback-guard) for what actually gates it.
- **The per-block device-input context** — how the *Audio Input* module actually gets those samples, and the one part of the input path that is **not** the render buffer:
  - Each callback the engine copies the input a **second** time, into `deviceInputSnapshot_` — storage the graph never renders over — and `renderPass` parks pointers into it on the playhead (`TransportService::setDeviceInputForBlock`), clearing them again the moment `processBlock` returns. `AudioInputModule` downcasts `getPlayHead()` and copies from there. This is the same "the playhead is the only handle every module already has" carrier the timeline snapshot uses; device input reaching modules through it is unrelated to the timeline feature proper — it is not a timeline feature.
  - The second copy is the whole point. The copy into the render buffer exists so the graph's `max(numIn, numOut)` channels start out holding the input; the graph then **overwrites those very channels** with its result, so a node running mid-graph would read partly-rendered output where the input used to be. Hosted mode has the identical problem in a sharper form — the host hands us one buffer that is both its input and its output — so `processHostBlock` takes the same snapshot before `renderNextBlock`, and the module behaves the same in both modes (`AudioInputModuleTest.HostedInputFlows`).
  - Sized in **both** prepare paths (`prepareDeviceInputSnapshot`, `TransportService::kMaxDeviceInputChannels` = 8 channels × twice the block size), never from the audio thread. A block longer than that publishes **no** input rather than allocating or truncating — the module renders silence for it, the same degraded-but-safe posture as `deviceScratch_`. With automation slicing on, `renderPass` takes an `inputSampleOffset` so each 64-sample slice publishes *its* slice of the capture instead of replaying the block's first one.
  - `AudioEngine::getDeviceInputChannelCount()` is the message-thread half: the input channel count the graph is currently prepared for (0 before either prepare path has run). `GraphEditor::refreshIoModulesAfterDeviceChange()` pushes it into every Audio Input module on a device change so the card's jacks resize immediately instead of one rendered block later. See [`modules.md § Audio Input`](modules.md#audio-input--audio-output-graph-io).
  - **No-playhead caveat.** A module reads the transport only through `getPlayHead()`; when nothing has installed one — a bare unit test constructing the module directly, or a foreign host that never calls `setPlayHead` — the module finds no transport and renders silence rather than crashing.
- **Device state persistence** — inputs are **opt-in**, and the opt-in is the persisted device setup:
  - *Out:* in Standalone mode the engine registers as a `juce::ChangeListener` on its `AudioDeviceManager` and, on every change, hands `deviceManager.createStateXml()` to the owner-installed `onDeviceStateChanged` callback. The engine stays `ApplicationProperties`-free — Core never touches settings — so `MainComponent` (owning path only; the plugin's host owns the device) stores the string under `"audioDeviceState"` and calls `saveIfNeeded`. The payload is legitimately **null** until the user has explicitly chosen a setup: JUCE does not treat its own startup defaults as explicit, so an untouched install persists nothing.
  - *In:* `MainComponent::initialiseCommon` parses that string and calls `audioEngine.setSavedDeviceState(...)` **before** `initialise()`. With a state, `initialise()` restores it via `deviceManager.initialise(0, 2, savedState, selectDefaultDeviceOnFailure=true)`; with none it takes exactly the old `initialiseWithDefaultDevices(0, 2)` path, which is why there is no migration step — *absent state is the legacy behaviour*. The **0** input channels *needed* is load-bearing and deliberately not 2: JUCE falls back to that count whenever the saved setup doesn't pin its input channels (saved after changing only the output device) and whenever the saved device can't be opened at all, so asking for 2 would silently switch a microphone on for a user who never asked. It costs nothing when the state *is* explicit — `setAudioDeviceSetup` re-derives the needed count from the saved channel mask, which the Audio tab writes the moment the user ticks an input channel. macOS also needs `MICROPHONE_PERMISSION_ENABLED` on the app target (top-level `CMakeLists.txt`), since the OS kills any process that opens an input stream without `NSMicrophoneUsageDescription`.
  - *Test seam:* `AudioEngine::initialiseDevices(const juce::XmlElement*)` is a protected virtual holding **everything** in `initialise()` that touches hardware (device open, callback attach, change-listener subscribe, MIDI inputs). A test subclass overrides it to assert which branch was chosen with none of the side effects.
- **Device latency** — `getInputLatencySamples()` and `getOutputLatencySamples()` are symmetric siblings: both read a value **cached at `audioDeviceAboutToStart`** (cleared at `audioDeviceStopped`) rather than asking the device manager. That's the latency of the stream actually *running* — an engine whose callback is detached is not being clocked by any device, and JUCE re-runs `audioDeviceAboutToStart` on every device change or restart so the cache can't go stale while it is attached — and caching is what makes both assertable headlessly against a fake device. 0 in Hosted mode and 0 when no device has started. `getRecordingLatencySamples()` sums them with the graph's: see [Latency alignment](#latency-alignment).
- **Module lifecycle** — dynamic addition/removal of modules and connections in the graph.
- **Preset load/save** — delegates to `PresetManager`.
- **Modulation-matrix view** — `getModulationRoutings()` returns a `std::vector<ModulationRouting>` derived on demand from the live graph. Never serialized. `RoutingKind` values: `AttenuverterChain`, `DirectCV`, `PolyBus`. `getActiveModRoutings()` and `getModulationDisplayInfo()` are thin adapters over it.
- **Voice count / mute API** — `getDisplayVoiceCount()`, `setMasterMute(bool)`, `isMasterMuted()`.
- **Host modes** — `HostMode::Standalone` (default) vs `HostMode::Hosted` (used by the audio-plugin wrapper). Both funnel through one private `renderNextBlock` (which delegates to `renderPass`, once per callback or once per slice) so master-mute semantics can't drift between them. See [Plugin Layer](#plugin-layer) below.
- **Device-callback attachment** — `isReceivingDeviceCallbacks()` / `suspendDeviceCallback()` / `resumeDeviceCallback()`. "Is something else clocking this graph right now?" is the precondition every offline renderer needs, and the host mode alone can't answer it — a Standalone engine whose callback has been detached is just as quiescent as a Hosted one. Suspending mirrors exactly how `initialise()` attached the callback; JUCE calls `audioDeviceStopped()` on the way out (so the caller owns re-preparing the graph) and `audioDeviceAboutToStart()` on the way back in (so re-attaching re-prepares at the *device's* rate on its own). Used by [Bounce/export](#bounceexport).
- **Transport** — the engine owns a `synth::TransportService` (`getTransport()`) and installs it as the graph's playhead once, in the constructor (`mainProcessorGraph.setPlayHead(&transport)`); JUCE re-applies it to every node on every render pass, so nodes re-created by a preset load or an undo restore need no re-injection. `transport.tick(numSamples)` runs as the first thing in `AudioEngine::renderPass` — before the graph — so it happens exactly once per **render pass** in both host modes (one pass per callback normally; one per 64-sample slice when control-rate slicing is enabled, which advances the transport in smaller steps but by the same total), and `transport.prepare(...)` runs before the graph's `prepareToPlay` in both `audioDeviceAboutToStart` and `prepareForHost`. `getGraphLatencySamples()` **reports** the graph's aggregate latency (JUCE's graph already compensates parallel paths internally); the engine adds no compensation of its own. `getOutputLatencySamples()` reports the open output device's buffering the same way — 0 in Hosted mode (the host owns the device) and 0 when no device has started; the playhead subtracts it so the drawn line matches what is *heard* (see [`docs/timeline_panel_core.md` §4](timeline_panel_core.md)), and `getRecordingLatencySamples()` folds it into the round trip a recorded take is shifted back by.
- **Timeline snapshots** — the engine also owns a `synth::TimelineSnapshotExchange` (`getTimelineSnapshots()`) and opens exactly one block on it per render pass, immediately after the tick, so the snapshot reclamation epoch advances in lockstep with the clock. `shutdown()` calls `reclaimAllUnsafe()` last, once nothing can read it. See [TimelineSnapshot](#4-timelinesnapshot-the-audio-threads-view-of-the-timeline).
- **Automation** — alongside the snapshot exchange the engine owns an `EpochExchange<AutomationBindingTable>` (`getAutomationBindings()`) and an `AutomationApplier`. `publishTimeline(doc)` is the single message-thread entry point that feeds both; `renderPass` applies one pass' worth of automation between the MIDI capture point and `graph.processBlock`. `setAutomationSlicingEnabled(bool)` (default **off**) turns the whole per-block sequence into a per-64-sample-slice sequence. `setAutomationRecorder(AutomationRecorder*)` (null by default) hands the applier the recorder's audio-visible half — the per-lane record modes and the in-flight gesture claims it must yield to. The engine also owns a `synth::AutomationUiFeed` (`getAutomationUiFeed()`), passed into every `applyBlock` call so automation-driven writes can reach the UI without a notifying parameter write. See [Automation applier](#automationapplier-writing-automation-into-live-parameters), [Automation recorder](#automationrecorder-record-modes-and-gesture-capture) and [UI reflection](#ui-reflection-automated-parameter-changes-shown-in-the-ui-without-a-feedback-loop).
- **MIDI recording** — `synth::MidiRecorder` (`Source/Timeline/MidiRecorder.h/.cpp`) records external MIDI into a new timeline clip as one undo step. `AudioEngine::setMidiCaptureSink(MidiRecorder*)` stores a `std::atomic<MidiRecorder*>` (null by default); `AudioEngine::renderPass` calls `recorder->captureBlock(midiMessages, transport.getCurrentBlockInfo())` unconditionally, right after the snapshot is opened and just before the automation applier. This is the **single** capture point, and deliberately so: `handleIncomingMidiMessage` forwards every external MIDI message to two places — a direct `pushMidiMessage()` into any bound `ExternalMidiModule`, and `midiMessageCollector`, which is what `midiMessages` here actually is (collector-drained in standalone mode, delivered directly by the host in hosted mode). Recording from the `ExternalMidiModule` push-path copies too would double-record any note whose source also has an ExternalMidi node bound to it — those copies stay internal to that module's own `processBlock` and never reach this buffer, so capturing only here is what makes "recorded once, from the single collector-merged stream" true. `captureBlock` is lock-free and allocation-free: it pushes a POD `{beat, pitch, velocity, channel, isNoteOn}` per NoteOn/NoteOff into a fixed 4096-slot `juce::AbstractFifo` ring (dropping and setting an atomic overrun flag if full, never blocking); `stopAndCommit` (message thread) drains the ring, pairs NoteOn/NoteOff by `(pitch, channel)`, and commits a single new "Take" clip via `AppUndoManager::recordTimelineChange`. See [`docs/midi_input.md`](midi_input.md) for the two-paths detail this taps into.
- Requires `#include <bit>` for `std::popcount` (C++20).

### 2. TransportService (the one clock)

`Source/Transport/TransportService.h/.cpp`, `Source/Transport/TempoMap.h`, `Source/Transport/BlockTimeInfo.h`

The timeline's transport spine: play state, sample position, BPM, time signature, and loop bounds (in beats), headless-testable with no device dependency.

- **Beats are canonical.** All musical-time conversion goes through the two-method `TempoMap` seam (`beatFromSample`/`sampleFromBeat`), implemented by `ConstantTempoMap` for v1. A BPM change preserves the beat position and re-derives the sample position; so does a sample-rate change (`prepare`).
- **Command FIFO, never a lock.** The message thread posts POD commands (`play`/`stop`/`locateBeat`/`setLoop`/`setBpm`/`setTimeSignature`) through a lock-free SPSC `juce::AbstractFifo`, drained in posting order at the top of `tick()`. Posts are non-blocking and return `false` when the FIFO is full (dropped, caller may re-post). Commands take effect at sample 0 of the next block.
- **`tick(numSamples)` once per callback** computes an immutable POD `BlockTimeInfo` (block start/end ppq, loop-wrap sample offset, bpm, time sig, play/loop state) describing the block *before* the graph renders it, then advances the position, wrapping at the loop end (a wrap landing exactly on the block boundary reports `loopWrapSample == -1`; tiny loops wrap by modulo). Zero allocation on the audio path.
- **It is a `juce::AudioPlayHead`.** The engine installs it with `graph.setPlayHead(...)`; `juce::AudioProcessorGraph` re-applies the playhead to every node processor on every render pass, so every module — however created (fresh drop, preset load, undo restore) — reads the transport via the standard `getPlayHead()->getPosition()` API with no per-node injection bookkeeping. Sample-accurate consumers on the audio thread use `getCurrentBlockInfo()` instead. `AudioEngine` is the owner that wires this up: it calls `setPlayHead(&transport)` in its constructor, `transport.prepare(...)` ahead of the graph's `prepareToPlay`, and `transport.tick(...)` as the first statement of `renderPass` — the single site both Standalone and Hosted modes clock the graph from.
- **Cross-thread reads** (UI playhead, status bar) go through `getPositionSnapshot()`, a seqlock over individual atomics — consistent multi-field reads, no locks, no tearing. The snapshot reflects the start of the current block (what's audible now).
- **The playhead also carries this block's `TimelineSnapshot`.** `setCurrentTimelineSnapshot` / `getCurrentTimelineSnapshot` park a *borrowed* pointer on the transport; `AudioEngine::renderPass` sets it from `timelineSnapshots.beginAudioBlock()` immediately after `tick(...)`. The playhead is the only thing every module already has a handle to, so this is how a module reaches the timeline without per-node injection: downcast `getPlayHead()` to `synth::TransportService*` and read `getCurrentBlockInfo()` and the snapshot together, off one object. Two rules, both load-bearing: the pointer is **written and read on the audio thread only** (hence a plain pointer, no atomic), and it is **valid for the current block only** — caching it in a module member and reading it next block is a use-after-free, since the exchange frees a superseded snapshot two callbacks after retiring it. It is legitimately null (nothing published yet, a bare transport in a unit test), so every reader null-checks.
- **Permanent, unconditional integration.** The playhead install, the engine's per-block tick, and the sequencer sync dispatch are ordinary, always-compiled engine code — there is no build-time flag and no alternate configuration to keep in sync. `AudioEngine::setTransportEnabled` is a separate, purely runtime API (no persisted setting drives it; nothing calls it outside `AudioEngineTransportTests.cpp`) that freezes/resumes the transport without a rebuild.
- **Offline rendering** — `synth::OfflineTransportDriver` (`Source/Transport/OfflineTransportDriver.h/.cpp`) clocks an `AudioEngine`'s graph at a fixed sample rate / block size with **no audio device**: it drives the engine through `prepareForHost` / `processHostBlock` and offers `renderBlocks(n)` and `renderToBeat(beat)`, the latter rendering whole blocks until the just-rendered block's `endPpq` reaches the target, so it may overshoot by up to one block and returns an empty buffer rather than spinning if the target isn't ahead of a *playing* transport. `streamBlocks` / `streamToBeat` are the same two loops with **nothing accumulated** — the per-block `BlockCallback` is the only way to see the audio and the return value is a block count; that is what bounce/export renders through, since handing it a contiguous buffer of a ten-minute take (~230 MB at 48 kHz stereo) would be pure waste. `renderBlocks`/`renderToBeat` are implemented on top of the streaming pair, so there is exactly one loop per shape. Both streaming calls take an optional pre-block `BlockGate`: a predicate consulted *before* each block that ends the loop without rendering it — the seam a consumer both cancels through and blocks in (bounce/export waits there for `AudioClipStreamer`). The precondition is **"nothing else is clocking this graph"**, asserted as `!engine.isReceivingDeviceCallbacks()` — a `HostMode::Hosted` engine satisfies it by construction, a Standalone one only after `AudioEngine::suspendDeviceCallback()` (it used to be a blunter `jassert(engine.isHosted())`, which would have refused the one case bounce/export actually needs). This is the headless harness every engine-level timeline test uses. Allocation happens once per accumulating render call on the message thread; the per-block path allocates nothing.

#### Bounce/export

`Source/Transport/BounceExporter.h/.cpp` — `synth::BounceExporter::bounce(engine, outFile, BounceOptions, progress)` renders a beat range of the **current patch** to a WAV file, faster than realtime, through the same graph the app plays through. Message thread, blocking. There is no second offline-only signal path to keep in sync: the loop is `OfflineTransportDriver`, the clock is the app's own `TransportService` driven through its normal stop/locate/play commands, and the modules are the live nodes. The only difference from playback is that nobody is waiting for a device — there are no sleeps and no device on the path, it just renders. (Order of magnitude: `BounceExporterTest.EnergyWhereNotesAre` builds its patch, bounces 4 seconds of audio and reads the file back in well under 100 ms.)

- **Device suspension.** A Standalone engine with a live device is detached for the duration via `AudioEngine::suspendDeviceCallback()` (the exact inverse of `initialise()`'s `addAudioCallback`), so nothing else clocks the graph while the render owns it. JUCE calls `audioDeviceStopped()` on the way out and `audioDeviceAboutToStart()` on the way back in, so **re-attaching re-prepares the graph and the transport at the device's rate by itself** — `resumeDeviceCallback()` must not do that by hand. A Hosted engine is used as-is (its host owns the clock; there is no portable way for us to quiesce it). `AudioEngine::isReceivingDeviceCallbacks()` is the tracked bool behind all of this and the property the driver asserts on.
- **Choreography.** Save the position snapshot (position, play state, loop state) and the graph's prepare format → suspend the device → construct the driver (which re-prepares the graph at the render format) → `stop()`, `setLoop(..., enabled=false)` (a bounce renders the range **linearly**; a live loop would make "render until `endBeat`" unreachable), `locateBeat(startBeat)`, `play()` → render one block on its own, then `streamToBeat(endBeat)`. The lone first block is load-bearing: `streamToBeat` decides whether the target is ahead of the playhead by reading the *cross-thread position snapshot*, which the queued locate has not reached yet, so bouncing bars 1–2 while the playhead sits at bar 40 would otherwise bail out instantly. It is not a throwaway — a command takes effect at sample 0 of the block that drains it, so that block *is* the first block of the range.
- **Length.** Whole blocks only: `ceil(rangeSamples / blockSize) × blockSize`, up to one block past `endBeat`, plus `ceil(tailSeconds × sampleRate / blockSize)` tail blocks.
- **Tail semantics.** The tail is rendered with the transport **stopped**, so time-locked sources (clips, sequencers) fall silent while reverbs and delays ring out. That is the difference between a tail and simply bouncing a longer range.
- **Restore.** Loop state restored, playhead located back to where it was, and left **stopped** — bouncing from a playing transport leaves you stopped at the prior position, which is what every DAW does. Transport commands only take effect on a tick and nothing is going to tick the engine again, so the restore renders one throwaway block to make them real; that is what lets a caller read the restored position straight after `bounce()` returns. The prepare format goes back too (the device's on re-attach, otherwise the previous hosted format).
- **Streamed audio clips.** A bounce outruns `AudioClipStreamer`'s prefetch thread by orders of magnitude, and constructing the driver re-prepares the engine, which runs `invalidateAllStreams()` — so with no handshake every Track Audio clip would start with a silent head and drop out at the disk's whim. Each block therefore waits, **before it is rendered**, on `AudioClipStreamer::waitUntilPrimed(beat, bpm, sampleRate, framesAhead, timeoutMs)`: it steers every open stream to the frame that clip will be asked for at `beat` (through `synth::sourceFrameForClipBeat`, the one beat→file-frame mapping playback also uses) and blocks until each ring covers it. The beat comes from the last block's `BlockTimeInfo::endPpq`, not from the position snapshot, which lags a block behind. Cheap once primed; a wait that times out counts one `BounceResult::streamDropouts` and renders anyway, so a starved disk is *reported*, never silently mixed in. With the prefetch thread paused for a test the priming call fills synchronously on the calling thread, which is what keeps offline renders deterministic and sleep-free.
- **Cancellation.** The progress callback returns `false` to cancel. Two things end the render: the callback posts `transport.stop()` (a stopped transport reaches no beat, so `streamToBeat` gives up one block later), and the driver's pre-block `BlockGate` refuses the next block outright. The gate is what stops the **tail**, which renders with the transport already stopped and would otherwise run to its full length with nobody writing the blocks.
- **Atomicity.** The render goes to a sibling `juce::TemporaryFile` and is moved into place only on success, so a failed or cancelled bounce never leaves a truncated file and never touches a file that was already there. An unwritable or nonexistent destination fails when the stream is opened — before a sample is rendered.
- **Determinism.** Two bounces of the same project are byte-identical. Nothing on the render path reads the wall clock (that is what driving the graph from the transport rather than a device bought), voice allocation is deterministic, and block boundaries are a function of the options alone. The qualifier is *the same project*, not *the same session*: bouncing twice in a row from one live engine starts the second render from whatever DSP state the first left behind (free-running oscillator phase, an un-decayed delay line), because `prepareToPlay` resets rates and ramps but not phase.
- **Non-render-safe modules.** Every offline block is handed an **empty** `juce::MidiBuffer`, and the engine's `midiMessageCollector` is never drained offline (no device callback is running to drain it). Live-input modules therefore contribute silence to a bounce **by definition, not by accident** — External MIDI, and any future hardware-input module, have nothing to emit. The one hole worth naming: `ExternalMidiModule` keeps its own collector fed straight from `handleIncomingMidiMessage`, so a note physically played while a bounce is running can still land in the file.
- **The metronome** is summed *after* the graph (see the subsection below), which keeps it out of any in-graph tap by construction — but a bounce captures exactly that post-graph buffer, so `bounce()` forces it off explicitly (see `MetronomeForceOffGuard` below) rather than relying on the summing point alone.
- **Formats.** 16 / 24-bit integer PCM, or 32 = IEEE-float WAV (JUCE's `WavAudioFormatWriter` sets `usesFloatingPointData` for 32-bit), so a float bounce is a bit-exact copy of what the graph produced with no clipping and no dither decision to make. `sampleRate` is free to differ from the device's.

#### Metronome + count-in

`Source/Transport/Metronome.h/.cpp` (`synth::Metronome`) — a click generator that is a pure audio-thread synth, not a graph module: `AudioEngine` owns one (`metronome_`, exposed via `getMetronome()`) and calls `renderClicks(buffer, transport.getCurrentBlockInfo())` directly from `renderPass`, **after** `mainProcessorGraph.processBlock` and **before** `renderNextBlock`'s master-mute zero-fill.

- **Why post-graph, and why the ordering matters.** Nothing inside the graph — no module, no future in-graph recording tap — can ever see the click, because it is summed into the buffer only after the graph has already finished with it. Master mute clears the *whole* buffer after this call runs, so it silences the click along with everything else the engine produces — deliberate, mirroring how master mute already treats the graph's own output. A bounce (`BounceExporter::bounce`) is the one place this "post-graph" property is *not* automatically enough: a bounce captures exactly the post-graph buffer, which is the click's insertion point, so it cannot rely on the summing order to keep the click out — see below.
- **Beat-crossing scan.** Mirrors `TimelineMidiSourceModule`'s loop-wrap-aware scan exactly: a block that doesn't cross the loop end is one beat range `[startPpq, endPpq)`; one that does is two — `[startPpq, loopEndPpq)` at offsets `[0, loopWrapSample)`, then `[loopStartPpq, ...)` for the remainder. Every integer beat inside a range fires a click (a range beginning exactly on an integer, e.g. transport start, still fires — no beat is ever skipped or double-fired across two blocks that tile exactly). A beat is a **downbeat** (bar start) when `fmod(beat, beatsPerBar) == 0` (`beatsPerBar = timeSigNumerator * 4 / timeSigDenominator`, the same "a beat is always a quarter note" convention `TimelineTransportBar`/`TransportService::getPosition()` use) — 1600 Hz / amplitude 0.35, vs. 1050 Hz / amplitude 0.25 for every other beat, each an exponentially-decaying sine burst to −60 dB over ~4 ms.
- **Clicks span block boundaries.** A fixed pool of 4 voices (`{samplesRemaining, phase, phaseInc, amp, decayMul}`) persists across calls rather than resetting per block, so a click starting 5 samples before a block ends continues into the next call with no phase or amplitude discontinuity (`MetronomeTests.cpp`'s `ClickSpansBlockBoundary` proves this by comparing a two-call split render against an uninterrupted single-call render of the identical click). Overflow (a 5th click while all 4 still ring) steals the voice with the **fewest samples remaining** — every voice starts with an identical countdown, so that is the one that has rung the longest. Zero allocation, zero locks, zero logging.
- **Enabled vs. forced-on.** `setEnabled`/`isEnabled` is the user-facing toggle (message thread writes, audio thread reads, both relaxed atomics). `setForcedOn`/`isForcedOn` is OR'd with it — the count-in pre-roll (below) forces the click audible through the pre-roll bars regardless of the user's own toggle. With **neither** set, `renderClicks` is a complete no-op: it does not touch the buffer and does not advance any voice state, so a disabled metronome costs two atomic loads and nothing else (`DisabledMetronomeIsSilentAndFree`).
- **Bounce force-off.** `BounceExporter.cpp`'s `MetronomeForceOffGuard` (RAII) saves `isEnabled()`/`isForcedOn()`, forces both off, and restores them in its destructor — unwound on every exit path (success, cancellation, every early-return failure), constructed right after `bounce()` obtains its `transport`/`graph` references so it is alive for the rest of the function. This is the explicit mechanism the post-graph-summing paragraph above says is needed: summing order alone keeps the click out of anything *inside* the graph, but the bounce itself reads the post-graph buffer, so nothing structural saves it there.
- **Count-in choreography.** A persisted setting, `"timelineCountInBars"` (0/1/2, default 0, restored/persisted by `TimelineTransportBar` alongside `"timelineMetronomeEnabled"`), read by `MainComponent`'s `onRecordToggled` handler (the record flow) at the moment Record is clicked:
  - **Stopped, count-in > 0:** `punchInBeat = current ppq`; `preRollStart = max(0, punchInBeat − countInBars × beatsPerBar)`; `transport.locateBeat(preRollStart)`; `metronome.setForcedOn(true)`; `transport.play()`; `midiRecorder.startRecording(armedTrack, punchInBeat)` — the SAME `punchInBeat` is both the recorder's bookkeeping value and (see below) its audio-thread filter threshold.
  - **Already playing, or count-in off:** no pre-roll, no forced-on — `punchInBeat` is simply the current position, matching the transport's original "record implies roll" behaviour exactly (`RecordWhilePlayingSkipsCountIn`).
  - **Clearing forced-on.** `MainComponent`'s existing 10 Hz poll clears `setForcedOn(false)` once `position.ppq >= midiRecorder.getPunchInBeat()` (gated on `midiRecorder.isRecording()`, idempotent once already false). `commitMidiRecording()` also clears it unconditionally on every stop (explicit or auto-committed) — a take that was never in a pre-roll simply clears an already-false flag.
- **The punch-in filter.** `MidiRecorder::captureBlock` drops any event whose computed beat is before `punchInBeat` (a relaxed `std::atomic<double>`, written by `startRecording` before `recording` flips true and never mutated again until the next `startRecording`) — this is what makes a count-in's pre-roll audible (the performer hears the click and can play along) but never committed to the take. `startRecording`'s `punchInBeat` parameter therefore does double duty: informational bookkeeping for every existing caller that passes "now" (the filter is then a no-op, which is why no pre-existing test needed updating when the filter was added), and the actual audio-thread cutoff for the count-in's pre-roll callers.
- **UI.** `TimelineTransportBar` gains a metronome toggle (a drawn "quarter note" `juce::Path`/`juce::Rectangle` glyph, no assets — see `docs/layout.md` §16) and a 3-item count-in `juce::ComboBox` ("Off"/"1 bar"/"2 bars"), both persisting themselves via the bar's own `setApplicationProperties` (the same restore/persist-on-change idiom `TimelinePanelComponent` uses for its snap combo) rather than routing through the panel, which has no other reason to know either setting exists.

#### Input monitoring & feedback guard

Live device input reaching the graph makes a mic → speaker loop *possible* the moment a user patches *Audio Input* onward — a resonant filter or a delay with feedback turned up is a genuinely dangerous loop, not a hypothetical one. Two mechanisms, both **ungated** (input-path safety, not a timeline feature):

- **The monitoring gate.** `AudioEngine::setInputMonitoringEnabled(bool)` / `isInputMonitoringEnabled()` is an `std::atomic<bool>` (default **false**), published once per render pass to the transport carrier — `TransportService::setInputMonitoringEnabledForBlock`/`isInputMonitoringEnabledForBlock()`, the same "the playhead is the one handle every module already has" pattern the device-input snapshot and the timeline snapshot use. `AudioInputModule::processBlock` reads the carrier (never the engine atomic directly) and **clears its own output** when it reads false — the engine's device-input *capture* (`captureDeviceInput`) is completely unaffected, so a track recording straight off the device input still works even with monitoring off; only what this module hands the rest of the graph is gated. Recording *taps the graph*, so "monitoring enabled" **is** the record path for input chains — gating anything upstream of the module would break recording, not just monitoring.
- **The feedback guard.** `AudioEngine::runFeedbackGuard`, called from `renderPass` **post-graph, pre-master-mute** — right beside the metronome click, after it sums in, so the guard sees exactly what would reach the speakers. Only evaluated while monitoring is enabled (a loud synth alone, or a loud device input the user never wired anywhere, can never trip it): each render pass it takes the peak sample magnitude across the graph's **output** channels only (`mainProcessorGraph.getTotalNumOutputChannels()` — a device with more inputs than outputs parks the extra input channels past the output count in the same render buffer, and a hot mic sitting there unconnected to anything is not feedback) and accumulates a **consecutive-samples** run (not a block count, so the timing is block-size-agnostic — control-rate slicing evaluates the same total elapsed samples in smaller steps) for every pass whose peak is at or above `kFeedbackPeakThreshold` (**0.97**), resetting the run to 0 the moment a pass falls under it. Once the run's elapsed time reaches `kFeedbackSustainSeconds` (**0.25 s**), the guard: disables monitoring (the *same* flag the gate above reads), latches `feedbackGuardTripped_` for the UI, and **zeroes that render pass's entire output immediately** — it does not wait for the disabled flag to take effect on the next pass, which could be a whole device block away. It cannot pin an exact in-block trip sample (the peak is measured over the whole pass), so it clears the whole pass rather than guessing an offset. The run also resets whenever monitoring is off, so a loud stretch that happened before monitoring was enabled can never count toward a trip the moment it's switched on.
- **UI surfacing + the re-arm rule.** `MainComponent`'s existing 10 Hz poll derives the gate's input: `isInputMonitoringEnabled` should be true exactly when some `TrackKind::Audio` track has `armed == true` (mirroring the audio-recording armed-track lookup, but existence rather than first-wins — the gate does not care which armed track would host the take). `consumeFeedbackGuardTripped()` (an atomic exchange, consumed **exactly once** per trip) shows `statusBar.showMessage("Input muted — sustained clipping (feedback protection)")` and latches `feedbackGuardLatched_` — a `MainComponent`-side bool, **not** part of the engine — which keeps monitoring off on every subsequent poll for as long as the **same arm state** persists, even though the Audio track is still armed. The latch clears only on the arm set's **false → true edge**: disarming every Audio track and then arming one again is the explicit reset gesture; simply *staying* armed after a trip must not silently re-enable monitoring.
- **Thresholds are public `constexpr` on `AudioEngine`** (`kFeedbackPeakThreshold`, `kFeedbackSustainSeconds`) rather than buried in the `.cpp`, so a test asserting the guard's timing does not have to duplicate the numbers by hand. 0.9 and 0.95-amplitude signals both sit under the 0.97 peak margin and must never trip however long or bursty they run (`FeedbackGuardTest.FalsePositiveCorpus`); a 3-block loud transient is far short of the 0.25 s sustain margin (`BriefTransientDoesNotTrip`).

### 3. TimelineDoc (the timeline document model)

`Source/Timeline/TimelineDoc.h/.cpp`

The message-thread model behind the timeline: tracks → clips → notes, plus automation lanes and markers. Mutable, serialisable, headless — no GUI, editor or audio dependency. Everything downstream (the audio-thread snapshot, undo, `.agsproj` save) hangs off it.

- **Beats are canonical, and tempo isn't here.** Every time in the document is a beat position; BPM and time signature stay on `TransportService`. A tempo map moves into the doc only when real (non-constant) tempo maps arrive.
- **One mutation choke point.** Every public mutator validates its arguments first, then funnels the actual edit through the private `applyMutation()`, which bumps `getRevision()` and fires `Listener::timelineChanged` exactly once. Because validation happens *before* that seam, a call that changes nothing — a rejected note, `addLane` finding an existing lane, a setter given the value already stored — neither bumps the revision nor notifies. Snapshot republication, undo capture and save-dirty marking all attach here rather than diffing the model.
- **Ids are handles, not indices.** `TrackId`/`ClipId`/`LaneId`/`NoteId`/`MarkerId` are distinct tagged types (`value == 0` is the invalid sentinel), assigned monotonically, never reused within a doc's lifetime, and stable across a save/load — the next-id counters are serialised too, and on load they're floored at one past the highest id in the file so a hand-edited counter can't reissue a live id.
- **Sorted invariants are the model's contract**, not a convenience: clips within a track by `(startBeat, id)`, notes within a clip by `(startBeat, pitch, id)`, breakpoints by beat. That's what lets the audio-thread snapshot build by flattening instead of sorting. Note positions are clip-relative, so moving a clip never rewrites its notes. Overlapping clips are legal in the model; whether the UI draws them is a policy decision above.
- **The note-editing and clip-operations API** follows the same validate-then-`applyMutation` contract: `removeNote`/`moveNote`/`resizeNote`/`setNoteVelocity` reject bad input and no-op silently (no revision bump) when the requested value is already what's there; `quantiseNotes` snaps every note in a clip toward a beat grid, blended by strength, as a single mutation (a call that moves nothing is a no-op). `splitClip` keeps the original id on the left part and mints a new id for the right; a note straddling the split point is itself split into a truncated left note (same id) and a new right note re-based to beat 0 — the only place a note's id changes ownership mid-edit. `joinClips` rejects clips on different tracks and REJECTS overlapping clips (kept deliberately simple: unambiguous note re-basing beats supporting the merge case), extending `a` to cover `b`'s span and re-basing/merging `b`'s notes before removing it. `duplicateClip` deep-copies a clip's notes with fresh ids, placed immediately after the source. All three carry `Clip::muted` along with everything else: **both halves** of a split inherit the source clip's mute (a split is a cut, not an edit of what the user muted — cutting a muted clip in two must not make half of it audible), a duplicate copies it, and a join keeps the **surviving clip `a`'s** flag, the same "the clip that survives owns the state that survives with it" rule its asset/gain/source-offset already follow. Each merged **note** independently keeps its own `MidiNote::muted` — mute is a note property, not a clip one, so `joinClips`' merge never touches it either way.
- **Per-clip/per-note mute, rename and cross-track move (the edit-tool data layer).** `Clip::muted` and `MidiNote::muted` are plain `bool`s, both **additive** (absent in a file loads as `false`, `kFormatVersion` stays 1) and both written only through a mutator — `setClipMuted(ClipId, bool)` / `setNoteMuted(NoteId, bool)` — that no-ops (no revision bump, no notification) when the flag already reads that way, the same "setting what's already there is a no-op" contract every setter here has. `setClipName(ClipId, const juce::String&)` **trims** the name first and **rejects** a trimmed-empty result outright (no mutation) rather than storing a blank title, matching `setTrackName`'s policy — a cleared rename field keeps the old name instead of erasing it. `moveClipToTrack(ClipId, TrackId destTrack, double newStartBeat)` is `moveClip`'s cross-track sibling: same validation (`newStartBeat` finite `>= 0`, no clamping, no overlap policy, the destination track's `kMaxClipsPerTrack` cap applies), plus a **payload-based kind check** — a clip with a non-empty `assetRef` may land only on a `TrackKind::Audio` track, an empty-`assetRef` (MIDI) clip only on `TrackKind::Midi`, and an `Automation` track accepts neither. This is deliberately stricter than the rest of the model (which is permissive on purpose — see the `Clip`/`TrackKind` note above): a drag is the one moment the user states an intent about which lane a clip belongs to, and silently parking an audio clip on a track that will never play it is worse than refusing the drop. `destTrack` equal to the clip's current track is not a special case to the caller — it behaves exactly like `moveClip` (no-op included) and skips the kind check entirely, so an in-place drag never fails on data the model already tolerates. Every field this section describes travels through `moveClipToTrack`, `setClipMuted` and `setClipName` untouched — id, notes, every audio field.
- **Audio clips are the same `Clip` struct.** One clip type covers both kinds: a MIDI clip is one whose `assetRef` is empty and whose `notes` carry the music; an audio clip names a rendered asset instead. The audio half is `assetRef`, `gainDb`, `fadeInBeats`/`fadeOutBeats` and `sourceStartSeconds` (seconds, not beats — it indexes a recorded file, whose samples do not move when the tempo map does), written through `setClipAsset` / `setClipGainDb` / `setClipFades`. All five fields are **additive**: absent in a file means the struct default, and `kFormatVersion` stays **1**. `TrackKind::Audio` is fully usable — nothing in the model was ever MIDI-only.
  - **`assetRef` is bundle-root-relative, and that is a security rule, not a formatting one.** `TimelineDoc::isValidAssetRef` rejects a leading `/` or `\`, a drive letter, and any `..` segment; both `setClipAsset` and `fromVar` gate on it, so a hand-edited `project.json` is not a way around the check (see §5's asset policy for the threat).
  - **`splitClip` carries the asset across but does NOT re-seat `sourceStartSeconds`** — converting the split beat to seconds needs a tempo map, which this document deliberately does not have. Both halves keep the same asset, gain and source offset; each keeps the fade at the edge it still owns. Advancing the right half's source offset is the audio clip streamer's job, with the tempo map in hand. `duplicateClip` is an exact copy (no conversion needed); `joinClips` keeps `a`'s asset and inherits `b`'s fade-out, because two clips naming different assets cannot become one clip naming both.
- **A lane's identity is `(nodeUuid, paramId)`, doc-wide.** It binds to the graph node's `"uuid"` property — never its integer `NodeID`, which merge-mode graph apply is free to renumber. `addLane` for a pair that already exists anywhere in the document returns the existing lane's id and mutates nothing. Point values are stored **denormalised**, alongside a `RangeSnapshot` of the parameter's range captured at lane creation: if the range changes in a later build the mismatch is detectable instead of silently reinterpreting every point. Values are clamped into that snapshot on insert.
- **Markers are document data, not a track.** A `synth::Marker` is `{MarkerId id, double beat, juce::String text, juce::uint32 colourArgb}` in a `std::vector<Marker>` on the doc itself, sorted by `(beat, id)` exactly like clips. Deliberately NOT a `TrackKind` or a track row: a marker has no clips, no binding and no audible effect, so a "marker track" would have to be excluded from every place that iterates tracks to make sound. `beat` is **absolute** (unlike a note's clip-relative start) and `colourArgb` is inert display data.
  - **Mutation API**, all through the same validate-then-`applyMutation` choke point every other mutator uses: `addMarker(beat, text, colourArgb)` (returns an invalid `MarkerId` on a non-finite/negative beat, an over-cap label, or a doc at `kMaxMarkers`), `removeMarker(id)`, `setMarkerText(id, text)`, `setMarkerColour(id, argb)`, `moveMarker(id, newBeat)` (re-seats at the new sorted position, the same way `moveClip` does). Reads are `getMarker(id)` / `getMarkers()`. Every setter no-ops — no revision bump, no notification — when handed the value already stored, and `moveMarker` to the current beat reports success while bumping nothing.
  - An **EMPTY label is legal** and stored verbatim: unlike `setClipName` there is no trim-and-reject, because a marker is identified by its position and its id, not by its name, so a blank one is still a usable cue point. What IS refused is a label over `kMaxMarkerTextLength` (128) — **rejected, never truncated**, by the mutation API, by `fromVar` and by `validateTimeline` alike.
  - `clear()` drops markers as well as tracks, and its "nothing to do" guard checks BOTH containers so a markers-only document still gets its one notification. `isEmpty()` deliberately still reports on **tracks only** — it is what `ArrangementContext` asks to decide whether there is an arrangement to describe, and a document holding nothing but cue points has no arrangement.
- **Hard caps, enforced by rejection** (`kMaxTracks` 256, `kMaxClipsPerTrack` 4096, `kMaxNotesPerClip` 16384, `kMaxLanesPerTrack` 512, `kMaxBreakpointsPerLane` 16384, `kMaxMarkers` 1024, `kMaxMarkerTextLength` 128) — the model is bounded before `validateTimeline` ever sees untrusted input. Exceeding a cap is refused, never clamped or truncated.
- **`toVar()`/`fromVar()` is the dialect the project bundle embeds under the reserved top-level `"timeline"` key** (the one `AIStateMapper::validatePatch` refuses from provider output). `fromVar` is all-or-nothing: any malformed field — wrong type, out-of-range value, duplicate id, reserved track kind, a cap exceeded, a `"version"` that isn't 1 — returns `false` and leaves the doc byte-identical, same revision, no notification. On success it replaces the whole doc and fires once. A missing field takes its default; a *present* one must be well-typed — except a note's `"id"`, which is required (the dialect never shipped without one), so both a missing and a duplicate note id fail the whole load. Ordering is repaired rather than trusted (the loader re-sorts), because no reader downstream should have to defend against a file with a broken sort invariant.
  - **`"markers"` is an ADDITIVE top-level array** (with its own `"nextMarkerId"` counter), always written — an empty array when there are none — so a reader gets one shape to parse rather than two. A file predating markers simply has neither key and loads with none; `kFormatVersion` stays **1**, since adding a field is additive by the patch-format forward-compatibility rule. A marker `"id"` is required and unique like a note's; `beat`/`text`/`colourArgb` are optional and take the struct default when absent. `synth::validateTimeline` allow-lists both keys **with its own strict per-marker checks** — a top-level key that gate does not know about is REFUSED, so the loader and the gate have to be extended together (see [`AI_Engine.md`](AI_Engine.md)).
- **Orphaned bindings.** A `Track`'s `bindingUuid` and an `AutomationLane`'s `nodeUuid` are the doc's only references to graph nodes, and both are keyed on the node's stable `"uuid"` property — never its integer `NodeID`, which merge-mode graph apply routinely renumbers (see §5 below). After *any* graph change — a deleted module, a rejected restore, an AI patch that dropped a node — such a binding can stop resolving. The rule: an unresolvable binding becomes **orphaned — retained, flagged, re-bindable — and is never auto-deleted**. Auto-deleting would let one AI patch apply silently destroy an hour of hand-authored automation; a merge that adds or renumbers nodes elsewhere in the graph must not orphan bindings that still resolve fine.
  - `Track::orphaned` / `AutomationLane::orphaned` are **runtime-only**: not written by `toVar`, and always `false` immediately after `fromVar` — there is no graph at load time to check a binding against, so the flag is *derived* state, not part of the document's persistent identity.
  - **Unbound vs. orphaned are distinct states.** An *empty* `bindingUuid`/`nodeUuid` is merely **unbound** — it was never pointed at anything, and playing/automating nowhere is legal. **Orphaned** means the binding *was* set and no longer resolves. Only a non-empty binding can be orphaned.
  - `TimelineDoc::reconcileBindings(uuidResolves)` recomputes every flag against a caller-supplied `uuid -> bool` callback, so the doc itself stays graph-agnostic and headless. It routes through the single `applyMutation` choke point **only if at least one flag actually changed** — one revision bump and one `Listener::timelineChanged` call however many bindings flipped in the pass; a reconcile that changes nothing is a true no-op (no bump, no notification, returns `false`). This is explicitly **not** a user edit and must never be wrapped in `AppUndoManager::recordTimelineChange`/`recordCombinedChange` — it derives current truth from the graph, it doesn't record an undoable intent.
  - `synth::TimelineReconciler::reconcile(doc, graph)` (`Source/Timeline/TimelineReconciler.h/.cpp`) is the graph-aware bridge: it collects the `"uuid"` property of every live node and calls `reconcileBindings` with straightforward set membership. Message thread only. **Call sites:** today, only `ProjectBundle::load` (see §5) — once the app owns a live `TimelineDoc` alongside its graph, it must also run after every graph-restoring choke point in `AppUndoManager`'s restore path (`applyJSONToGraph`, `applySnapshotPreservingNodes`, and any direct node delete outside the undo manager) — anywhere a node can appear or disappear is a place a binding can start or stop resolving.
  - **Re-binding.** `TimelineDoc::rebindLane(id, newNodeUuid)` is the one-click re-bind gesture's model half: it retargets a lane's `nodeUuid`, rejects a target that would collide with another lane's `(nodeUuid, paramId)` identity (the same doc-wide invariant `addLane` enforces) or an empty uuid or an unknown `LaneId`, and clears `orphaned` **optimistically** — the next reconcile re-derives whether it actually resolves. Unlike `reconcileBindings`, this **is** a normal user mutation (revision bump, notification, undoable). `setTrackBinding` clears the track's `orphaned` flag the same way whenever the uuid it stores actually changes.
- **MIDI file interchange.** `synth::MidiClipFile` (`Source/Timeline/MidiClipFile.h/.cpp`) imports and exports Standard MIDI Files (SMF) against `TimelineDoc` clips — the escape hatch while the piano roll stays minimal, and the intended future AI-authored-note-data surface (a `.mid` blob carries no file paths and no plugin identifiers, unlike almost anything else a model could hand back). **PPQ time format only** — a file using SMPTE time format is rejected outright with a message mentioning "SMPTE"; ticks convert to beats by dividing by the file's own ticks-per-quarter-note. **Tempo is deliberately not read**: tempo/time-signature/every other meta event are ignored on import and never written on export, since `TimelineDoc` has no tempo map (tempo lives on `TransportService`, see above) — only track-name meta events are read, to name imported tracks. **Note pairing is FIFO per `(pitch, channel)`**, identical to `MidiRecorder`: the earliest still-open note-on for a key is closed by the next note-off for that key, and a note-on with velocity 0 is treated as a note-off (the SMF convention `juce::MidiMessage::isNoteOn()`/`isNoteOff()` already implement via their default arguments). A dangling note-on, or any paired note resolving to a non-positive length, is floored to `kMinNoteLengthBeats` (1/32 beat) rather than dropped. **Bounds-checking-strict**: a track whose note count would exceed `TimelineDoc::kMaxNotesPerClip` rejects the WHOLE import rather than truncating — this is a future untrusted-input surface. `importIntoTrack` is all-or-nothing against the doc's `kMaxClipsPerTrack` cap and performs its own `addClip`/`addNote` calls with no batching; the caller wraps the whole call in `AppUndoManager::recordTimelineChange` for undo. Export writes SMF type 1 at `kExportPpq` (960) ticks-per-quarter-note, one tempo-less track per clip, notes at clip-relative beats exactly as stored (no truncation to the clip's own length).

### 4. TimelineSnapshot (the audio thread's view of the timeline)

`Source/Timeline/TimelineSnapshot.h/.cpp`, `Source/Timeline/EpochExchange.h`, `Source/Timeline/TimelineSnapshotExchange.h`

The immutable, flattened projection of `TimelineDoc` the audio thread reads, plus the exchange that publishes it. The doc is a tree of `juce::String`s and nested vectors the message thread mutates in place — none of which is audio-safe — so the message thread flattens it once per change and hands the result over.

- **Flatten on publish, never sort.** `TimelineSnapshot::buildFrom(doc)` (message thread) produces four contiguous arrays of trivially-copyable PODs — `tracks`, `notes`, `lanes`, `points` — plus per-track/per-lane index ranges (`firstNote`/`numNotes`, `firstLane`/`numLanes`, `firstPoint`/`numPoints`). Because the doc keeps clips sorted by `(startBeat, id)` and notes within a clip by `(startBeat, pitch)`, each clip contributes an already-sorted run and a track's clips fold together with a **stable merge of sorted runs** (`std::inplace_merge`), never a full sort. Clips may overlap, which is why concatenation is not enough. `revision` carries the doc revision it was built from.
- **Beats become absolute, notes are clipped to their clip.** The doc stores note starts clip-relative (so moving a clip never rewrites its notes); the snapshot stores `clipStart + noteStart` and an absolute `endBeat`, because the audio thread compares against the transport's ppq and must not have to find the owning clip. A note starting **at or after** its clip's end is **dropped**; one overhanging the end is **truncated** so `endBeat` == clip end.
- **Mute is excluded at flatten time, not skipped downstream.** A muted `Clip` (`Clip::muted`) contributes **nothing** to the snapshot — no `NoteEvent`s, no `AudioClipInfo` entry — as if it were absent from the document; a muted `MidiNote` inside an *unmuted* clip is dropped from that clip's run the same way (mute is not part of the note's sort key, so it says nothing about the note's position — only whether it's emitted). Doing the exclusion once, here, is what keeps every downstream consumer — `TimelineMidiSourceModule`, the `AudioClipStreamer`'s assignment table, an offline bounce — free of any notion that mute exists at all: they cannot forget to honour a flag they structurally never see. **Track-level mute is the deliberate exception** and stays a `bool` field on `TimelineSnapshot::TrackInfo` rather than being excluded the same way, because track solo/mute interact **per block** at the consumer: a track muted at the doc level but un-silenced by another track's solo has to keep its notes flattened so the solo logic has something to un-silence — excluding a muted track's content here, before solo is even evaluated, would make solo-over-mute impossible to implement downstream.
- **Fixed char buffers, never `juce::String`.** `bindingUuid` / `nodeUuid` / `paramId` are copied into `char[64]`, truncated at 63 bytes and always NUL-terminated (uuids are 36 chars, so truncation is theoretical). The audio thread `strcmp`s these; a `juce::String` copy is refcounted and therefore not audio-safe. `selfCheck()` re-verifies every index range and sort order — used by tests and the stress harness, not on the real audio path.
- **The exchange is generic.** All of the machinery lives in `synth::EpochExchange<T>` (`Source/Timeline/EpochExchange.h`) — `T` need only be default-constructible; `TimelineSnapshotExchange` is a thin subclass of `EpochExchange<TimelineSnapshot>` that keeps the `emptySnapshot()` spelling every caller already uses. The second instantiation is `EpochExchange<AutomationBindingTable>` (see [Automation applier](#automationapplier-writing-automation-into-live-parameters)), which is why the correctness argument is written once, in the template's header, rather than copied.
- **One atomic pointer, no `shared_ptr`, no locks.** `TimelineSnapshotExchange::beginAudioBlock()` is the whole read path: two atomic operations and a branch, zero allocation, `noexcept`. It is called **once per graph render pass, before the graph**, and the reference it returns is valid only until the next call — never cached across blocks. "Render pass" rather than "callback" because of the control-rate slicing flag below: with slicing on, one device callback is several passes. Nothing about the reclamation argument changes — it only needs "starting a block is a promise the previous block's reference was dropped", which holds per slice exactly as it holds per callback, and slicing makes the epoch advance *faster*, never slower. It is **never null**: an exchange with nothing published returns a static empty snapshot, eagerly constructed by the exchange's constructor so the audio thread never runs a function-local static's guarded initialisation. `atomic<shared_ptr>` is rejected on purpose: it is lock-based or a per-read refcount RMW, and it would make the audio thread run `free()` whenever it dropped the last reference.
- **Epoch reclamation.** `beginAudioBlock()` bumps `audioEpoch` **before** loading the pointer. `publish(std::unique_ptr<TimelineSnapshot>)` swaps the new snapshot in, pushes the displaced one onto a message-thread-only retire list tagged with the epoch observed **at retire time**, then frees every retiree whose tag is `<= audioEpoch - 2`. The argument: a callback still holding the retiree must have bumped the epoch before its load, and its load must precede the publisher's swap (it didn't see the new pointer), so the tag is at least that callback's own epoch value; two epochs later, two further callbacks have *started*, and starting one is a promise the previous block's reference was dropped. All four operations (bump, load, swap, retire-time read) are `seq_cst` — a release bump plus an acquire load does not stop the load being hoisted above the bump, and nothing weaker gives the two threads the single total order the argument needs. This runs once per block, so the cost is noise (same trade as `TransportService`'s position snapshot).
- **Idle audio, and shutdown.** With the device stopped the epoch never advances, so retirees accumulate — bounded by the number of publishes made while idle, and drained by the first `reap()` after audio restarts. `reap()` is public so a host that publishes rarely can drain on a timer; while audio runs, `publish()`'s own reap keeps steady-state occupancy at a handful of snapshots. `reclaimAllUnsafe()` frees **everything, including the current snapshot**, ignoring the epoch rule — legal **only** once the audio thread is stopped and cannot call `beginAudioBlock()`. The destructor calls it, and `AudioEngine::shutdown()` calls it last, after the device callback is removed and the graph is cleared.
- **Engine wiring.** `AudioEngine` owns the exchange (`getTimelineSnapshots()`), and `AudioEngine::renderPass` opens exactly one block on it per render pass, right after `transport.tick(...)`. Exactly one `beginAudioBlock()` per pass *is* the epoch-reclamation contract — never call it a second time in the same pass, and never skip it. The returned reference is parked on the transport (`TransportService::setCurrentTimelineSnapshot`, see §2) so modules can reach it through the playhead they already hold. Unlike the tick it is deliberately *not* gated on `setTransportEnabled`, since freezing the transport is a musical decision and must not stall reclamation.
- **`anySoloed`** is computed once in `buildFrom` over the **MIDI and Audio** tracks. Solo is a document-wide predicate — "is anything soloed?" is what decides whether a *non*-soloed track is silent — so consumers read the flag instead of rescanning every track every block. Audio tracks were excluded until audio-clip playback arrived, because nothing rendered them; now that `TimelineAudioSourceModule` does, a soloed audio track has to silence the MIDI tracks like any other, or solo would mean "solo, except audio". Automation tracks stay out: nothing plays them.
- **Audio clips.** An **Audio**-kind track contributes an `audioClips` run and **no** notes; a **MIDI** track contributes notes and **no** audio clips. One `synth::Clip` type covers both kinds in the document, so the track's `TrackKind` is what decides which half is flattened — a note left on an audio clip, or an `assetRef` left on a MIDI clip, is inert rather than half-played. Each `AudioClipInfo` carries the clip's doc `clipId` (the identity `AudioClipStreamer` keys its pool on — stable for the clip's lifetime, never reused), its absolute `startBeat`/`lengthBeats`, the `assetRef` copied into a fixed `char[256]` (larger than the 64-byte uuid buffers on purpose: an assetRef is a *path*, and truncating one silently would point at a different file rather than merely fail to match), the fades, the source trim, and `gainDb` already converted to a linear factor — **once**, here, with `juce::Decibels`' own −100 dB floor, so the audio thread never runs a `pow()` per clip per block. Runs are sorted by `startBeat` with no merge step (the doc already keeps a track's clips sorted) and clips are **not** clipped to anything: overlap is legal and sums at playback.
- **Testing.** `Tests/TimelineSnapshotTests.cpp` pins the flatten policy and the reclamation protocol, including a `TimelineSnapshot::liveInstanceCount()` counter (always compiled in) that proves snapshots are actually freed. `StressPublishAcquire` runs a reader thread against a publisher for ~1.2 s; on its own it only proves nothing crashed, but under the label-gated `run-asan` CI job it becomes a hard use-after-free detector — a premature free racing a concurrent read is exactly what ASAN reports.

#### AutomationKernel (evaluating a lane on the audio thread)

`Source/Timeline/AutomationKernel.h` — header-only, `noexcept`, allocation- and lock-free. `synth::AutomationKernel::evaluate(points, numPoints, beat, fallbackValue, cursor)` turns one lane's contiguous breakpoint run (`snapshot.points.data() + lane.firstPoint`, `lane.numPoints`) into its value at a beat, in the lane's own denormalised units. The applier is the consumer — it walks a snapshot's lanes, calls this once per lane per block and pushes the result at the bound parameter.

- **Endpoints clamp, never extrapolate.** An empty run returns `fallbackValue` (callers pass the lane's range default); a beat before the first point returns the first value, at or after the last returns the last. A lane is flat outside its own span, and a NaN beat takes the "before the first point" branch rather than producing a NaN.
- **Shape comes from the segment's LEFT point** — `BreakpointCurve`'s own definition. **Hold** returns the left value for the whole segment; **Linear** is `a + (b - a) * x^gamma` with `gamma = exp2(2 * tension)` (tension −1 → 0.25, fast start; 0 → 1, a plain lerp; +1 → 4, slow start), tension re-clamped to [-1, 1] so a hand-built run can't reach `std::pow` with a wild exponent. Endpoints stay exact for every tension, and the value exactly *at* a breakpoint's beat is always that breakpoint's own value. **Any other curve number — Bezier (2), or one from a future build — evaluates as Linear**, deliberately: an old build opening a newer file plays a sane approximation instead of a silent or stepped lane.
- **The cursor is the caller's, and it self-checks.** `AutomationCursor` caches the active segment plus its precomputed `gamma`, so a playing transport costs O(1) per call (one `std::pow` inside a shaped segment, a plain lerp when tension is 0). A beat *behind* the cached segment, a cold cursor, or a forward jump of more than `kMaxLinearAdvance` segments pays exactly one binary search — the worst case is O(log n) whatever the caller does with the beat. The cursor also stores the `points` pointer it cached against and re-searches on a mismatch, so a cursor held across a **snapshot swap** degrades to one search instead of reading a stale array; callers should still reset it (`cursor = {}`) on swap, but forgetting is then a lost cache rather than a wrong parameter value.
- **Defends against runs the doc can't produce.** Duplicate beats resolve to the rightmost point (so a zero-length segment is never the active one), a gap too small to reciprocate finitely is treated as degenerate, and `x` is clamped into [0, 1] before `std::pow` — a NaN escaping here would land straight in a live audio parameter. `Tests/AutomationKernelTests.cpp` pins all of it, including a 100k-beat sweep whose every warm-cursor result must match a cold binary-search evaluation **bit for bit**, and a perf tripwire (1M evaluations over a 4k-point run) that fires if the cursor ever degrades into a per-call scan.

#### AutomationApplier (writing automation into live parameters)

`Source/Timeline/AutomationApplier.h/.cpp` — the audio-side consumer of the kernel, plus the message-side table that tells it which lane drives which parameter. `AudioEngine::publishTimeline(const TimelineDoc&)` is the only producer; `AudioEngine::renderPass` is the only caller.

- **Bindings are resolved once, on the message thread.** For each snapshot lane, `publishTimeline` finds the graph node whose `properties["uuid"]` matches `lane.nodeUuid` (through a uuid → node map built once per publish, not a walk per lane) and then the `juce::RangedAudioParameter` on that node's processor whose `paramID` matches `lane.paramId`. A lane that resolves to neither produces **no binding**: orphaned lanes stay in the document (the orphaned-bindings policy) and simply automate nothing. The audio thread never walks the graph and never touches a `juce::String`.
- **A binding holds a refcounted `Node::Ptr`, not a `NodeID`.** A `juce::AudioProcessorGraph::Node` owns its processor, so holding a `Node::Ptr` keeps that processor — and therefore the `RangedAudioParameter*` — alive even after the node is removed from the graph. Deleting an automated module mid-render is therefore safe with no synchronisation: the applier keeps writing into a parameter nobody reads any more, and the next `publishTimeline` drops the binding. The alternative (re-resolving a `NodeID` per block) would mean walking the graph's node list on the audio thread.
- **Publish order is load-bearing: snapshot FIRST, bindings SECOND.** `Binding::laneIndex` indexes into `snapshot->lanes`, and the table carries the `const TimelineSnapshot*` it was resolved against so the applier reads lanes and points through *that* pointer rather than through the snapshot exchange — applier and bindings are coherent by construction. The raw pointer is safe because the engine always publishes the two back to back: a published table's snapshot is at most one publish behind the exchange's current one, and the exchange frees a retiree only two epochs after it retires it, by which time the audio thread has already loaded the newer table (both exchanges are opened in the same pass, bindings after the snapshot). A one-pass split-brain — Track In reading snapshot N+1 through the playhead while the applier still holds table N — is possible and harmless: both are valid published states, one block apart.
- **Callers must republish after a graph change.** Undo/redo, patch apply, preset load, a module delete: anything that adds, removes or replaces nodes invalidates *resolution*, not safety. A stale table keeps working (the `Node::Ptr`s see to that) but a node added since the last publish is not automated until the next one. Republishing an unchanged doc is cheap and always correct.
- **Applier semantics.** `applyBlock(table, blockInfo, recordState, uiFeed)` is `noexcept`, allocation-free, lock-free and log-free. Three deliberate rules: **not playing ⇒ nothing is written** (a stopped transport leaves every knob free for the user); **`setValue`, never `setValueNotifyingHost`** (a plain store — notifying would fire parameter listeners from the audio thread for every automated parameter on every block, and since the automation recorder would also feed playback straight back into its own parameter listener, so every pass would re-record itself; UI reflection of automation instead rides `uiFeed`, a one-way ring read on a message-thread timer — see [UI reflection](#ui-reflection-automated-parameter-changes-shown-in-the-ui-without-a-feedback-loop)); and values **clamp into the parameter's current range** via `RangedAudioParameter::convertTo0to1`, which clamps to [0, 1] itself, so a lane authored against a wider range pins at the endpoint. A non-finite value is skipped rather than handed to JUCE (`NormalisableRange` `jassert`s on NaN). Each binding owns its `AutomationCursor`, so swapping tables swaps the cursors with them and there is nothing to reset. On top of all that, the automation recorder's **per-lane record mode** decides whether the lane may write this block at all — see the record-modes table below.
- **Automation writes the base value; CV stacks on top.** See [`docs/modulation.md`](modulation.md) — automation is a very precise knob turn, not a modulation source.
- **Control-rate slicing (`setAutomationSlicingEnabled`, default OFF).** With the flag on, `renderNextBlock` runs the whole per-block sequence — `transport.tick(sliceLen)` → snapshot open → MIDI capture → `applyBlock` → `graph.processBlock` — once per 64-sample slice over a `juce::AudioBuffer` **view** into the caller's buffer, with the block's MIDI split into a preallocated scratch `MidiBuffer` per slice at slice-relative sample positions. The channel-pointer array and the MIDI scratch are sized in `prepareSliceScratch` (both prepare paths); a callback wider than prepare sized for falls back to a single unsliced pass rather than allocating. The final partial slice is handled; master mute still zero-fills once, after every slice.
  - **Why it ships off.** It is not audio-neutral. Per-sample processing doesn't care (`AutomationSlicingTest.SliceParityTimeInvariantChain` measures a max-abs difference of exactly **0** for an Oscillator → Filter → VCA chain), but any module that reads a control **once per block** — `ChorusModule`'s `cvRate[0]`, and the same pattern in several FX — lands on a different trajectory and stays there. `AutomationSlicingTest.SliceDifferenceOnBlockRateFx` renders a Chorus with an LFO on its Rate CV both ways and *reports* the difference (measured: max-abs ≈ **2.0**, i.e. full-scale) without asserting anything about equality; that number is the evidence. So turning slicing on is a measured, per-patch decision, not a free upgrade. The CPU cost is the smaller problem — `AutomationSlicingTest.SlicingCostTripwire` measures ~**1.1×** for 200 blocks over a 49-node patch, and asserts only against a 4× blow-up.
  - **What it buys.** Automation moves 8× per 512-sample block instead of once. `AutomationSlicingTest.SlicingMovesAutomationWithinTheBlock` pins that exactly: the sliced parameter leads the unsliced one by `slope * (blockSize - 64) / samplesPerBeat` at the end of every block.
- **Testing.** `Tests/AutomationApplierTests.cpp` (binding resolution, the playing-only rule, range clamping, deleted-node safety, republish-under-render, plus the record-mode branches: `OffLaneIsCompletelyInert`, `WriteWithGlobalRecordOffActsLikeRead`, `ClaimedTouchLaneYieldsToTheHand`) and `Tests/AutomationSlicingTests.cpp` (the four facts above). Both drive a `HostMode::Hosted` engine through `synth::OfflineTransportDriver` and assert on parameter values or rendered audio, never on applier internals.

#### AutomationRecorder (record modes and gesture capture)

`Source/Timeline/AutomationRecorder.h/.cpp` — the message-thread half of automation: it turns parameter gestures into breakpoints. The sibling of `MidiRecorder` (arm → capture into a fixed ring → commit as one undo step), with a different source: `juce::AudioProcessorParameter::Listener` callbacks, which is where a UI slider attachment's `beginChangeGesture` / `setValueNotifyingHost` / `endChangeGesture` trio lands.

**A parameter listener is called on whatever thread wrote the parameter.** Our own UI writes on the message thread, but a host automating a *hosted* plugin's parameter calls straight from its audio thread — `juce::AudioProcessorParameter::sendValueChangedMessageToListeners` dispatches inline, under the parameter's listener lock. So `ParamListener`'s two callbacks are allocation-free and lock-free and do nothing but read atomics (the suspend counter, the global arm), take the transport's seqlock position snapshot, denormalise through a `RangedAudioParameter*` resolved once at bind time, and push a POD `Event` into a ring. The whole capture state machine — opening and closing spans, reading record modes off the doc, thinning, committing, touching `AppUndoManager` — runs in `drainEvents()` on the message thread, called from `update()`, `pollTransport()` and the arming/detach paths. There are **two** rings, because `juce::AbstractFifo` is single-producer: one the message thread fills, one every other thread fills (its pushes serialised by a try-lock that never blocks — a contended push drops the event and raises `hadOverrun()`, like a full ring). A value push also refuses to consume the last `kGestureHeadroom` slots, so a gesture edge always fits: dropping a value only thins the take, but dropping a gesture *end* would lose it, since nothing else closes a `Touch` span. A message-thread gesture edge drains inline, so a knob still claims and commits with no latency; a foreign-thread edge waits for the next `update()`. Which ring a callback belongs to is decided by comparing `juce::Thread::getCurrentThreadId()` against an id stamped by `attachTo()`/`update()` — **not** `juce::MessageManager::existsAndIsCurrentThread()`, which takes a `std::mutex`. `callbackDepth` (the counter that stops `unbindAll()`'s graveyard from freeing a listener whose callback is on the stack) is atomic for the same reason.

**Record modes.** `AutomationLane::recordMode` is a `synth::LaneRecordMode` stored as an `int` (it is serialised as one, so the numbers are format — same contract as `TrackKind`/`BreakpointCurve`, pinned by `static_assert`s). It is written only through `TimelineDoc::setLaneRecordMode(id, mode)`, which rejects anything outside 0..4 rather than clamping, and `fromVar` rejects an out-of-range value as malformed; a lane in a file that predates record modes loads as **Read**. It rides into `TimelineSnapshot::LaneInfo::recordMode` so the audio thread can honour it without touching the doc.

| Mode | Playback (applier) | Capture (recorder) |
| --- | --- | --- |
| `Off` (0) | never writes | never captures |
| `Read` (1) | always writes | never captures |
| `Touch` (2) | writes **unless the parameter is claimed** | span opens on gesture start, **commits on gesture end** |
| `Latch` (3) | writes **unless the parameter is claimed** | span opens on gesture start, stays open after the gesture ends, commits on stop |
| `Write` (4) | **never writes while global record is armed**; with record off it reads like `Read` | span opens at play-start (no gesture needed), commits on stop, then auto-drops to `Touch` |

**Gesture-gating is the programmatic-write guard.** A value change is only ever captured **while a capture span is open**, and only a real gesture (or, for `Write`, the transport starting to play on an armed lane) can open one. A preset load, an AI patch apply and an undo restore all push values with `setValueNotifyingHost` exactly like a knob drag does — with no gesture there is no span, so nothing is captured, and none of those call sites has to know this class exists. `AutomationRecorder::ScopedProgrammaticApply` is the belt-and-braces second guard for a future path that *does* wrap programmatic writes in gestures: while one is alive (a re-entrant counter, not a flag) even gestured events are dropped. Intended call sites, to be wired with the app-level owner: preset load, `AIStateMapper::applyJSONToGraph` on the apply path, and the undo/redo restore.

**Claims are the whole of what the audio thread sees.** `GestureClaims` is eight `std::atomic<const juce::AudioProcessorParameter*>` slots naming the parameters a hand is currently on; `AutomationRecordState` bundles them with the global record arm. `AudioEngine::setAutomationRecorder(AutomationRecorder*)` stores **only** `&recorder->getAudioState()` in a `std::atomic<const AutomationRecordState*>` (borrowed, never owned — same contract as `setMidiCaptureSink`), so the audio thread can never reach the recorder's doc, undo manager or capture buffers. `applyBlock` does a relaxed eight-slot pointer scan per `Touch`/`Latch` binding. A ninth simultaneous gesture simply gets no slot and that lane keeps playing back — failing that way round is deliberate, since the alternative is a container the message thread can resize under the audio thread.

**Unregistering a borrowed pointer is a handshake, not a store.** Both `setAutomationRecorder` and `setMidiCaptureSink` publish the new value and then call `AudioEngine::drainAudioCallbacks()`, so once a setter returns, no audio callback can still be inside code that read the OLD pointer — which is what makes `~MainComponent`'s "null it, then destroy it" safe. It matters most on the plugin path: the engine belongs to `AgentSynthAudioProcessor` and keeps rendering after the editor and its `MainComponent` (the owner of both objects) are gone. The audio half is two monotonic counters bumped on the way into and out of `renderNextBlock` — the one funnel both `audioDeviceIOCallbackWithContext` and `processHostBlock` go through — and the drain waits for *finished* to catch up with the *started* count it read after publishing. Monotonic counters rather than an in-flight count on purpose: a host's audio thread renders back-to-back, so "is anything in flight right now?" can be missed forever, where "have the passes that had already started finished?" always completes within one block. Bounded (2 s) so a wedged device thread degrades into "carry on" instead of deadlocking teardown, and it must never be called from the audio thread. Pinned by `PluginProcessorTests.cpp`'s `BorrowedPointerSetterWaitsForAnInFlightRenderPass` / `AutomationRecorderSetterDrainsToo` (a probe module parks the audio thread inside a pass; the setter must not return until it leaves) and `DestructionWhileTheHostKeepsRenderingIsSafe`.

**Commit.** One `AppUndoManager::recordTimelineChange` per commit *batch* — a `Touch` gesture end is a batch of one, a stop is a batch of every span that was open, so undoing a stop is one Cmd+Z and not one per lane. Each span: RDP-thin the captured points, remove every existing breakpoint inside `[spanStart, spanEnd]`, lay an anchor at `spanStart` (the value at span entry for `Write`/`Latch`, the first captured value for `Touch`), insert the thinned points, and for `Write`/`Latch` close with a terminal anchor at `spanEnd` (Touch deliberately does not — releasing the knob is exactly where the underlying automation should take back over). An **empty `Touch` gesture is a total no-op** (nothing removed, no undo step); an empty `Write`/`Latch` span still flattens its region to the entry value, because "overwrite from here to stop" is what was asked for.

**Thinning** is Ramer-Douglas-Peucker, **iterative** (an explicit index stack — a 16k-point take must not recurse per point) and measured by **vertical** distance in value units, not perpendicular: beats and parameter values have unrelated units, so a perpendicular metric would change meaning with the lane's range. `epsilon` is `kThinningEpsilonFraction` (0.2%) of the lane's range span — 40 Hz on a 20 Hz–20 kHz cutoff lane. Kept points keep their **exact** captured values, so a gesture's corners survive verbatim.

**Auto-drop happens before the commit, not after.** On stop, every `Write` lane in the document drops to `Touch` (Cubase's rule — a forgotten `Write` mode must not wipe the lane on the next playback). The order matters: `recordTimelineChange`'s before/after snapshots are whole-document and `recordMode` is part of a document, so dropping the mode *after* the commit would bake "was Write" into the undo step and undoing the take would silently re-arm the lane. The drop itself is a plain `setLaneRecordMode` and is never wrapped in undo.

**Re-entrancy.** A commit mutates the doc → listeners fire → the owner republishes → `unbindAll()` + `bindLane()`, all potentially *inside* one of the recorder's own parameter callbacks. Two rules make that safe: capture state lives in `spans`, keyed by `LaneId` and independent of `bindings` (so a re-entrant rebind finds nothing in flight, and an open `Latch`/`Write` span survives an unrelated republish instead of being dropped), and every commit path *takes* its pending commits and resets the span state **before** touching the doc; and `unbindAll()` moves the detached per-parameter listener objects to a graveyard drained only when no callback is on the stack, rather than destroying the listener whose method is currently executing. One listener object per binding, not the recorder itself: JUCE hands the callback only the parameter's index *within its own processor*, so two lanes bound to index 3 on two different modules would otherwise be indistinguishable.

**Driving.** `update()` (message thread; a UI timer owns it in the app, tests call it directly) purges the graveyard, drains the ring and polls the transport for the play-start / stop transitions. Capture requires the transport to be **playing** — a knob turned against a stopped transport has no span to land on. The ring is a fixed 16384-slot `juce::AbstractFifo` of `{laneId, beat, value}`: the listener callback may run on a host's audio thread, so it must not allocate; overflow drops the event and raises `hadOverrun()`, and the take still commits, just thinner. **No logging anywhere in this file** — a parameter drag produces a value change per mouse move (see CLAUDE.md's freeze incident).

**Testing.** `Tests/AutomationRecordTests.cpp`. Most of it is headless — a bare `TransportService` ticked like `renderPass` does, plus a standalone `FilterModule` for a real `RangedAudioParameter` — and covers Touch/Latch/Write commit shapes, the programmatic-write guard, `ScopedProgrammaticApply`, RDP thinning, empty spans, ring overflow, the auto-drop, and `recordMode` round-tripping through `toVar`/`fromVar` and the snapshot. Two tests need a hosted `AudioEngine`: `ApplierRespectsClaims` (a real gesture stops the applier writing, releasing it resumes) and `RecorderNeverHearsTheApplier` (200 rendered blocks of playback into an armed `Touch` lane capture nothing and create no undo step).

#### UI reflection (automated parameter changes shown in the UI without a feedback loop)

`AutomationApplier::applyBlock`'s `setValue` (never `setValueNotifyingHost`) is deliberately silent — no attachment hears it, so a slider under active automation used to sit frozen. This closes that gap with a one-way feed instead of a notification: `synth::AutomationUiFeed` (`Source/Timeline/AutomationUiFeed.h`) is a pre-allocated 4096-slot lock-free SPSC ring of `{nodeId, param, newNormalized}`, owned by `AudioEngine` (`getAutomationUiFeed()`) and passed into `applyBlock` alongside the record state.

- **Push is deduped per binding, not per block.** `AutomationBindingTable::Binding` carries its own `nodeID` (captured alongside the refcounted `Node::Ptr` at `publishTimeline` time) and a `mutable lastPushedNormalized` (NaN until the first write). After the plain `setValue`, the applier pushes only when the newly-written normalised value differs from `lastPushedNormalized` — a static lane pushes once, ever; a ramping one pushes on essentially every block. A full ring drops the newest event silently: reflection is best-effort and must never add audio-thread latency.
- **`GraphEditor`'s existing 30 Hz timer drains it** (`timerCallback()`) — no second free-running timer. For each event it finds the `ModuleComponent` for `event.nodeId` in `content.getModules()` and calls `ModuleComponent::reflectParameterValue(param, normalized)`; an event for a NodeID with no live component (module hidden or deleted) is simply discarded. Draining an empty ring is one `AbstractFifo::prepareToRead` call, effectively free on a tick with nothing queued.
- **`reflectParameterValue` finds the control through a param → control map, not by name.** `ModuleComponent` keeps `sliderParams`/`comboParams`, index-parallel to `sliders`/`comboBoxes` and populated only in `createControls()`'s generic auto-UI branch (float/int sliders, choice combos) — the two ExternalMidiModule combos that aren't `ComboBoxParameterAttachment`-driven get a `nullptr` entry so the arrays stay aligned. A match denormalises via the SAME `RangedAudioParameter` the control's own range mirrors (a slider's `NormalisableRange` is set up by `SliderParameterAttachment`'s ctor to be exactly the parameter's, in denormalised units) and calls `setValue(..., juce::dontSendNotification)`.
- **`dontSendNotification` is the whole trick.** No attachment callback fires, so the parameter itself is never written and no gesture starts — `AutomationRecorder`'s parameter listener (the only thing that could turn this into a loop) never hears it, whatever record mode is armed. The control's own repaint rides the existing buffered-image / 15 Hz gating discipline (see §10–11 of `docs/layout.md`) — nothing here calls `repaint()` directly.
- **Testing.** `Tests/AutomationUiReflectionTests.cpp`: a bare-applier dedupe check (flat lane ≤1 event over 20 blocks, a ramping one ~1 per block); a real `ModuleComponent` reflecting into its Filter cutoff slider with a spy `AudioProcessorParameter::Listener` proving zero callbacks; an armed `Touch`-lane `AutomationRecorder` capturing nothing from a reflection; a two-module `GraphEditor` routing events to the right component by NodeID and discarding one for a deleted node without crashing; and a 5000-push overflow test against the 4096-capacity ring.

### 5. ProjectBundle (.agsproj)

`Source/ProjectBundle.h/.cpp`

The on-disk project format that pairs a patch with a `TimelineDoc`. A bundle is a directory named `*.agsproj` containing `project.json` plus two asset subdirectories, `Audio/` and `Peaks/` (created empty; the audio-recording flow is the first thing to write into them). `project.json` is everything `AIStateMapper::graphToJSON` writes (nodes, connections, modulations, schemaVersion, any keys `PatchDocument` had stashed from a prior load) with one addition: a top-level `"timeline"` key holding `TimelineDoc::toVar()`.

- **`"timeline"` is reserved everywhere else, meaningful only here.** A plain `.json` preset that happens to carry one only ever stashes it inertly via `PatchDocument` (see §3 above); `AIStateMapper::validatePatch` refuses it outright from provider-authored output (`PatchValidationError::TimelineNotAllowed`) so a model can never author automation. `ProjectBundle` is the one place a `"timeline"` key is actually interpreted.
- **Fixed, all-or-nothing load order**, mirroring `SnippetManager::insertSnippet`'s trusted/untrusted pairing:
  1. Parse `project.json` — unparseable or non-object is rejected.
  2. **Detach `"timeline"` from the root before anything else.** This has to happen *before* the gate in step 3: the untrusted validator refuses any patch carrying a `"timeline"` key, and a bundle's `"timeline"` is this format's own dialect, not provider output smuggled in — pulling it out first means it's validated on its own terms in step 4 instead of tripping a check meant for a different threat. The remaining root is "the patch".
  3. **Gate:** `AIStateMapper::validatePatch(patch, graph, clearExisting=true, trusted=false)`. `project.json` is a file on disk, hand-editable exactly like a preset or a snippet — a malformed patch is rejected whole, never partially applied.
  4. Validate the timeline into a **local** `TimelineDoc` via `fromVar` (already all-or-nothing). A missing `"timeline"` key is not an error — it means a plain patch is being opened as, or upgraded into, a bundle, and the timeline starts empty. A present-but-malformed one is rejected whole.
  5. Only once *both* validations pass does anything mutate: `applyJSONToGraph(patch, graph, clearExisting=true, trusted=true)` — trusted, so node `"uuid"`s are honoured and parameter values aren't rescaled by the untrusted-input heuristic, the same reasoning as the snippet insert path; `patchDocument.loadFromVar(patch)` on the timeline-stripped root, so `"timeline"` is never double-stored in the stash; then the live `timeline` is brought to the validated state (`fromVar` on the same var already proven valid against the local doc, or `clear()` when the key was absent).
  6. **Binding pass — never delete.** `TimelineReconciler::reconcile(timeline, graph)` recomputes every track's `bindingUuid` and lane's `nodeUuid` against the freshly-loaded graph's live node uuids (see §3's "Orphaned bindings" for the full policy). A binding that no longer resolves is retained and flagged `orphaned`, never deleted; one that resolves is (re-)confirmed. Running this at the end of `load` means a freshly opened project shows correct orphan state immediately, before the user touches anything.
  - On any failure before step 5, `graph`, `timeline` and `patchDocument` are left exactly as they were.
- **Save order matters too.** `graphToJSON(graph)` → `patchDocument.toVar(...)` (re-merging whatever unknown top-level keys were stashed on this bundle's last load) → **then** `"timeline"` is set to `timeline.toVar()` **last**, so a live timeline always overwrites a stale one sitting in the stash (e.g. a bundle that started life as a plain `.json` carrying an old `"timeline"`).
- **Asset policy (enforced since audio recording arrived).** Any asset reference stored in the document (`Clip::assetRef`) is a path *relative to the bundle root* (`Audio/foo.wav`) — an absolute or escaping path is rejected, the same restriction as `ModuleBase::setExtraState`'s trusted-only file paths. The check is `TimelineDoc::isValidAssetRef`, applied by both `setClipAsset` and `fromVar`. The record flow writes takes into `Audio/take-<n>.wav` + `Peaks/take-<n>.agpk`.
  - **Unsaved projects — adopted on save.** A take recorded before the project has ever been saved has no bundle to go into: it lands in `<user app data>/<settings folder>/Recordings/` and its clip carries the reserved prefix `Recordings/take-<n>.wav` — still relative in form, so the one path rule holds, but resolved against app data rather than a bundle root. `synth::AssetManager::adoptRecordingsAssets` (see the "Asset management" section below) moves those files into `Audio/` on the first save and rewrites the refs. `Recordings/` is therefore a reserved subdirectory name inside a bundle.
  - **Nothing is ever auto-deleted from `Audio/`/`Peaks/`.** Undoing a take removes the clip, not the recording. Reaping unreferenced files is `synth::AssetManager::cleanUnusedAssets`'s job.
- **Plain `.json` save/load is unaffected.** `GraphEditor::savePreset`/`loadPreset` are untouched by this class — a `.agsproj` is a parallel format, not a replacement.

#### Opening and saving one from the app

The toolbar's existing Save and Load-from-file dialogs carry both formats (`"*.json;*.agsproj"`), and `MainComponent::saveToFile()` / `openFromFile()` — the dialog callbacks' whole bodies, and the two `…ForTest` hooks tests drive instead of a dialog — branch on the `juce::File` they are handed:

- **Save.** A name ending in `.agsproj` writes a bundle (`ProjectBundle::save(dir, graph, timelineDoc, graphEditor.getPatchDocument())`, creating the directory and its `Audio/`/`Peaks/` subdirectories). Anything else is `GraphEditor::savePreset` exactly as before — a plain `.json` preset carries no `"timeline"` key.
- **Open.** A `.agsproj` is a **directory**, so the open dialog also sets `canSelectDirectories`; the handler confirms `ProjectBundle::isBundle()` before doing anything. The load is bracketed the way `GraphEditor::loadPreset` brackets its own (detach module components *before* the graph's processors are freed, `updateComponents()` after, whatever the outcome), wrapped in a programmatic-apply scope, and followed by the standard reconcile+publish pass. Anything else goes down the untouched `loadPreset` path, which leaves the live timeline alone.
- The `PatchDocument` is the graph editor's own (`GraphEditor::getPatchDocument()`), so a bundle re-merges the very same unknown-top-level-key stash a plain preset load filled.
- Both branches always exist — the dialog offers both formats unconditionally, since `.agsproj` bundles are a permanent part of the app rather than something a build configuration could omit.

### 6. ModuleBase

`Source/Modules/ModuleBase.h`

Abstract base class for every audio processing unit. Extends `juce::AudioProcessor`.

#### ModuleType enum

Every concrete module implements `virtual ModuleType getModuleType() const = 0`. Current values:

```
Oscillator, Filter, VCA, ADSR, LFO, Sequencer, PolySequencer,
MidiKeyboard, PolyMidi, ExternalMidi, Attenuverter,
Delay, Distortion, Reverb, Chorus, Phaser, Compressor, Flanger, Limiter,
ParametricEQ, VoiceMixer, Bitcrusher, PitchShifter, RingModulator, Noise, Math, Sampler, Wavetable,
MacroControl, SampleHold, EnvelopeFollower, Comparator,
AudioInput, TimelineMidiSource, RecordTap, TimelineAudioSource, HostedPlugin
```

The last four are the internal-only / singleton nodes: `AudioInput` (a patch singleton), and `TimelineMidiSource` / `RecordTap` / `TimelineAudioSource`, which the module library never offers and a model may never author.

`ModuleType` is consumed by `LayoutUtil::getModuleWidthBucket` to classify modules into width buckets (Narrow / Single / Double) and by `ModuleComponent` for type-safe UI layout switching.

#### Node uuid mirror (`setNodeUuid` / `getNodeUuid`)

A graph node's `"uuid"` property (see `AIStateMapper::graphToJSON`) is the app's long-lived node identity — timeline track bindings and automation lanes key on it. It lives in a `juce::NamedValueSet` of `juce::String`s, neither of which the audio thread may touch, so `ModuleBase` **mirrors** it into a fixed `char[64]` the moment it is assigned. `getNodeUuid()` is audio-safe (acquire-load a flag, return the buffer or `""`, never null, no allocation), which is what lets `TimelineMidiSourceModule` `strcmp` itself against a `TimelineSnapshot::TrackInfo::bindingUuid`.

- **Writers are exactly the three places `AIStateMapper` writes the property**: `adoptUuidIfTrusted` (trusted apply), `graphToJSON`'s lazy generation, and `applySnapshotPreservingNodes`. Each calls the shared `mirrorUuidIntoProcessor` helper immediately after `node->properties.set("uuid", ...)`. Add a fourth writer of the property and it must mirror too, or a Track In node silently stops matching its track.
- **The invariant the lock-free read relies on:** the uuid only ever transitions **empty → value**, and only while the node is not yet audio-visible (all three writers run on a node the caller just created, or under the graph callback lock). It is never rewritten to a different value and never cleared, so an audio-thread reader sees either `""` (and does nothing) or the final value — there is no torn intermediate state to defend against.

#### ModulationTarget / ModulationCategory

- `ModulationTarget { juce::String name; int channelIndex; }` — describes a modulatable parameter and the audio-buffer channel that carries its CV signal. Returned by `virtual getModulationTargets()`.
- `ModulationCategory` enum: `Envelope, LFO, Oscillator, Sequencer, Filter, FX, Other`. Returned by `virtual getModulationCategory()`.

#### VisualBuffer

Modules may opt in to a thread-safe `VisualBuffer` (circular buffer of `std::atomic<float>`) for scope visualization. Enabled/disabled via `enableVisualBuffer(bool)` and accessed via `getVisualBuffer()`.

#### Logical-Port API

Maps raw audio-buffer channel indices to the visible jack slots shown in the UI.

| Symbol | Description |
|---|---|
| `PortRole` | Enum: `Audio, ModCV, Pitch, Gate, Midi, Other` |
| `LogicalPort` | `{ int visibleJackIndex; PortRole role; bool isPolyGroupHead; int polyVoiceSpan; }` |
| `mapInputChannel(int rawChannel)` | Virtual — returns `LogicalPort` for a raw input channel |
| `mapOutputChannel(int rawChannel)` | Virtual — returns `LogicalPort` for a raw output channel |
| `getVisibleInputPortCount()` / `getVisibleOutputPortCount()` | How many jacks the UI renders |
| `JackTarget` / `getJackTargets(jack, isInput)` | Inverse of `mapInput/OutputChannel` — every poly-group head anchored to a visible jack; drives connection creation in `GraphEditor` |

`GraphEditor` uses this API to anchor wire endpoints to the correct visible jack regardless of how many raw channels are fanned out underneath, and to resolve which raw channels a dragged cable or poly toggle should wire (`GraphEditor::resolvePolyLink`, `rewireForPolyChange`). See [docs/modulation.md](modulation.md#creating-poly-connections).

#### isAutoPromotableModTarget

`virtual bool isAutoPromotableModTarget(int dstChannel) const`

Guards poly-mode CV inputs from being auto-wrapped in an `AttenuverterModule` by the AI/routing layer. Default: returns `true` iff `dstChannel` is in `getModulationTargets()`. Modules override this to exclude poly-voice pitch/gate channels which should not receive an attenuverter.

#### Extra (non-parameter) State

`virtual juce::var getExtraState() const` / `virtual void setExtraState(const juce::var&)`

For state that has to survive a graph rebuild but is not expressible as a `juce::AudioProcessorParameter` — today only `SamplerModule`'s loaded file path. `AIStateMapper::graphToJSON` writes whatever `getExtraState()` returns as the node's `"state"` property, and `applyJSONToGraph` feeds it back through `setExtraState()`. Return a **void** `var` when there is nothing to persist, so modules that do not use the hook add no JSON.

This matters because preset load — and any undo that has to fall back to a full rebuild — goes through `graphToJSON` → `applyJSONToGraph`, which rebuilds processors from scratch: anything not in that JSON is silently lost. (An ordinary undo restores by diffing and keeps the processor, so it re-applies `"state"` only when it actually changed — see [AppUndoManager](#appundomanager).)

`setExtraState` is only ever called on the **trusted** path (our own snapshots and presets). A module may legitimately read this as a filename, so honouring it for untrusted model output would turn a patch suggestion into an arbitrary file read.

#### Port Labels

`virtual juce::String getInputPortLabel(int channelIndex) const` / `getOutputPortLabel(int channelIndex)` — overridden per-module to provide descriptive jack names (e.g. "CV In", "Audio L") shown in the UI.

#### Bypass/Mute Contract

Every `processBlock` override **must** honour both flags using **two separate branches**:

```cpp
if (isBypassed()) {
    // Dry pass-through — do NOT touch audio channels (ch0, ch1).
    // Clear CV channels (index >= 2) so mod CV does not leak as audio.
    return;
}
if (isMuted()) {
    buffer.clear();
    return;
}
// ... normal DSP ...
```

**Never** collapse to `if (isBypassed() || isMuted()) buffer.clear()` — that silences on bypass instead of passing the dry signal through.

**Exception:** modules with no dry audio path clear their output on bypass, because there is nothing to pass through. Two shapes qualify:

- **Pure sources** — no audio *input* (e.g. `OscillatorModule`, `PolyMidiModule`).
- **Audio-in / CV-out taps** — no audio *output* (e.g. `EnvelopeFollowerModule`, whose ch0 output is Env CV, and `ComparatorModule`, whose outputs are Gate / Inverse). Passing the dry signal through would push audio-rate samples into a CV destination, which is worse than emitting no modulation.

Both still use two separate branches, never a fused `if (isBypassed() || isMuted())`, so the intent stays explicit.

#### Output Level Stage

`ModuleBase` offers an opt-in output-level parameter for modules whose output is audio — `addOutputLevelParameter()` in the ctor, `prepareOutputLevel(sampleRate)` in `prepareToPlay`, `applyOutputLevel(buffer, numAudioChannels)` at the end of the **normal** `processBlock` path. It is a no-op on modules that never opt in.

Two constraints follow from the contract above: `applyOutputLevel` must sit **after** both early returns (a bypassed module passes dry audio through at full level; a muted one is already cleared), and `numAudioChannels` must exclude CV channels. Full rules, including why this is opt-in rather than universal and why it must be the last parameter added, live in [`fx_modules.md § Output Level`](fx_modules.md#output-level-shared-stage).

Related: look parameters up with `findParameterByID(processor, "paramID")` rather than `getParameters()[n]`. Parameter order is not part of a module's contract, and positional lookups silently repoint when a parameter is added.

### 8. App wiring — who owns the timeline, and every hook that keeps it in step

`Source/MainComponent.h/.cpp`

**`MainComponent` owns the app's one live `synth::TimelineDoc`, its `synth::AutomationRecorder`, and its `synth::MidiRecorder`**, as plain members. All three exist unconditionally, and every line of wiring below is likewise permanent, always-compiled code — there is no build configuration in which it is stripped out. The plugin path gets the same wiring for free — `MainComponent` is shared by both targets — with the one difference that the engine is injected rather than owned.

**Declaration order is load-bearing:** `timelineDoc` and `automationRecorder` are declared *before* `undoManager`, so they outlive it. A `TimelineSnapshotAction` sitting on the undo stack holds a reference to the doc (see `AppUndoManager` below), and members are destroyed in reverse declaration order. `midiRecorder` has no such constraint — unlike `automationRecorder`, it holds no reference to the doc or the undo manager between calls (`stopAndCommit(doc, undo)` takes both as parameters), so its declaration position is not load-bearing.

This is the definitive hook inventory. There are six kinds, and nothing else in the app publishes, reconciles, arms the automation recorder, or starts/stops a MIDI take:

| # | Hook | Where | What it does |
|---|---|---|---|
| 1 | **Publish-on-change** | `TimelineDoc::Listener::timelineChanged` | `publishTimelineAndRebindRecorder()`: `AudioEngine::publishTimeline(doc)`, then `recorder.unbindAll()` + one `bindLane()` per resolvable lane. The rebind repeats `publishTimeline`'s own resolution (uuid -> node map built once, then `findParameterByID`) deliberately: a lane the applier can play back is exactly a lane the recorder must capture into. |
| 2 | **Reconcile-after-graph-change** | `reconcileTimelineAfterGraphChange()`, called from: preset load (`openFromFile`), factory-preset load (`loadFactoryPresetAtIndex` — the one choke point behind both the Load menu and the test hook), New Patch, `.agsproj` open, AI apply (`aiPatchApplied`), and the undo manager's post-restore hook | `TimelineReconciler::reconcile(doc, graph)`, then `publishTimelineAndRebindRecorder()` **only if it returned `false`**. A reconcile that flips a flag is itself a doc mutation, so hook 1 has already published by the time it returns — publishing again would just rebuild a snapshot for nothing. |
| 2b | **Catch-all** | `GraphEditor::onGraphStructureChanged` (fires at the end of every `updateComponents()`) | `reconcileTimelineBindingsOnly()` — reconcile with **no** unconditional republish. This is what covers a graph edit with no explicit site of its own, the canonical one being "the user deleted the Track In node from the canvas" (that goes through `recordStructuralChange`, a *record*, not a restore, so the undo hooks never fire). Kept cheap on purpose: `updateComponents()` is called after every structural mutation, and a binding can only start or stop resolving when a node appears or disappears — which is also the only way an orphan flag moves, so hook 1 still publishes for exactly the cases that need it. |
| 2c | **Hosted-plugin publish** | `HostedPluginModule::onInstancePublished`, installed on every hosted node by `installHostedPluginObservers()` (run from the same `onGraphStructureChanged` catch-all as 2b) | `reconcileTimelineBindingsOnly()` + `rebuildGraphForLatencyChange()`. The only reconcile trigger that is not a graph *edit*: a hosted plugin's load completes asynchronously, so a lane bound to one of its parameters cannot resolve at the moment the node appears, and no later graph change is guaranteed to come along. Same reconcile-only, no-unconditional-republish posture as 2b, for the same reason. |
| 3 | **Programmatic-apply guard** | `MainComponent::ProgrammaticApplyScope` (an `AutomationRecorder::ScopedProgrammaticApply` RAII guard) around: preset load, factory load, New Patch, `.agsproj` open, the AI apply span (`aiPatchAboutToApply` -> `aiPatchApplied`), and every undo/redo restore | Suspends automation capture so a programmatic rewrite of parameters is never mistaken for a user gesture. Belt-and-braces over the recorder's primary guard (a capture span only ever opens from a real gesture). |
| 4 | **Recorder driving** | the existing 10 Hz `timerCallback` | `automationRecorder.update()` — drains the gesture ring and polls the transport. No new timer. |
| 5 | **MIDI take start/stop** | `TimelineTransportBar::onRecordToggled`, installed in `initialiseCommon()`; auto-commit half in the same 10 Hz `timerCallback` | ON: finds the first `armed && kind == TrackKind::Midi` track by iterating `timelineDoc.getTracks()`; none found -> `setRecordingState(false)` + `statusBar.showMessage("Arm a track to record")`, transport untouched (no side effect on a rejected request). Found -> rolls the transport if it isn't already playing (record implies roll — a DAW convention), then `midiRecorder.startRecording(track, currentPpq)`. OFF (button click, **or** the poll noticing playing -> stopped while `midiRecorder.isRecording()`) -> `commitMidiRecording()`: `midiRecorder.stopAndCommit(doc, undoManager)`, a `hadOverrun()` warning ("Dropped MIDI events during recording") via the status bar, then `setRecordingState(false)` — the ONE place a take ever commits, so the explicit button path and the auto-commit-on-stop path can never diverge. |

`initialiseCommon()` installs all of it: `timelineDoc.addListener(this)`, `recorder.attachTo(doc, undoManager, engine.getTransport())`, `engine.setAutomationRecorder(&recorder)`, `engine.setMidiCaptureSink(&midiRecorder)`, `undoManager.setRestoreHooks(...)`, the panel's doc + `TrackHeaderHost`, the transport bar's `onRecordToggled`, and one initial publish so the audio thread starts from this document rather than the exchange's empty fallback. The destructor unwinds in the reverse order: stop listening, drop the panel's view, unhook the engine from both recorders (each unhook drains the audio callbacks — see the borrowed-pointer handshake above, which is what makes this safe while a host keeps rendering), `automationRecorder.detach()` (which commits anything in flight while the doc and undo manager are still alive), clear the restore hooks. `midiRecorder` needs no equivalent `detach()` — see the declaration-order note above.

**Track headers** call back into `MainComponent` through `synth::ui::TrackHeaderHost` — create/re-bind/delete `Track In` nodes, select one in the graph, and run any track edit as one undoable step. See [`docs/timeline_panel_core.md` §3](timeline_panel_core.md) for the chip semantics, the add-track rule and the never-auto-rebind rule.

**New Patch clears the timeline too**, as its own undo step: `GraphEditor::newPatch()` owns the graph's `recordStructuralChange`, and folding the timeline into it would mean nesting transactions. The timeline is cleared *first*, so the graph's step is the newer one — Cmd+Z brings the canvas back, Cmd+Z again brings the timeline back, and the post-restore reconcile re-derives the bindings after each.

#### Audio recording

Hook 5 above gained a second kind of take. The armed-track lookup now considers `TrackKind::Audio` as well, and **first-armed wins**: with one armed track of each kind, whichever comes first in the document decides which kind of take this is. There is deliberately no "record both at once" — that would be two takes, two commits and two undo steps for one gesture.

**The pipeline.** `RecordTapModule` (`Source/Modules/RecordTapModule.h/.cpp`, see [`docs/modules.md`](modules.md) for the module itself) is a transparent stereo pass-through with three threads behind it:

```
audio thread                writer thread (juce::TimeSliceThread)      message thread
processBlock ──push──▶ SPSC ring ──drain──▶ AudioFormatWriter (WAV)    startCapture / stopCapture
                    (interleaved,     └──▶ peak buckets ──▶ .agpk sidecar (on stop)
                     131072 frames)
```

- **Ring**: one interleaved `juce::AbstractFifo` of 131072 frames — 2.7 s at 48 kHz, 1 MiB of float storage for stereo, allocated once in the constructor. Sized so the writer thread can be descheduled for seconds without dropping a sample.
- **Overrun policy**: a full ring **drops** the samples that don't fit and sets a flag. The audio thread never blocks and never allocates. The take still commits, just short, and the flow surfaces `"Dropped audio during recording"` in the status bar.
- **Not `AudioFormatWriter::ThreadedWriter`**: that class is its own ring plus its own time-slice client, so stacking it on ours would mean two buffers, two overrun policies and two answers to "how long is the file". One ring, one writer, one counter.
- **Peaks** are accumulated during the drain (min/max per channel per 256 source samples) and flushed to `Peaks/<stem>.agpk` on stop, so waveform painting can draw the clip without re-reading the WAV. The format — and the accumulation math — now live in `synth::PeaksFile` (see below); `RecordTapModule` owns a `PeaksFile::Accumulator` and calls `PeaksFile::write()` at `stopCapture()`.

**The master tap.** `MainComponent::ensureMasterRecordTap()` finds or creates THE tap: a `Rec Tap` node spliced **in front of** the Audio Output node, with every audio connection that fed the output re-routed through it (MIDI connections, and anything on a channel the stereo tap doesn't have, are left alone). Creating it is **one compound undo step** (`recordCombinedChange`; only the graph domain actually changes). It is a singleton by construction — this function is the only thing that ever creates one — so a second take finds the tap already there and pushes no undo step.

**Take files.** In a saved project: `Audio/take-<n>.wav` + `Peaks/take-<n>.agpk` inside the bundle, `n` the first free number. In an unsaved one: `<app data>/<settings folder>/Recordings/`, with the reserved `Recordings/` ref prefix — see §5's asset policy; adopted into the bundle on the first save (see the "Asset management" section below).

**Punch-in is a trim, not a start.** The capture starts at the **Record-on click**, before any of the count-in's pre-roll — so the pre-roll bars are *recorded*, and excluded from the committed clip by the clip window instead. That replaces the original v1 behaviour, where the capture was started by the 10 Hz poll on the first tick at or after the punch and a take could therefore be missing **up to one poll interval (~100 ms)** of head while still claiming to start exactly at the punch.

`startCapture()` is called *after* the transport's `locateBeat`/`play` have been posted, deliberately: those take effect at the top of a block, and a frame captured before a locate belongs to the *old* position, which would break the one thing the anchor promises — that take frame `f` sits at `captureStart + f`. Starting after them can cost the one block that may already be in flight (~10 ms at 512/48 kHz), all of it pre-roll. (The same contiguity argument is why a **loop wrap** mid-take still mis-places a take: the transport's position is no longer monotonic across the take. Recording into a loop is not supported.)

#### Latency alignment

Two corrections, both applied at commit time; neither touches the audio path.

1. **A sample-honest anchor.** `RecordTapModule::processBlock` records the transport sample its *first captured block* started at (`BlockTimeInfo::blockStartSample`, read off the playhead on the audio thread) and reports it as `TakeResult::captureStartTimelineSample`. A take always begins at sample 0 of a block — the armed flag is read once at the top of `processBlock` — so `captureStartBlockOffset` is always 0 and is reported only so the arithmetic states its anchor in full. No transport behind the tap (a bare unit test, a foreign host) leaves the anchor invalid, and the commit falls back to the original placement.

2. **Round-trip compensation.** `AudioEngine::getRecordingLatencySamples() = getInputLatencySamples() + getGraphLatencySamples() + getOutputLatencySamples()` — report-only aggregation, exactly like each of its terms. The argument for that sum: **a musician plays against what they hear.** A click at timeline sample `G` leaves the speakers `output` samples after the graph rendered it, so the performer hears grid position `G` late by that much and plays *then*; the note travels back through the input device and reaches our callback a further `input` samples later, plus whatever the graph reports between its input node and the tap. Audio captured at `T` was therefore played at `T - (input + graph + output)`.

`synth::computeTakePlacement` (`Source/Timeline/TakePlacement.h/.cpp`) is the whole of that arithmetic as a pure function — it lives outside `MainComponent` so it can be asserted to the sample headlessly:

```
S0              = captureStart - recordingLatency        // where frame 0 was PLAYED
clipStartSample = max(punchSample, S0, 0)
trimFrames      = clipStartSample - S0                   // -> sourceStartSeconds
lengthFrames    = takeLength - trimFrames
```

The trim is expressed as `sourceStartSeconds`, never by rewriting the WAV: **the file keeps every captured frame — pre-roll included — and the clip window merely excludes them.** The clamp at 0 is what keeps a take recorded from beat 0 honest: the shift would put frame 0 at a negative timeline sample, so the clip stays at 0 and the remainder moves into `sourceStartSeconds`; the content never moves relative to itself, only the window onto it does. A take whose every frame precedes its punch (record disengaged during the count-in) commits nothing — the pre-roll WAV it already wrote is left on disk, unreferenced, exactly like the file behind an undone take. Inside a saved bundle, `synth::AssetManager::cleanUnusedAssets` can reap it later; in the unsaved-project `Recordings/` folder it is never auto-deleted at all — that sweep is bundle-internal only.

**The playhead is a different sum, and stays that way.** The playhead's drawn line offsets by the **output latency alone**, because it answers "where is the audio the user is *hearing* right now?" — not "where was this note played?". Recording compensation is the full round trip; the playhead is one leg of it. Pinned by `LatencyFlowTest.PlayheadUsesOutputLatencyOnlyNotTheRecordingSum`.

The round trip is surfaced in the status bar as `RT <n> ms` — see [`layout.md §4.1`](layout.md).

**Commit.** `commitAudioRecording()` is the single choke point, called by both the Record-off click and the poll's playing→stopped edge (exactly mirroring `commitMidiRecording()`): `stopCapture()`, then `computeTakePlacement`, then **one** `recordTimelineChange` that adds the clip and sets its asset. `startBeat`, `lengthBeats` (floored at 1/32 beat) and `sourceStartSeconds` all come from the placement. An empty take, or one that is all pre-roll, commits nothing and pushes no undo step. **Undo removes the clip; the file stays** — nothing auto-deletes a recording.

#### Device & sample-rate changes

**One consolidated hook.** `AudioEngine::handleStreamFormatChange(newRate, newBlockSize)` is called from BOTH `audioDeviceAboutToStart` (Standalone) and `prepareForHost` (Hosted) — the two places the engine's sample rate or block size can change while a project is open — instead of each path re-preparing its own consumers. **Order matters, and is fixed:**

1. **Transport first.** `transport.prepare(newRate, newBlockSize)` — every consumer below, and every module's *next* `processBlock`, must see the new rate consistently once this call returns. `TransportService::prepare()` already keeps the **beat** canonical and re-derives the sample-domain mirror from it, so **musical position survives untouched**: play a project to beat 4 at 48 kHz, switch to 96 kHz, and the transport still reads beat 4 — only `samplePosition` moves (it doubles, since the same beat now maps to twice as many samples). True whether the transport is playing or stopped. Pinned by `DeviceChangeTests.cpp`'s `MusicalPositionSurvivesRateChange_*`.
2. **Metronome reset.** `Metronome::resetVoices()` zeroes every ringing voice's `samplesRemaining`. A click spanning the boundary was computed for the OLD rate (`Metronome::startClick`'s `phaseInc`/`decayMul` are both functions of the sample rate active when the click started) — continuing to render it against the NEW rate's sample clock would make it audibly the wrong pitch **and** the wrong length. Silencing it is simpler, and no more of a discontinuity, than rescaling in place: the next beat crossing starts a fresh voice at the new rate exactly as normal.
3. **Streamer invalidate.** `AudioClipStreamer::invalidateAllStreams()` — see below.
4. **In-flight-take check.** Scans the graph for a capturing `RecordTapModule` and asks the registered `MidiRecorder` (via `midiCaptureSink_`) whether it is recording; either sets `formatChangedDuringCapture_` (a one-shot atomic, consumed by `consumeFormatChangedDuringCapture()`, same exchange-back-to-false contract as `consumeFeedbackGuardTripped()`).

Channel-count-dependent prep (`prepareDeviceScratch`, `prepareSliceScratch`, `prepareDeviceInputSnapshot`, the device latency caches) stays as separate calls in each of the two call sites, unchanged — those need `numInputChannels`/`numOutputChannels`, which vary by call site and aren't part of "format" (rate + block size) in the sense this hook consolidates.

**Rings self-heal on a miss, but a miss is not guaranteed — hence the explicit invalidate.** `TimelineAudioSourceModule::renderClip` recomputes a clip's `sourceFrame` from the engine's **current** sample rate every block (`sourceFrame = round(secondsIntoClip * info.sampleRate)`), so a rate change is a *discontinuity* in that mapping, not a gentle drift: the same beat position now asks the ring for a very different frame number. If that new frame number happened to fall inside the OLD ring's still-published window, `readFrames` would serve **real PCM data from the wrong position** — wrong content, not silence, because nothing about the window itself looks stale. `AudioClipStreamer::invalidateAllStreams()` closes that gap: it sets a `forceInvalidate_` atomic that (a) `readFrames` checks directly, forcing silence for every call until it clears, and (b) the prefetch thread consumes on its next slice — collapsing every open stream's window to its last-requested frame (`wantedFrame`, the same steering signal a normal miss already updates) before clearing the flag, and `moveToFrontOfQueue` wakes the prefetch thread immediately rather than waiting for its next scheduled nap. Splitting the guarantee this way — the audio-thread-visible flag for correctness, the prefetch-thread-only window mutation for the actual refill — is what lets `invalidateAllStreams()` be called safely from the prepare path (not the audio thread, not the prefetch thread) without ever touching the window atomics directly from a third thread. Pinned by `DeviceChangeTests.cpp`'s `StreamerRefillsAtNewMappingWithoutGarbage`: silence immediately after the change, then (after the paused prefetch thread is pumped) the first non-silent block matches the file at the **new** mapping exactly.

**A take cannot span a format change.** Neither half of a take is honest across one: an audio take's WAV has a **fixed header rate**, set once at `startCapture()` — continuing to record across the boundary would silently mix two real sample rates under one declared one. So a take is **finalized at the change boundary** rather than allowed to continue: `handleStreamFormatChange`'s step 4 sets `formatChangedDuringCapture_`, and `MainComponent::timerCallback()`'s 10 Hz poll consumes it and routes through the exact same choke points a manual Record-off or a transport-stop edge already use (`commitAudioRecording()` / `commitMidiRecording()`), plus `statusBar.showMessage("Recording stopped: audio device changed")`. This mirrors the existing "commit on stop" checks in shape, but needs its own condition: the transport typically keeps **playing** right through a format change (nothing about `prepare()` touches the `playing` flag), so the stop-edge checks would never fire on their own.

**The poll commits; the AUDIO side stops at the boundary itself.** A 10 Hz poll is up to ~100 ms late, and every block rendered in that window is new-rate audio the tap would otherwise append to an old-rate WAV. So the stop is split in two: `RecordTapModule::prepareToPlay` — which the graph calls for every node on both format-change paths — latches `captureHalted_` the moment the prepared rate stops matching the rate the take was armed at (`captureSampleRate_`, stored by `startCapture()` before arming), and `processBlock` reads that latch beside the armed flag and stops pushing. Deliberately **not** by clearing `capturing_`: the take is still the message thread's to commit, and `stopCapture()` no-ops on a disarmed tap, so clearing it would lose the take entirely. The commit flow above is unchanged — it just finalizes a file that already ended at the boundary. Pinned by `RecordTapTests.cpp`'s `PrepareAtANewRateStopsCaptureAtTheBoundary` (a re-prepare at the *same* rate, i.e. any ordinary graph rebuild, must not halt anything) and `DeviceChangeTests.cpp`'s `AudioTakeCapturesNothingAfterTheRateBoundary`.

The WAV itself needs no correction — it was recorded at its own (pre-change) rate and nothing here touches it. What *does* need correcting is the **commit math**: `computeTakePlacement` converts sample-domain anchors (`captureStartTimelineSample`, the take's `recordingLatencySamples`) to beats using a `sampleRate`/`bpm` pair, and if that pair is read **live** off the transport/engine at commit time (as it used to be, since rate never used to change mid-take), a take finalized after a format change would silently divide an OLD-rate sample count by a NEW-rate samples-per-beat — wrong by exactly the rate ratio. The fix: `MainComponent::AudioTake` now freezes `captureSampleRate`/`captureBpm`/`captureRecordingLatencySamples` at **record-on**, not at commit, and `commitAudioRecording()` reads the frozen fields instead of the live transport snapshot. This is a no-op for the overwhelming common case (rate never changes during a take, so frozen == live throughout) and the correctness fix for the case that changed. A MIDI take needs no equivalent fix: `MidiRecorder`'s captured events are stored purely as **beats** (computed from the block's `BlockTimeInfo` at capture time, which is always in the canonical beat domain regardless of what the sample rate happens to be that block), so nothing about a MIDI commit is rate-dependent in the first place. Pinned by `DeviceChangeTests.cpp`'s `AudioTakeCommittedAtFormatChange` (reproduces `computeTakePlacement` independently from the frozen pre-change values and asserts the committed clip matches — a live-value regression fails this exact comparison) and `MidiTakeCommittedAtFormatChange`.

**Duplex refusal's reachable half.** `AudioEngine::initialiseDevices` always requests 0 input channels as the fallback floor, so a saved device state that cannot be opened (or that never pinned an explicit input count) yields a **working, output-only** engine rather than a failed one — headless JUCE can't open a real device to prove the full restore path, but `audioDeviceAboutToStart` with a `FakeAudioIODevice` reporting **zero** active inputs while `AudioInputModule` was built expecting more exercises the reachable half directly: no crash, `AudioInputModule::getVisibleOutputPortCount()` still floors at 1 (`visibleFor()` already clamps into `[1, kMaxChannels]` regardless of the device's count), the input-monitoring gate stays safe (nothing to copy, so every path clears the buffer), and the callback with 0 input channels renders clean silence. Pinned by `DeviceChangeTests.cpp`'s `ZeroInputDeviceSurvives`.

**UI refresh.** `MainComponent`'s existing device-state-changed callback already calls `graphEditor.refreshIoModulesAfterDeviceChange()` on any device change; nothing new is needed there. The lane area's cached waveform **peaks are source-sample-based** (bucketed from the file's own samples via `PeaksFile`, never the engine's sample rate) and are deliberately **not** invalidated on a rate change — a naive port of "invalidate caches on device change" here would be wrong, not merely wasteful. The status bar's `RT <n> ms` readout needs no special handling either: it already reads `getRecordingLatencySamples()` and the transport's *current* sample rate fresh on every poll tick, so it reflects the new rate on its very next 5 Hz update with no cache to invalidate.

#### Waveform peaks and clip rendering

**`synth::PeaksFile` (`Source/Timeline/PeaksFile.h/.cpp`) is the single place that knows the `.agpk` format** — read AND write. It was factored out of `RecordTapModule`, which originated the format and now delegates to it rather than keeping a second implementation: `RecordTapModule` owns a `PeaksFile::Accumulator` (the same bucket math — min/max per channel every `bucketSize` source samples, a short final bucket — just no longer duplicated), the writer thread's drain step calls its `addSamples()`/`flushPartial()`, and `stopCapture()` calls `PeaksFile::write()`. `PeaksFile::kMagic`/`kVersion` are what `RecordTapModule::kPeaksMagic`/`kPeaksVersion` now alias, so every file ever written by this build still parses unchanged. `PeaksFile::read()` is tolerant of a musically-short final bucket (that's the format, not a defect) but rejects anything structurally broken: bad magic/version, a zero bucketSize/numChannels, or a payload that isn't a whole number of (min,max) pairs forming whole buckets.

**Waveform painting** (`synth::ui::TimelineClipLaneArea::paintWaveform`) renders a committed audio clip (non-empty `assetRef`, wider than `kMinWidthForWaveform`) as one drawn line pair per pixel column, sampled from whichever buckets the clip's span covers. `TimelineClipLaneArea::bucketRangeForClip()` is the pure geometry behind that: given `sourceStartSeconds` and the transport's bpm (to convert the clip's beat length to seconds) and sample rate (to convert seconds to source samples — the peaks file itself carries no sample rate, the same "engine rate, no resampling" honesty `AudioClipStreamer` already states for playback), it returns the `[firstBucket, firstBucket + bucketCount)` window into `PeaksFile::Data::buckets`. Peaks are cached by assetRef (`std::map<juce::String, PeaksFile::Data>`), loaded lazily on first paint through a host-supplied resolver (`std::function<juce::File(const juce::String&)>`) — `MainComponent` wires this to `AudioClipStreamer::resolveAssetRef()`, the SAME resolution playback uses, re-targeted at the `Peaks/` sidecar via a small ref transform (`Audio/take-n.wav` → `Peaks/take-n.agpk`; `Recordings/take-n.wav` → `Recordings/take-n.agpk`, since `chooseTakeFiles()` points an unsaved project's audio and peaks at the same folder). **Cache policy:** any doc mutation (`refreshFromDoc()`) clears the whole cache rather than diffing which assetRefs actually changed — peaks files are small, so a cold re-read is cheap and this avoids per-ref dirty-tracking that isn't worth building yet. `invalidatePeaksCache()` is the public escape hatch for a resolver whose target moved without a doc change.

**The live-recording strip.** While an audio take is in flight, the armed track's lane shows a growing translucent strip from the punch beat to the transport's current position (zero-width, i.e. nothing drawn, while a count-in pre-roll is still rolling *before* the punch), with a live waveform sourced from `RecordTapModule::copyLivePeaks()` — a message-thread, lock-guarded snapshot of the SAME `PeaksFile::Accumulator` the writer thread is still appending to (`peaksLock_`, held only for the copy/append, never touched by the audio thread). `MainComponent::timerCallback()`'s existing 10 Hz poll calls `TimelineClipLaneArea::updateLiveRecording()` alongside its other polled updates (gated on `timelinePanel.isVisible()`, same as `updateFromTransport()`); that method repaints the strip's dirty rect **only when the copied bucket count actually grew** since the last call — never merely because the transport tick moved the strip's right edge — which is the "repaint on data arrival" reading of the animation/repaint rules in this file's UI section. Because a completed bucket only flushes once `kPeakBucketSize` (256) source samples have accumulated, the strip updates in those quanta (a few ms of audio at session rates), not sample-by-sample.

### AudioClipStreamer (disk-streaming clip playback)

`Source/Timeline/AudioClipStreamer.h/.cpp`. The engine-owned service behind [`Track Audio`](modules.md) clip playback: one shared prefetch thread keeps a per-clip ring filled ahead of the playhead, and the audio thread only ever copies out of those rings. **Nothing ever holds a whole file** — a ten-minute take costs one ring, ~1 MiB. That is the point, and it is the deliberate opposite of `SamplerModule`'s whole-file-in-RAM model.

```
message thread            prefetch thread (one TimeSliceThread)        audio thread
  setAssetRoots()           applyPendingAssignments()                   acquire(clipId)
  syncToSnapshot()  ──────▶   open / close AudioFormatReaders   ──────▶ readFrames(...)
   (assignment table,          serviceStream(): reposition / top up      (ring only; never
    under a lock)              towards wanted + 3/4 ring                  blocks, allocates
                                                                          or touches a file)
```

**Thread ownership is the whole design.** The prefetch thread owns every `juce::AudioFormatReader` *exclusively* — opening, reading and closing all happen there. The message thread never touches a reader, a ring or a window atomic: `syncToSnapshot()` writes an **assignment table** (`{clipId, resolved juce::File, sourceStartSeconds}` per slot) under a `juce::CriticalSection`, and the prefetch thread copies it at the top of its next slice and acts on the difference. That is what makes "never delete a reader the prefetch thread may be using" true *by construction* — there is no retire list because no reader is ever visible to two threads at once. `AudioEngine::shutdown()` (and the destructor) call `releaseAll()`, which stops the thread **first** and only then frees; the same precondition `TimelineSnapshotExchange::reclaimAllUnsafe()` has.

**The ring is a sliding window, not a FIFO.** `kRingFrames = 1 << 17` interleaved stereo frames (~2.7 s at 48 kHz, 1 MiB), with the slot for source frame `f` fixed at `f & (kRingFrames - 1)`. Two atomics say what is readable: `ringStartSourceFrame` (first servable frame) and `ringEndSourceFrame` (one past the last). A `juce::AbstractFifo` — the house style in `RecordTapModule` and `MidiRecorder` — is deliberately *not* used here, and the reason is the seek: a FIFO's read cursor belongs to the consumer, so repositioning after a locate would need **both** threads to mutate it, and every scheme for that ends in a handshake the audio thread has to join. With a fixed slot mapping the prefetch thread is the sole writer of both window atomics and the audio thread mutates nothing, so a seek is two ordinary release stores.

**Fill ordering (load-bearing).** To append frames `[end, end + k)` the prefetch thread:

1. computes `newStart = max(start, end + k - kRingFrames)` — the oldest frame still intact once those slots are overwritten;
2. `ringStartSourceFrame.store(newStart, release)` — **the window shrinks BEFORE a byte is overwritten**;
3. writes the slots;
4. `ringEndSourceFrame.store(end + k, release)` — **frames are marked valid LAST**, so a reader that has seen the new end has, by release/acquire, seen the samples behind it.

A **reposition** is the same shape with the window collapsed first: `ringEnd` at the new position (which empties the window, because readability is gated on the end), then `ringStart`, and only then filling. Invalidate → reposition → fill, always.

Filling never goes past `wantedFrame + kPrefetchAheadFrames` (3/4 of the ring), so step 1 can never move `newStart` past `wanted - kRingFrames/4`: the quarter-ring of history behind the playhead is structurally safe. On top of that, `readFrames` re-reads **both** window atomics after copying and zeroes its output if the window moved under it — one extra pair of loads that turns "silence, never garbage" from an argument about timing into a property of the code.

**Steering.** There is no seek call. `readFrames(handle, sourceFrame, ...)` stores `sourceFrame` into the stream's `wantedFrame` — unconditionally, including on a miss, because a miss is exactly when the prefetch thread most needs to know where playback went. The prefetch thread compares `wanted` against the window each slice: outside it (a locate, a loop wrap backwards, a forward jump) → reposition; inside it → top up towards `wanted + kPrefetchAheadFrames`.

**Offline priming.** Steering works because playback asks *before* it needs the audio and can afford a miss; an offline render can do neither — it produces blocks faster than any disk fills a ring, and the prepare it starts with has just invalidated everything. `waitUntilPrimed(beat, bpm, sampleRate, framesAhead, timeoutMs)` is its handshake: on the **message thread**, it computes each open stream's target frame for `beat` (`sourceFrameForClipBeat`, clamped into the clip's own span so a clip that has not entered yet is primed at its trim point), publishes those as `wantedFrame`, and blocks until every ring covers `[target, target + framesAhead)` — waking the prefetch thread and waiting on the event it signals at the end of each slice. It returns false on timeout, which the caller counts as a dropout. Two constraints: it writes `wantedFrame`, which belongs to the audio thread during playback, so it is legal **only while nothing is rendering**; and with the prefetch thread paused it pumps synchronously on the calling thread instead of waiting for a thread that cannot run. The realtime `readFrames` path is untouched — priming adds no lock, no allocation and no branch to it.

**Rings are allocated lazily**, per slot, on first use, and then never freed or moved — which is what makes the ring pointer safe to publish once and read forever. An engine whose session has no audio clips costs **no** ring memory. Mono files are up-mixed to stereo at fill time and files with more than two channels contribute their first two, both inside `juce::AudioFormatReader::read` (which also converts integer formats to float).

**Publication token.** A slot's `clipId` is stored **last**, with release, after its reader, ring and collapsed window are in place; `acquire()` acquire-loads it. A slot assigned to a clip whose file will not open keeps the id but leaves `ready == false`, so introspection can tell "no stream" from "a stream that cannot play" while the audio thread gets silence either way.

**Asset roots and the escape refusal.** `setAssetRoots(bundleRoot, recordingsRoot)` (message thread; either may be invalid). A ref starting with the reserved `Recordings/` prefix resolves against the directory *containing* the Recordings folder — exactly the form `MainComponent::chooseTakeFiles` stores for an unsaved project (see §5's asset policy) — and everything else against the bundle root. Every ref is re-checked with `TimelineDoc::isValidAssetRef` (relative only, no `..`, no leading separator, no drive letter) **and** the resolved file must still be `isAChildOf` its root: this is the layer that actually opens a file, and "the document validated it" is not a property it should assume when a ref can arrive from a hand-edited bundle. Anything unresolvable, escaping or missing simply gets **no stream**, and therefore silence — `synth::ui::TimelineClipLaneArea`'s missing-media placeholder (see the "Asset management" section below) is what makes that visible in the UI rather than a clip that silently plays nothing. `MainComponent::refreshAssetRoots()` is called wherever `currentBundleDir_` changes (project open, project save, New Patch) and once in the constructor before the first publish. On the open path it runs **before** `ProjectBundle::load`, not after: the load moves the timeline into the live doc, which fires `timelineChanged` synchronously and publishes to the streamer while the load is still running — with the old roots installed, the new bundle's refs would transiently resolve inside the *previous* bundle. A failed load restores the previous bundle dir and roots, since `load()` is all-or-nothing.

**Pool cap policy.** `kMaxStreams = 32`. `syncToSnapshot` **keeps** slots whose clip is still wanted with the same file (so editing one clip never re-seeks the other thirty-one) and fills what is left in **document order** (track order, then clip start order); clips past the cap get no stream and are silent. v1 is deliberately not playhead-aware — "furthest from the playhead loses" needs a position the message thread does not have at publish time, and would make *which* clip is silent depend on when the user last edited the document. It is silent, not logged: this runs on every doc edit, and a log here is exactly the per-edit spam `CLAUDE.md` forbids.

**Engine wiring.** `AudioEngine` owns `clipStreamer_` (declared before the graph, like the transport and the exchanges, so nodes are destroyed before the thing they read). `publishTimeline()` calls `syncToSnapshot()` with the **same snapshot object** it publishes, *before* publishing it — so a clip the audio thread is about to see either has a stream already opening or is one the streamer deliberately declined. `renderPass()` installs the pointer on the transport carrier beside the snapshot (`TransportService::setAudioClipStreamer`); unlike the snapshot it is not per-block (the streamer outlives any snapshot), but it is set there so the two always arrive together.

**The deterministic test pump.** `setPrefetchPausedForTest(true)` stops the service from ever starting its thread; `pumpForTest()` then runs slices **synchronously on the calling thread** until nothing is left to do, and returns the slice count. Tests therefore have no sleeps and no "eventually the ring fills" waits: publish → pump → render → assert, and the render loop's per-block callback pumps between blocks to stand in for the background thread. `Tests/AudioClipPlaybackTests.cpp` is written entirely against this, which is what lets it assert **bit-exact** sample content rather than RMS windows.

### Asset management

`Source/Timeline/AssetManager.h/.cpp` (`synth::AssetManager`) is a stateless bag of static functions — headless, message-thread-only, no GUI dependency — that closes out the asset lifecycle audio recording, clip streaming and waveform rendering opened: import-into-bundle, a missing-asset placeholder + relink flow, a collect/clean pass for files no clip references, and the `Recordings/` adoption sweep that resolves `ProjectBundle`'s audio-recording TODO. The one invariant every function shares: **never a silent delete.** Nothing is removed except the exact set `cleanUnusedAssets` names, and a clip whose asset is simply *missing* never triggers a deletion anywhere.

**Import + dedupe.** `importAudioFile(source, bundleRoot, error)` sniffs `source` with a `juce::AudioFormatManager` (rejecting anything that isn't a readable audio file, with `*error` explaining why) and copies it into `<bundleRoot>/Audio/` under a collision-free name — `name.wav`, `name-2.wav`, ... — reusing an already-present same-named file instead of writing a second copy when its content is **identical** (same size, then a whole-file FNV-1a-64 hash — cheap and streamed via `juce::FileInputStream`, deliberately not a cryptographic hash: this is dedupe bookkeeping, not a security boundary). The source is never moved or deleted. `importAudioFileToDirectory(source, destDir, error)` is the same primitive targeting an arbitrary directory rather than `<bundleRoot>/Audio/` — what the relink flow's unsaved-project path needs (see below), and what `importAudioFile` itself is a thin wrapper over.

**Missing-asset placeholder.** `synth::ui::TimelineClipLaneArea` already paints a committed audio clip's waveform via its peaks cache; this adds a second, existence-aware resolver seam — `setAssetExistsResolver(std::function<bool(const juce::String&)>)` — which `MainComponent` wires to `AudioClipStreamer::resolveAssetRef(ref) != juce::File()`, the SAME resolution playback and the peaks resolver use. A clip whose asset does not resolve gets a diagonal-hatch-over-dimmed-fill treatment (`paintMissingAssetPlaceholder`, theme-token colours via the usual `dynamic_cast<AppLookAndFeel*>` pattern) plus a `"missing: <name>"` label when the clip is wide enough, instead of the (impossible) waveform. The existence answer is cached per assetRef right alongside `peaksCache_` (`assetExistsCache_`), cleared at exactly the same two points (`refreshFromDoc()`, `invalidatePeaksCache()`/`setAssetExistsResolver()`) — so a repeated paint of a still-missing clip never re-stats the filesystem. No resolver installed → assumed to exist (no placeholder), the same degrade-gracefully contract every other host seam on this class has.

**Relink flow.** The audio-clip context menu gains **"Relink audio…"**, offered whenever `assetRef` is non-empty (missing OR present — relinking a present asset to a different file is just as legitimate as fixing a missing one). Unlike Split/Duplicate/Delete this is a plain callback (`TimelineClipLaneArea::onRelinkAudioRequested`) rather than a `ClipContextChoice`: relinking needs a host `juce::FileChooser` and an `AssetManager` import, neither of which the lane area has. Production: `MainComponent::promptRelinkClipAsset` opens the chooser and calls `relinkClipAsset(id, chosenFile)`; headless: `MainComponent::relinkClipAssetForTest(id, chosenFile)` calls the same function directly, bypassing the dialog. `relinkClipAsset` imports the chosen file — via `importAudioFile` into the current bundle, or via `importAudioFileToDirectory` into the app-data `Recordings/` convention when the project has never been saved — then rewrites `assetRef` on the clicked clip **and every other clip that shared its old ref**, as **ONE** undo step: every affected clip id + its own `sourceStartSeconds` is snapshotted first (a `TimelineDoc` reference does not survive a mutation), then a single `AppUndoManager::recordTimelineChange` batches one `setClipAsset` call per clip. The old file is never touched.

**Collect / clean (bundle-internal only).** `collectUnusedAssets(doc, bundleRoot)` walks `<bundleRoot>/Audio/` and reports every file (as a bundle-relative ref) that no clip in `doc` references, and `cleanUnusedAssets(doc, bundleRoot)` deletes exactly that set plus each file's `<bundleRoot>/Peaks/<stem>.agpk` sidecar, returning the count. A clip whose ref names a file that isn't actually on disk contributes nothing to the scan (there's no file to enumerate), so a missing ref can never cause anything else to be misclassified as unused or deleted. `Recordings/` is out of scope entirely — this pass never looks outside `bundleRoot`. Surfaced as `MainComponent::cleanUnusedAssets()` / the test hook `cleanUnusedAssetsForTest()`; **deliberately not wired to any menu, command or shortcut yet** — doing so would add a new `AppCommands` entry with no default binding, which only `checkForUpdates` does today (a macOS-only, Sparkle-convention exception `ShortcutManagerTest.CommandManagerHasCommands` special-cases explicitly), and extending that exception to every platform for a first cut of this feature was judged not worth the invariant surgery. The manager method + test hook exist and are ready for whichever surface (a future timeline-panel menu row, most likely) picks this up.

**`Recordings/` adoption on save.** `adoptRecordingsAssets(doc, recordingsRoot, bundleRoot)` is what `MainComponent::saveToFile` runs immediately **before** `ProjectBundle::save` on the `.agsproj` path: every clip whose `assetRef` carries the reserved `Recordings/` prefix (the unsaved-project convention) gets its file imported into `bundleRoot`'s own `Audio/` (deduped exactly like any other import — a take shared by several duplicated clips is imported once), its `.agpk` peaks sidecar copied alongside when one exists, and every clip sharing that old ref rewritten to the new one — all as **plain, direct** `TimelineDoc::setClipAsset` mutations, deliberately **NOT** wrapped in `recordTimelineChange`: saving must never create undo history. A ref whose source file is no longer on disk, or that fails to import, is left untouched (still resolvable exactly as before, or already the missing-asset case above). Resaving is stable: once a ref has been rewritten to `Audio/...` it no longer starts with `Recordings/`, so a later save's adoption pass has nothing left to do with it, and the sidecar copy checks the destination first so it is never re-copied or clobbered. The original `Recordings/` file is **never deleted** by this pass — nothing here deletes anything; that's `cleanUnusedAssets`'s job, and its scope is bundle-internal only, so a `Recordings/` file is never swept either. `docs/layout.md §16` documents the menu row this flow adds.

## Plugin Layer

`Source/Plugin/` wraps the same `AudioEngine` and `MainComponent` the standalone app runs in a `juce::AudioProcessor` (`AgentSynthAudioProcessor` / `AgentSynthPluginEditor`), producing the VST3/AU targets described in Project Structure above.

### Host modes (`AudioEngine::HostMode`)

- **`Standalone`** — `AudioEngine` owns a `juce::AudioDeviceManager`, opens the default output device and every available MIDI input, and is clocked by its own `audioDeviceIOCallbackWithContext`.
- **`Hosted`** — the only mode `AgentSynthAudioProcessor` uses. `initialise()` opens **no** audio device and **no** MIDI input — it only builds the initial patch. The host drives the graph instead, through a mirror of the device-callback trio: `prepareForHost(sampleRate, blockSize, numIn, numOut)` (from `prepareToPlay`), `processHostBlock(buffer, midi)` (from `processBlock`), `releaseFromHost()` (from `releaseResources`). Opening a device from inside a plugin would fight the host for the hardware; opening MIDI input directly would double-trigger notes the host already forwards.
- Both modes funnel through one private `AudioEngine::renderNextBlock`, which runs `renderPass` (transport tick, timeline snapshot, MIDI capture, automation, then `mainProcessorGraph.processBlock`) and then zero-fills on master-mute — the single choke point that keeps mute semantics from drifting between the two paths.

### Who owns what

- **AudioEngine** — owned by `MainComponent` (`ownedAudioEngine`) on the standalone path; owned by `AgentSynthAudioProcessor` and *injected* into `MainComponent` by reference on the plugin path (`MainComponent(tm, lf, AudioEngine&, ...)`). `MainComponent::initialiseCommon` skips `audioEngine.initialise()`/`shutdown()` whenever it doesn't own the engine, so opening/closing the plugin editor never re-initialises or tears down the running graph — only the processor's constructor/destructor call `initialise()`/`shutdown()`.
- **ThemeManager + AppLookAndFeel** — owned by `AgentSynthAudioProcessor`, not by the editor. A host may create and destroy `AgentSynthPluginEditor` many times over one plugin instance's life (every time its window is closed and reopened), and the LookAndFeel must outlive every `Component` that references it. `PluginProcessor.h` declares `themeManager`/`lookAndFeel` **before** `engine` specifically so they are destroyed *after* it and after any editor (which the base `AudioProcessor` tears down first) — the same shutdown-order guard `Main.cpp` uses for the standalone `AppApplication`.
- **LookAndFeel scope** — `AgentSynthPluginEditor` calls `setLookAndFeel(&processor.getLookAndFeel())` on itself and clears it in its destructor. It never calls `Desktop::setDefaultLookAndFeel`, which is process-global inside the host and would re-skin the host's own windows and every sibling plugin.
- **Settings window** — `MainComponent` passes `showAudioTab = !audioEngine.isHosted()` to `SettingsWindow`, which omits the Audio device tab in the plugin: the host owns the device, so an `AudioDeviceSelectorComponent` there would be inert at best, and dangerous if the user touched it.

### Plugin state format

`AgentSynthAudioProcessor::getStateInformation` / `setStateInformation` serialize a small JSON envelope — `stateVersion`, `patch`, `editorWidth`, `editorHeight`. The `patch` value is exactly `AIStateMapper::graphToJSON`'s output, the same shape a `.json` preset file uses, so plugin session state and preset files stay interchangeable; `setStateInformation` also accepts a bare patch object with no envelope, so a raw preset dropped straight into a host's state slot still loads.

Restore always calls `applyJSONToGraph(..., trusted=false)`: a host session file travels between machines and users, so it goes through the full `validatePatch` boundary (see [`docs/AI_Engine.md`](AI_Engine.md)) and is rejected whole — never partially applied — if it doesn't check out. Around the load, an open editor detaches its module components first (`prepareForGraphReplacement`) and rebuilds them after (`refreshAfterGraphReplacement`) — the same detach-before-clear ordering `GraphEditor::loadPreset` and `MainComponent::aiPatchAboutToApply` use to avoid a `ScopeComponent` timer firing against a freed `VisualBuffer`.

### Plugin hosting — third-party VST3/AU *inside* our graph

The mirror image of the section above: `Source/Plugin/Hosting/` is the app **hosting** other people's plugins, not being hosted. It lives in **Core** (not in the `AgentSynthPlugin` target), so the headless Tests target exercises it.

**The licensing decision:** JUCE's built-in hosting only — VST3 everywhere, AU additionally on macOS. No new dependency pins, and therefore no new licences to clear. **CLAP is deferred**: it would require vendoring the CLAP headers or `clap-juce-extensions`. The two formats are enabled as Core `PUBLIC` compile definitions in the root `CMakeLists.txt` (`JUCE_PLUGINHOST_VST3=1`, and `JUCE_PLUGINHOST_AU=1` under `if(APPLE)`) — `PUBLIC` because the format list is compiled from them and every consumer must agree on the values.

The format set itself is declared **once**, in `synth::addHostedPluginFormats()` (with `hostedPluginFormatNames()` reading the names back off the format objects). `DefaultHostedPluginBackend`, the scanner's default candidate source and the `--scan-plugin` child process all go through it, because hosting and scanning must agree: a format the scanner walks but the backend cannot instantiate produces a library row that always fails to load, and the reverse produces a plugin the user can never find.

#### `synth::HostedPluginBackend` — the seam

`Source/Plugin/Hosting/HostedPluginBackend.h`. An abstract "identity or description in, `juce::AudioPluginInstance` out, asynchronously" interface. It exists for two reasons:

1. **Format-agnosticism** — `HostedPluginModule` never mentions VST3 or AudioUnit, so adding CLAP later is a change to the backend, not to the module.
2. **Testability without third-party binaries** — there is no plugin we can check into this repo and load in CI. `Tests/StubPluginInstance.h` provides a `juce::AudioPluginInstance` subclass and a `StubBackend` that resolves any identity to it, and it deliberately matches the real threading: `createInstanceAsync` is called on the message thread and its callback fires on the message thread **later**, never re-entrantly (JUCE's own `AudioPluginFormat::createPluginInstanceAsync` contract). Tests therefore pump the message loop exactly as they would with a real plugin.

`HostedPluginBackend::getDefault()` is the process-wide backend (`DefaultHostedPluginBackend`, owning a `juce::AudioPluginFormatManager`). **This is the seam `HostedPluginModule::setExtraState` needs**: state restore happens deep inside `AIStateMapper::applyJSONToGraph`, which has no backend to plumb down, so the module reaches for the default. `HostedPluginBackend::ScopedDefault` is an RAII override tests install for the duration of a scope, restoring the previous backend on destruction so a failing test cannot leak a dangling stub into the next one.

`PluginIdentity` (format + `uniqueId` + name, **never a path**) is the serialized form; a full `juce::PluginDescription` is the other entry point. Identity → description resolution goes to the `PluginScanService` the owner installed via `setScanService()` (below); with none installed it falls back to an explicitly-set `knownPlugins_` vector, empty by default — so a serialized identity fails to resolve with "not installed on this machine" and the module stays a valid placeholder. The owner must clear the pointer before destroying the service; both owners' destructors do, guarded on the installed service still being their own.

#### The async publish pattern

The [Sampler](modules.md#sampler-module)'s retained-instance discipline, applied to a whole `AudioProcessor`:

1. Message thread starts an async load, bumping a generation counter so a callback from a superseded load cannot clobber a newer one. The module holds a `juce::WeakReference` to itself, so a callback arriving after the module dies is a no-op.
2. On callback (message thread): refuse anything wider than 16 in or out; otherwise `setPlayConfigDetails` + `prepareToPlay` to **our** rate and block, then apply any pending state blob — both **before** publication, so the audio thread never sees an unprepared instance or one block of the plugin's factory default.
3. Retire the previous instance into a message-thread-only list, then `store(release)` the new pointer. The audio thread `load(acquire)`s it **once per block and never caches it across blocks**.
4. Reap on the message thread only. A block counter, bumped on *every* path out of `processBlock` (including bypass, so reaping still progresses in a bypassed patch), tells the message thread when the audio thread has demonstrably moved on; retired instances are freed two blocks after retirement. The reap at retire time can never free what it just retired (the counter has not moved yet), so a retire while prepared also schedules a short message-thread re-reap — without it the most recently retired instance stays resident until the next load, unload or `releaseResources`. **Nothing is ever deleted on the audio thread** — pinned by `HostedPluginTest.AudioThreadNeverFrees`, which renders on a second thread while the message thread swaps instances and asserts every destructor ran on the message thread.

#### DAW-session state round-trips too

`AgentSynthAudioProcessor::setStateInformation` validates with `trusted=false` **and `allowInternalModuleTypes=true`** (see [Plugin state format](#plugin-state-format)) — the authorship restriction exists to stop *model output* naming internal types, and a host session file is our own saved graph, so the gate accepts "Hosted Plugin" nodes there while still rejecting a tampered file whole. The subsequent apply is trusted, which is what carries the plugin identity and its state blob. So a patch hosting a plugin round-trips through presets, undo/redo, `.agsproj` bundles **and** a DAW session with AgentSynth running as a plugin — pinned end-to-end by `HostedPluginTest.HostedPluginSurvivesDawSessionStateRoundTrip`.

#### Plugin scanning — a crash must kill a child, not the app

`Source/Plugin/Hosting/PluginScanService.h`. Owns the `juce::KnownPluginList` + blacklist that answers "which binary is this identity?" — and is therefore the only place a plugin path is stored (see [`modules.md § Hosted Plugin`](modules.md#hosted-plugin-module-third-party-vst3--au-hidden) for the resolution precedence and the load UX).

**The child-process design.** Scanning means loading a stranger's binary and calling into it, and plugins that crash, hang, or pop a modal window on probe are common enough that in-process scanning turns one bad plugin into an unrecoverable crash-on-launch. So:

1. The scan thread re-launches **our own executable** (`File::getSpecialLocation(currentExecutableFile)`) with `--scan-plugin <format> <fileOrIdentifier> <token>`, capturing stdout only — a plugin's stderr chatter stays on ours instead of interleaving into the document. `token` is fresh per launch (`PluginScanService::makeScanToken()`).
2. The child runs `synth::runPluginScanChildMode()` **before the application object exists**: it scans that one plugin into a throwaway `KnownPluginList`, prints `createXml()` between the `<<<AGENTSYNTH-SCAN-BEGIN:<token>>>>` / `<<<AGENTSYNTH-SCAN-END:<token>>>>` sentinels, and exits 0/1 (a missing or non-hex token is a bad-arguments exit). No window, no engine, **no settings file** — a child touching the settings file would race the parent that spawned it.
   The sentinels are not just anti-corruption. The plugin under scan runs *inside* that child and can print whatever it likes, so the parent accepts only blocks stamped with the token it issued, and only the **last** of those — anything forged while the plugin loads was printed before the real document the child emits on its way out. Take the first block instead and a plugin can write its own entry, path and all, into the parent's list.
3. `readAllProcessOutput()` blocks until the pipe closes, which is the hang we are guarding against, so a **watchdog thread** kills the child on the deadline (default 15 s — generous on purpose: a cold-cache VST3 can honestly take ten seconds, and killing a slow-but-honest plugin blacklists it for good). Reading on the scanning thread rather than the watchdog keeps the pipe drained, so a chatty plugin cannot deadlock by filling the buffer.
4. A crash, a timeout, a non-zero exit and "described nothing" are indistinguishable from here and all get the same response: **blacklist the candidate and continue** with the next one.

**The entry point.** `Source/Main.cpp` hand-rolls `main()` rather than using `START_JUCE_APPLICATION`, so the intercept happens before a `JUCEApplication` is ever constructed — otherwise a scan of 50 plugins bounces 50 Dock icons and each child pays for an `NSApplication` it never uses. Windows GUI builds have no `argv` at their entry point, so they keep JUCE's `WinMain` and intercept as the first statement of `initialise()` instead (JUCE's own AudioPluginHost does the same); both call the same Core function. **Plugin builds of ourselves never scan**, so there is no entry point to intercept there.

**The three injectable seams**, which is what makes any of this testable with no plugin binaries in the repo: `CandidateSource` (what to scan — the default asks each format for its own search paths, which is machine-dependent), `ChildLauncher` (how to scan one — a test returns canned XML for a "good" plugin and `false` for a "crashing" one), and `setScanTimeoutMs`. `Tests/PluginScanTests.cpp` drives everything above them through those three.

**Threading and ownership.** `scanAsync()` runs the whole scan on one background thread and posts progress/completion to the message thread; every read of the list is mutex-guarded, so the UI can query mid-scan. The destructor cancels and joins, and posted callbacks carry a shared liveness flag. Persistence is the **owner's** job — Core never touches `juce::ApplicationProperties`: the owner loads the list from the `"pluginScanList"` user setting, installs the service on the default backend, and saves `toXml()` (list **and** blacklist) after each scan. Same owner-drives-persistence shape as the audio device state. Both owners open the settings file through `synth::userSettingsOptions()` (`Source/UserSettings.h`), never a local copy of the fields.

**Two owners, one slot.** In the standalone app the owner is `MainComponent`. In a plugin build it is **`AgentSynthAudioProcessor`**, which restores the list and installs the service in its own constructor: `setStateInformation` runs whether or not the host ever opens our window, so a resolver that only existed while the editor did would leave every Hosted Plugin node in a restored session an unresolved placeholder. The processor's service outlives every editor, so a `MainComponent` built on an **external** engine with a service already installed **adopts** it (`getPluginScanService()` returns the adopted one) instead of replacing it; its destructor's "still ours" guard therefore leaves the processor's service in place. The processor re-installs its own only if the slot is found empty (a sibling plugin instance was deleted).

**Never inside a host.** `MainComponent::startPluginScan()` refuses when `AudioEngine::isHosted()`: `currentExecutableFile` inside a VST3/AU is the *host's* binary, so a scan there would launch a copy of the DAW per candidate plugin. Resolving is unaffected — that is what the paragraph above exists for.

#### Editor windows

`Source/Plugin/Hosting/HostedPluginEditorWindow.h/.cpp` + `HostedPluginWindowManager.h` — AppUI, not Core (these are windows, not audio logic), so a plugin editor never touches `GraphEditor`'s paint/timer path.

- **`synth::HostedPluginEditorWindow`** — a `juce::DocumentWindow` hosting `instance->createEditorIfNeeded()`, or a `juce::GenericAudioProcessorEditor` when the plugin reports no editor of its own (`AudioProcessor::hasEditor()`). Built with `addToDesktop=false`, so *constructing* one never creates a native peer — only `HostedPluginWindowManager::openEditorFor`'s later `setVisible(true)` does, which is what let the test suite build and inspect these headlessly (state, never pixels). `setContentOwned(editor, true)` is the whole resize story: `ResizableWindow::childBoundsChanged` already tracks the content's own size changes, so the editor resizing itself is the window resizing itself, with no override needed; `setResizable()` mirrors the editor's own `isResizable()`.
- **Reacting to the module.** The window installs itself on `HostedPluginModule::onInstanceChanged` (a single-slot `std::function`, fired on *every* edge of `hasInstance()`) and holds the module through a `juce::WeakReference`, never a plain reference — a node delete removes it from the graph (destroying the module) *before* `onGraphStructureChanged` ever fires (see below), so the window may outlive the module it points at by one event. The module's **destructor** fires the "instance gone" edge before it frees the instance, for the same reason a retire does: that node-delete interval is precisely when the window would otherwise be sitting on an editor built on a destroyed plugin instance (`HostedPluginEditorWindowTests.cpp`, `NodeDeleteDropsTheEditorBeforeTheInstanceDies`). `onInstanceChanged` fires twice for a reload (once with the old instance gone — **before** it can be reaped, so an editor referencing it is torn down while it is still guaranteed alive — once with the new one live) and once for a plain unload; the window can't tell those apart synchronously, so it defers an "is it still gone?" recheck to the next message-loop turn (`juce::MessageManager::callAsync`) — a reload has already republished its replacement by the time that runs, a real unload hasn't. Pinned choice: a real unload **closes** the window rather than leaving it on an empty placeholder (`HostedPluginEditorWindowTests.cpp`, `UnloadClosesOrFallsBack`).
- **`synth::HostedPluginWindowManager`** — owned by `MainComponent`, one window per `NodeID`; a second `openEditorFor` on an already-open node refocuses instead of duplicating. `closeAllForNode` / `closeAll` are direct map operations; `pruneClosedNodes(graph)` is the close-on-node-delete hook, wired to the **existing** `GraphEditor::onGraphStructureChanged` MainComponent already listens to (no GraphEditor changes needed) — and it is a **pure `graph.getNodeForId()` lookup**, never a module dereference, for exactly the dangling-reference reason above.
- **Shutdown / member order.** `MainComponent::~MainComponent()` calls `pluginWindowManager.closeAll()` as its very first line — before `graphEditor.detachAllModuleComponents()` and `audioEngine.shutdown()` — so every editor (and any live `juce::AudioPluginInstance` it references) is torn down while the graph is still fully alive. `MainComponent` also declares the manager **after** `ownedAudioEngine`/`audioEngine` and `graphEditor`: members are destroyed in reverse declaration order, so this is a second, independent safeguard that holds even if the explicit call above were ever removed.
- **The affordance.** `ModuleComponent`'s `HostedPluginModule` branch (mirrors the `ExternalMidiModule` dynamic-cast branch) adds the card's only body content, an "Open Editor" button enabled while `hasInstance()` (refreshed on the card's 15 Hz timer). Its click fires `GraphEditor::onOpenPluginEditorRequested(nodeId)` — a new field shaped exactly like `onAutomateParameterRequested` — which `MainComponent` resolves to a live `HostedPluginModule*` and hands to `openEditorFor`.

#### Automation lanes on hosted-plugin parameters

A hosted plugin's own parameters live on the *inner* `juce::AudioPluginInstance`, never on `HostedPluginModule`'s own `getParameters()` (which carries only `muted`). `HostedPluginModule` exposes them for lane resolution, message thread only, all reading the live instance atomically:

- `findInstanceParameter(paramId)` — exact `juce::HostedAudioProcessorParameter::getParameterID()` match.
- `findInstanceParameterByIndex(index)` — the parameter currently at a raw index.
- `getInstanceParamIndexFallback(paramId)` — the CURRENT index for `paramId`, captured into a lane's `paramIndexHint` at creation time and never re-derived afterwards.
- `getInstanceParameters()` — every live parameter, for the automation strip's lane-picker "Add lane…" entries; a parameter with no stable id gets a synthetic `"legacy:<index>"` key so it still has a non-empty, lane-identity-usable `paramId`.

**Why a hosted parameter needs different handling than one of our own modules'.** `juce::AudioPluginInstance::addParameter` is deliberately hidden `private` — every hosted parameter must be a `juce::HostedAudioProcessorParameter`, a sibling interface to `RangedAudioParameter` (not a subtype of it) with no `NormalisableRange`. A format that has a persistent string identity implements `getParameterID()`; one that doesn't (or has none for a specific parameter) either skips the interface's id contract entirely or implements it returning an empty string (JUCE's own VST2 wrapper does the latter) — both count as "no stable id" here. Since there is no `NormalisableRange`, a lane targeting a hosted parameter carries a `RangeSnapshot` of exactly `{0, 1, default}` (a hosted parameter's native domain is always 0..1 — JUCE's own host contract), and that snapshot **is** the denormalised ↔ 0..1 map `AutomationApplier` uses in place of `RangedAudioParameter::convertTo0to1`/`convertFrom0to1`. `AutomationBindingTable::Binding` and `AutomationRecorder`'s own binding carry this as a second, mutually-exclusive field (`hostedParam`) alongside the existing `RangedAudioParameter* param`, so every pre-existing call site that only ever touched `param` keeps compiling and behaving identically.

**The shared resolver.** Every lane-resolution call site — the audio-thread binding build (`AudioEngine::publishTimeline`), `TimelineReconciler`, the AI-tool `writeLane` path (`TimelineOps::runWriteLane` / `TimelineValidator::validateLane`), and `AutomationRecorder`'s rebind (`MainComponent::publishTimelineAndRebindRecorder`) — funnels through one function, `synth::resolveLaneParameter` (`Source/Timeline/AutomationBinding.h/.cpp`), so "does this lane resolve, and does it orphan" cannot drift between paths:

1. Exact `paramId` match on the live instance always wins.
2. Failing that, `paramIndexHint` is tried, but **only** as a rescue for a parameter with no stable id at all (the legacy-format case). A hinted index that instead names a *different*, still-identified parameter never binds — that is a version change having moved the parameter set under us, and the lane must **orphan**.
3. Anything else — no live instance (still loading, unloaded, refused, or never installed), or a hint that names nothing — also orphans. A `HostedPluginModule` node with no instance cannot currently vouch for *any* parameter.

Non-plugin nodes are the unchanged path: an exact `paramID` match via the global `findParameterByID`, and a miss is merely unbound, never orphaned — `paramIndexHint` is never consulted for them. `TimelineDoc::reconcileBindings` grew an optional second predicate (`laneResolves`, richer than the original uuid-only `uuidResolves`) precisely so `TimelineReconciler` can supply this per-parameter check for a `HostedPluginModule` node while every graph-agnostic `TimelineDoc` test keeps passing a single uuid predicate unchanged.

`AutomationLane::paramIndexHint` (`-1` = none) is an additive serialised field, captured once at lane-creation time (from `resolveLaneParameter`'s exact-match result, or `synth::captureParamIndexHint`) and never re-derived afterwards.

**A completed load reconciles.** A lane bound to a hosted parameter *always* orphans while the plugin is still loading — the node cannot vouch for a parameter set it does not have yet — so the interesting question is what un-orphans it. Previously, nothing did: an async load completing fired no reconcile of its own, and a freshly opened project's hosted-plugin lanes stayed orphaned (and unplayable) until some unrelated graph edit happened to trigger the next pass. `HostedPluginModule::onInstancePublished` closes that: it fires on the message thread at the end of every publish, and `MainComponent` reconciles there — hook 2c in the [inventory above](#8-app-wiring--who-owns-the-timeline-and-every-hook-that-keeps-it-in-step). Reconciled, not *re-bound*: an orphaned lane whose parameter really is gone stays orphaned, exactly as the resolver decides.

#### Latency compensation

A plugin's reported latency is the one number about it that can change *after* it is loaded, and JUCE will not notice on its own.

**Why a rebuild is required.** `juce::AudioProcessorGraph` bakes each node's `{bus layout, latencySamples}` into its render sequence and derives the parallel-path compensation delays from that snapshot. Calling `setLatencySamples()` on a node therefore changes nothing audible: the sequence keeps compensating for the old value until it is **rebuilt**. `AudioProcessorGraph::rebuild()` is public and re-derives everything (JUCE's own unit tests use exactly this pattern), so the fix is to call it — but a module has no idea which graph it is in, so detecting the change and reacting to it are deliberately split:

- **`HostedPluginModule` detects.** It installs a listener on the live instance at publish and removes it at retire/unload/destruction. `juce::AudioProcessor::setLatencySamples` fires `audioProcessorChanged(..., ChangeDetails::withLatencyChanged (true))` on that listener from **whatever thread the plugin was on** — commonly its audio thread, since a lookahead toggle usually lands there — so the listener does exactly one thing: `triggerAsyncUpdate()`. A `juce::AsyncUpdater` allocates nothing when triggered (its message object is built once, in the constructor) and coalesces, which is what makes it callable from a render callback; all the real work happens on the message thread, where the module re-reads the **live** instance's latency (never a value the notification carried — that is the guard against a retired instance's in-flight callback) and fires `onLatencyChanged` if, and only if, the value actually moved.
- **`MainComponent` reacts**, through `rebuildGraphForLatencyChange()`: `audioEngine.getGraph().rebuild()`, then a refresh of the status bar's round-trip readout (the graph is one of the three terms of `getRecordingLatencySamples()`, so the displayed number is stale until the next 5 Hz poll otherwise — same feed, not a second one). Host-agnostic: in a plugin build this is our own inner graph, which we own in both modes. The observers are installed by `installHostedPluginObservers()`, swept from `GraphEditor::onGraphStructureChanged` — the one hook every node-adding path already runs through — and they are **separate slots** from `onInstanceChanged`, which `HostedPluginEditorWindow` owns.

**Which edges notify.** A publish does **not** fire `onLatencyChanged`; `onInstancePublished` already tells the owner to rebuild (and to reconcile), and firing both would rebuild the graph twice for one event. An unload **does** — the node drops to 0 and the graph is otherwise left compensating for a plugin that is gone. `prepareToPlay` deliberately does not: the graph prepares its nodes from *inside* its own rebuild and re-reads every node's latency immediately afterwards, so asking the owner to rebuild from there would re-enter a rebuild already in progress to redo work it was about to do anyway.

**How it is proved.** `Tests/HostedPluginLatencyTests.cpp` renders an impulse down two parallel paths into Audio Output — one dry, one through a hosted plugin — and asserts both copies land on the **same output sample**, off-by-zero, at two different latencies across a rebuild. The stub plugin really delays its audio by the latency it reports (`StubPluginInstance`'s delay line); without that the graph would delay the dry path while the "latent" one stayed instantaneous and the test would pass while proving nothing. `WithoutARebuildTheParallelPathsDrift` is the negative control: skip the rebuild and the impulse arrives twice, separated by exactly the uncompensated delta.

**The wrapper mirrors it to the DAW.** The rebuild above aligns paths *inside* the graph; a DAW hosting AgentSynth additionally needs `AgentSynthAudioProcessor` to report the inner graph's latency as its own, or AgentSynth's whole track drifts against every other track in the session. The mirror is two-sided: `prepareToPlay` sets it right after `prepareForHost` (the graph was just prepared, so the figure is current), and `processBlock` ends with an int compare against `getGraphLatencySamples()` so a runtime change reaches the host on the next block rather than the next prepare (`setLatencySamples` is allocation-free; JUCE's wrappers defer the actual host notification off the audio thread). Pinned by `InnerGraphLatencyIsMirroredToTheHost`.

**Observers are uninstalled on editor close.** `installHostedPluginObservers()`' callbacks capture the `MainComponent`, and on the plugin path the engine — and every hosted module in its graph — outlives that editor-owned component. `~MainComponent` therefore nulls `onLatencyChanged`/`onInstancePublished` on every hosted node (right after `pluginWindowManager.closeAll()`), pinned by `ClosingTheEditorUninstallsTheObservers`. **Known narrow limitation:** while the plugin's editor is closed there is consequently no observer to trigger the inner rebuild, so a latency flip driven purely from the audio side (e.g. an automation lane toggling a lookahead parameter) stays uncompensated *between the graph's parallel paths* until the editor reopens or the host re-prepares; the host-facing mirror above still keeps the whole instance's reported latency honest at the next prepare.

### AppUndoManager

`Source/AppUndoManager.h/.cpp`

Snapshot-based undo/redo wrapping `juce::UndoManager`. Structural graph changes (add/remove module, connect/disconnect) are captured as JSON before/after snapshots via `SnapshotAction`. #### Restoring a snapshot is a diff, not a rebuild

`SnapshotAction` restores through `AIStateMapper::applySnapshotPreservingNodes`, which compares the target snapshot against the live graph and touches only what differs. It does **not** replay the snapshot through `applyJSONToGraph`, which reaches the same end state by destroying and re-creating every node.

- **Identity is the per-node `uuid`**, not the integer `id` (merge mode renumbers ids). A live node whose uuid appears in the snapshot is **kept** and updated in place — parameters via the trusted param path, position from `"position"`, and `"state"` re-applied through `setExtraState` **only when it changed** (it reloads a sample/wavetable off disk, so an unconditional re-apply would hit the filesystem on every Cmd+Z). A live node whose uuid is absent from the snapshot is removed; a snapshot node with no live match is created, re-adopting both its uuid and its original id when that id is free.
- **A parameter-only undo performs zero topology operations.** No node and no connection is added or removed, so JUCE never rebuilds its render sequence and the audio callback never blocks. Mixed restores batch their topology ops (`UpdateKind::none`) and rebuild exactly once at the end. No graph callback lock is taken at any point.
- **Module runtime state survives.** Sequencer position, envelope stage and sounding voices belong to the processor instance, which is no longer thrown away. This is also what makes hosted plugins and timeline-driven MIDI sources viable: neither can afford to be re-instantiated on every Cmd+Z.
- **Any doubt falls back to the old full rebuild.** `applySnapshotPreservingNodes` plans the whole restore before mutating anything and returns `false` — graph untouched — on a live or snapshot node with no uuid, a duplicate uuid or id, a uuid whose module type no longer matches, an unknown type, a connection naming an undefined node, or a merge delta (`"remove"` / `"removeModulations"`) rather than a full snapshot. `SnapshotAction` then runs `applyJSONToGraph(..., clearExisting=true, trusted=true)`, which is always correct. Correctness beats preservation.
- **UI teardown is now conditional.** The action's `preRestore` hook (`GraphEditor::detachAllModuleComponents`, and the AI service's `aiPatchAboutToApply`) exists to detach UI from processors that are about to be freed, so it fires only when a node is actually being removed — or on the fallback, which frees everything. When nothing is freed there is nothing to detach, and `updateComponents()` (the `postRestore` hook) reconciles additively, so a parameter-only undo no longer destroys and re-creates every `ModuleComponent` either.

#### Timeline undo

`TimelineDoc` edits (tracks, clips, notes, automation lanes) go through a separate `TimelineSnapshotAction`, not the graph's `SnapshotAction` — folding timeline JSON into every graph snapshot would inflate the size of every existing undo step (a parameter tweak, a module drag) that never touches the timeline at all. Unlike `SnapshotAction`'s diffing restore, `TimelineSnapshotAction::perform()`/`undo()` call `TimelineDoc::fromVar` directly: `fromVar` is already the doc's own all-or-nothing load path, so there is nothing to diff against, and a `var` this action holds always came from this doc's own `toVar()`, so `fromVar` failing would mean the doc's round-trip contract itself broke (`jassert`ed, not silently swallowed). Both action types push onto the **same** `juce::UndoManager`, so the app has one undo stack and Cmd+Z stays chronological whichever domain each step came from.

- `recordTimelineChange(doc, mutation)` snapshots `toVar()` before and after the mutation; if the two serialisations are identical (the doc rejected the edit, or it was a genuine no-op) nothing is pushed and it returns `false` — a no-op must not create an undo step.
- `recordCombinedChange(graph, doc, mutation)` is for edits that touch both domains in one gesture — the canonical case is deleting a module a timeline lane is bound to. It opens ONE transaction, captures graph + timeline "before", runs the single mutation, then pushes a graph `SnapshotAction` and/or a `TimelineSnapshotAction` — only for whichever domain(s) actually changed — inside that same transaction, so one `undo()`/`redo()` reverts or re-applies both together, never half the edit. It reuses the exact same pre/post-restore lambda plumbing (`detachAllModuleComponents` / `updateComponents`) `recordStructuralChange` gives the graph half, factored into a private `createGraphSnapshotAction` helper rather than duplicated.
- **Lifetime rule, extended:** exactly like `SnapshotAction` holding the graph, a pushed `TimelineSnapshotAction` holds a reference to the `TimelineDoc` — the doc must outlive the `AppUndoManager`, or `clearUndoHistory()` must run before the doc is destroyed. `MainComponent` satisfies this by declaration order (see §8 above).

#### Restore hooks

`setRestoreHooks(beforeRestore, afterRestore)` installs one pair of callbacks fired around **every** restore this manager performs — the graph's `SnapshotAction` and the timeline's `TimelineSnapshotAction` alike, on undo and on redo. They are deliberately *not* the same thing as `SnapshotAction`'s existing `preRestore`/`postRestore` pair, which is the GraphEditor's component lifecycle and whose "pre" half fires **lazily** (only when a node is actually being freed). These always fire, which is what the two current users need:

- `beforeRestore` opens an `AutomationRecorder::ScopedProgrammaticApply`. A parameter-only undo frees nothing — and is exactly the case that writes parameter values — so hanging the guard off the lazy hook would miss it entirely.
- `afterRestore` re-runs the timeline's binding reconciliation and publish. A **graph** restore can strand a track/lane binding; a **timeline** restore comes back out of `TimelineDoc::fromVar` with every `orphaned` flag reset to `false` (it is runtime-derived state, never serialised). Both need the same pass, and a combined step performs both restores, so the hook fires once per restore rather than once per transaction.

Actions capture the manager, not the callbacks, so hooks installed after an action was pushed still apply to it.

## Signal Flow

Modules communicate via two main signal types:

- **Audio Channels**: Stereo (usually) audio buffers containing PCM data.
- **CV (Control Voltage)**: Handled as control signals within the audio buffer (e.g., ADSR output feeding into VCA input 1).

## Quality Standards

All modules follow specific DSP requirements:

- **Smoothing**: All gain/cutoff parameters use linear smoothing to avoid clicks.
- **Antialiasing**: Oscillators use PolyBLEP for sharp waveforms.
- **Oversampling**: Nonlinear effects support configurable oversampling (e.g. Distortion and Ring Modulator offer Off/2x/4x modes).
