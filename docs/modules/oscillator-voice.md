# Oscillator voice feel

How each unison voice of the [Oscillator](modules.md#oscillator-module) starts a note and sits in the stack. Code: `Source/Modules/Oscillator/` and `Source/Modules/UnisonVoicing.h`.

## Phase and Rand

**Phase and Rand** (`phase` 0-360 degrees, `randomPhase` 0-100 %, defaults 0): on every note start each unison voice restarts at `frac(Phase / 360 + Rand x random)`, the random drawn independently per voice from a seeded generator (`phaseRandom`, reseeded in `prepareToPlay`) so a render repeats exactly. They are sampled at the note start, so they have no CV jack. Their card tooltips say so: they set the start of every new note and do not change a note that is already sounding (turning them on a held note is silent by design, since a steady tone's start phase is inaudible; a live shift would click). The Wavetable's Phase and Rand Phase carry the same tooltips. Between notes the oscillator still free-runs. **Mono** is MIDI driven: `scanMidi` records each note-on's sample offset and `processMonoMode` restarts the phases at that exact sample (`OscillatorModuleNotes.cpp`). A restart may land while the previous note still sounds, so the old phases keep running as a "ghost" and are blended out over 64 samples (`CROSSFADE_SAMPLES`) along a raised cosine (`Source/Modules/RestartFade.h`), which has no corner where the hand-over starts or ends (a straight ramp bent the sound there, a short tick on every note). A restart while a hand-over is still running turns the stack it interrupts into one more ghost with the share it holds at that sample, up to five at once, and each ghost leaves along its own curve, so the output never steps however fast restarts come; with no restart the output is byte-identical. Held notes are tracked in `synth::HeldNotes`; an overlapping note-on restarts today, and `shouldRestartOnNoteOn(overlapping)` is the one place a legato mode gates that. **Poly** restarts a voice on every rising edge of its **Restart** (Gate) input (below), on the exact sample, fading out of the old phases. Without a gate it falls back to restarting a voice when its pitch CV goes from silent (below 20 Hz) to sounding, the Wavetable's rule, and voice 0 also on a MIDI note-on (at the block start, fading out of the old phases only if it was already sounding).

**Gate input.** Poly MIDI holds a voice's pitch after release, so the pitch alone cannot show a new note on a voice that already played. The note start comes from a gate edge instead, the way modular systems reset an oscillator (a gate or trigger into its reset input) and the way voice-based synths restart each voice on note-on. The jack is the last input, shown as **Restart** on the card (its hover text: "Restarts the wave on each rising edge, like oscillator sync; poly instruments wire it automatically"); the name is display only, its channel, its `PortRole::Gate` and every saved cable are unchanged: in poly an 8-wide fan on raw ch20-27 (`kGateBase`), in mono one channel on raw ch20. `GateEdges` (`Source/Modules/GateEdges.h`, shared with the Wavetable) finds each voice's rising edges in the block with a Schmitt trigger at 0.1, low enough that a soft Vel -> Gate note still restarts. Poly MIDI drops a re-used voice's gate to 0 for at least 1 ms before every note, so every note-on is an edge. In mono a gate edge joins the MIDI note-ons in the per-sample restart list. Patch a slow source into it for a restart in time with it, or an audio-rate oscillator for a sync-style sound. `GateEdges` keeps an edge only if it comes at least 16 samples (`kMinSpacing`, about 3 kHz at 48 kHz) after the last kept one, counted across blocks, and holds up to 256 per block, so a fast gate restarts on the same samples whatever the host's block size. An unpatched gate is silent and changes nothing. The Poly switch (`PolyVoiceGraph`) and new poly instrument tracks wire Poly MIDI's Gate fan (ch8-15) to it, and a cable dragged from Poly Out onto Gate pairs the gate fan by role. Raw ch20-27 sit above the original 22 outputs, so the module now declares 28 outputs (ch22-27 silent): JUCE only gives a module a private copy of a shared input on channels below its output count, and without that a bypassed or muted Oscillator would clear Poly MIDI's gate for the ADSR. ch20-21 alias Audio R (voices 6-7) and are read before anything is written, like ch14-19.
**What Phase and Rand do to the sound.** Both change the first few hundred milliseconds of a note, not the settled tone. Phase moves where every voice's wave starts: a Saw at Phase 0 against 90, 180 or 270 differs by 1.5 to 1.8 times its own level over the first 30 ms in the reference synth, and the Oscillator reads the same, so the click or soft push of the attack changes while the sustained pitch and brightness do not. Rand adds up to that much extra phase to each voice, drawn per voice and per note: at Rand 0 a Unison 5 stack starts in phase and is loudest in its first 30 ms (about 1.5 to 2 times the settled level), and every repeat of the note is identical; at Rand 100 the voices start apart, the stack opens without that bump, and each repeat is a little thicker or thinner than the last (about 15 % in level over 100 ms, reference synth 15 %, Oscillator 18 %); Rand 50 sits between. A single voice has the same spectrum whatever its start phase, so with Unison 1 Rand changes only the waveform's start. Poly follows once its Gate is wired, which the Poly switch does; a Poly MIDI cable into the pitch inputs alone has no note start to restart on after a voice's first note. Tests: `OscillatorPhaseRand.*` in `Tests/Modules/OscillatorVoiceFeelTests.cpp`, `OscillatorPolyChord.PhaseAndRandAreAudibleOnEveryRepeatOfAChord`.

**Where a poly voice's first note starts.** A poly voice that has never played starts at the first sample its pitch input is sounding (20 Hz or more), not at the next block, so its first note rises with its envelope at every block size (Poly MIDI glides the pitch up from 0 over 5 ms). Test: `SourceClickGuard.PolyOscillatorFirstChordStartsOnItsOwnSample`.

**Poly pitch follows the glide per sample.** Poly MIDI writes a new note's pitch as a 5 ms per-sample glide. When a voice's pitch CV moves within a block (and the Oscillator's own Glide and Fixed rate are off), the voice takes the per-sample render path and reads the pitch CV at every sample (`pitchMovesWithinBlock`, `OscillatorModulePoly.cpp`); a constant pitch keeps the per-block fast path. Without it the pitch moved in block-size steps and a chord beat differently at every buffer size. Test: `OscillatorPolyChord.PitchGlideIsFollowedPerSampleSoTheChordDoesNotDependOnTheBlockSize`.

## Blend, Width and Detune

**Detune, Blend and Width** (`detune` default 35 cents, `blend` 0-1 default 0.75, `width` 0-1 default 1; Unison itself still starts at 1, so a new Oscillator is unchanged until Unison is raised, then the stack is wide and full at once): the voices nearest the root (the middle voice for an odd count, the middle two for an even one) stay at level 1; every other voice is `synth::unisonOuterGain(blend)` (`UnisonVoicing.h`, shared by both modules): 0 at Blend 0, 0.37 at half, 1.33 at Blend 1, so the outer voices overtake the centre near 87 %. Blend 0 is the centre voice alone, Blend 1 the full stack with the outer voices louder than the centre. Width pans the voices across Audio L / Audio R: the middle voice of an odd count stays centred, the others, in detune order, alternate right, left, right, ... so each mirrored pair lands on opposite sides (`synth::unisonPanSide`). A panned voice's near leg rises linearly from 1 to 2.5 and its far leg falls as `(1 - width)^1.2` (`synth::unisonPanGains`); Pan then balances the result. At Width 0 every voice has unity on both legs, the stack renders mono and Audio R is a copy of Audio L; at Width 1 each mirrored pair sits hard left and right. The stack is divided by the square root of the sum of the voices' mean leg power (`unisonLegPower`), so uncorrelated voices keep the loudness of one voice at any Unison, Blend and Width; one centred voice divides by exactly 1, and in-phase onsets can peak above one voice.

The two curves are fitted to a reference stack measured offline as a black box (a Saw at 220 Hz held, 34 cents detune, Rand 100 %, 3, 5 and 7 voices over Blend 0-100 % and Width 0-100 %): the share of the mid power on the centre voice and the side/mid level ratio land within 0.04 and 20 % of it, with the loudness held to within 1.5 dB of one voice (`Tests/Modules/UnisonConstantPowerTests.cpp`, measurement rig `Tests/Modules/UnisonStackMeasure.h`). The defaults are that measured reference's own settings (35 cents, Blend 75 %, Width 100 %; its voice spacing, levels and panning match this stack's at those values), so a new Oscillator at Unison 7 is as wide as the reference. A project, preset or generated patch stored without a Detune, Blend or Width loads each missing one as it was before the defaults changed (Detune 0, Blend 100 %, Width 0; `applyStoredParamDefaults`, and the same for the binary plugin state), so only a fresh Oscillator or Wavetable starts at the new values and a stored key always keeps its own. A generated patch that omits them therefore gets a mono, centred stack; one that writes them gets what it wrote. Tests: `Tests/Modules/UnisonDefaultsTests.cpp`. Stored Blend values keep their number, not their old sound: the curve above replaced the old "outer voices scaled between 1 and Blend" law.

**Changing Unison in a held note.** Each voice's leg gains move towards their targets no faster than 1.0 per 10 ms (`prepareUnisonMix`, `OscillatorModuleVoicing.cpp`) and ramp linearly inside the block. A voice entering the stack fades in from 0; a voice leaving keeps rendering at the detune of the outermost remaining voice while it fades out; the voices that stay slide to their new Blend level and side the same way. The divisor is taken from the same gains, so the normalisation follows the fades and nothing steps. The same slew smooths an automated Blend or Width. Detune keeps its detune offsets; the knob is skewed (centre at 25 cents) for fine control while the stored value stays in cents, and Detune CV adds cents linearly (+1.0 = 100 cents).

## Blend and Width CV

Blend and Width have CV jacks, appended after Glide: Blend on raw channel 18, Width on 19, the same channel in mono and poly (inputs 18 -> 20; the Gate fan later took 20 -> 28 and the outputs grew to 28 with it). Like Unison, Detune, Pulse Width and Glide they alias the Audio R output block, so `readGlobalParamCV` reads them before anything is written or cleared. Phase and Rand have no jack.

## Glide and Legato (mono feel)

Three Oscillator parameters, all in the card's More controls row:

- **Glide Mode** (`glideMode`): `Always` (default) takes the Glide time for any interval. `Scaled` takes Glide x |interval in semitones| / 12, so an octave takes the Glide time and a semitone a twelfth of it.
- **Glide Curve** (`glideCurve`): `Linear` (default) or `Exponential`, an RC-style approach in pitch (fast start, slow settle) that is timed to reach the target by the set time, then snaps.
- **Legato** (`legato`, mono only, default off): glide happens only for overlapping notes (tracked by `HeldNotes`); a note that does not overlap another jumps. An overlapping note does not restart the phase, and releasing the current note while others are held glides back to the most recent held note. With Legato off the behaviour is unchanged.

**Where the pitch changes.** `scanMidi` records every mono pitch change (a note-on, or the return to a held note) with its own sample offset in `pitchEvents`, and `processMonoMode` applies it at that sample, not at the start of the block the note lands in. The block starts on `noteAtBlockStart`, the note sounding before the block's first event, so a note released near a block start keeps its pitch until the next note begins and the result does not depend on where the block edges fall. A note counts as overlapping only if another note is still held once the note-offs on its own sample are applied, whichever order the host wrote them in, so two notes that touch never glide. A jump (a Legato note-on that overlaps nothing) sets the glide and the 5 ms frequency smoother to the new pitch at once, so it is clean at Glide 0 as well as with a long Glide. Without Legato at Glide 0 the 5 ms smoother still rounds each pitch step. Tests: `Tests/Modules/OscillatorLegatoJumpTests.cpp`.

The ADSR has a matching Legato switch (see `modules.md`). Code: `Oscillator/PitchGlide.h`, `OscillatorModuleNotes.cpp`.

## Fixed rate

`rateMode` (Rate: Follow notes / Fixed, default Follow notes) and `fixedRate` (Hz, 0.1 to 2000, skewed around 20 Hz, default 50) let the oscillator run at a set frequency whatever note is played, like a DX7 operator's Fixed mode or a free-running Eurorack VCO. Its main use is an audio-rate modulation source: a 53 Hz square patched into another Oscillator's Level makes a frog croak.

- **Formula**: in Fixed mode the frequency is `fixedRate * 2^((12*octave + coarse + fine/100 + CV shifts) / 12)`. The note term is dropped; the knobs and the Octave/Coarse/Fine CV still offset it. Follow notes is unchanged.
- **Floor**: Follow notes clamps a voice to 20-20000 Hz; Fixed clamps to 0.1-20000 Hz, so sub-20 Hz rates (LFO-like) work.
- **Poly voices stay note-gated**: a voice is live only while its pitch CV is at least 20 Hz (voice 0 falls back to the MIDI note); a live voice plays the Fixed rate instead of its note, an inactive one stays silent.
- **Phase restarts on notes** (note-on, Gate edge, a poly voice going live) exactly as in Follow notes, so a fixed-rate modulator keeps its pulses aligned to each call.
- **Glide has no effect** in Fixed mode: the target does not move with notes.
- **On the card**: Rate waits in the More row, so the card keeps its size; the Fixed rate knob takes Glide's cell while Rate is Fixed (no notes to glide between).
- **No jack for Fixed rate** (to keep the channel layout); automate the knob instead.

The shared logic is `OscillatorModule::baseFrequencyHz()` and `minRenderHz()` in `Source/Modules/Oscillator/OscillatorModuleRate.cpp`; tests: `Tests/Modules/OscillatorFixedRateTests.cpp`.
