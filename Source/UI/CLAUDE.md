# UI & theming invariants (Source/UI/)

Mechanism and history live in the linked docs.

- **No unconditional per-tick repaint** — `ModuleComponent` is buffered-to-image with a gated 15 Hz timer; the 30 Hz GraphEditor animation composites cached images; a theme switch is exactly one re-skin pass. All animations use `AnimationDriver` (VBlank-driven, time-bounded). Exactly two exceptions: the AI thinking spinner (in-flight only, region-confined) and the timeline playhead (strip-confined, playing-only). → [`docs/layout/rendering.md`](../../docs/layout/rendering.md) · [`docs/layout/animation.md`](../../docs/layout/animation.md)
- **A cable is not a graph edge** — one drawn wire can be 1 edge, 2 edges + a hidden attenuverter node, or N poly-bus edges. Never identify, hit-test, colour or delete a cable by `AudioProcessorGraph::Connection`; go through `GraphEditor::buildVisibleCables()`, the single enumeration feeding both `paint()` and hit-testing. Wire colour resolves only via `synth::ui::resolveCableColour` — reading a `*Wire` theme token at a paint site breaks user colour overrides. → [`docs/layout/cables.md`](../../docs/layout/cables.md)
- **Themes don't swap fonts** — all built-ins share Inter + JetBrains Mono; swapping the embedded typeface *family* at runtime corrupts text (JUCE 8 + CoreText). Themes differ by colour/treatment/glow only. → [`docs/layout/theming.md`](../../docs/layout/theming.md)
- **No high-frequency logging** — a global `juce::Logger` (Debug builds) pipes `writeToLog` into a UI-thread console; never add per-sample / per-frame / per-parameter / per-connection logs (one caused a multi-second freeze; guarded by `AIStateMapperTest.PresetLoadDoesNotSpamLogger`). → [`docs/ai/chat-component.md`](../../docs/ai/chat-component.md#logging-rules)
- **A module/macro rebuild mid-gesture cancels any live drag, never leaves it waiting on a `mouseUp` that can't arrive** — `ModuleComponent`/`MacroCardComponent::mouseDown` arm the drag-preview state (`GraphDragDropController::dragPreviewActive_` since FRO77 PR3, forwarded via `GraphEditor::isDragPreviewActive()`) / `GraphEditor`'s `selectionDragActive` and reset them only from their own `mouseUp`; `detachAllModuleComponents()`/`updateComponents()`/`syncMacroCards()` destroying that component first (an async apply, or the dragged node/macro itself vanishing) leaves no component left to deliver one. Call `GraphEditor::cancelLiveDragGestures()` from every such removal site. → [`docs/layout/selection.md`](../../docs/layout/selection.md)
- **Three collaborators own most of `GraphEditor`'s state, each reached only through `GraphCanvasHost`** — `SmartConnectionEngine` (FRO77 PR1, smart-connection suggestions), `MacroGroupController` (FRO77 PR2, macro grouping/geometry/ports/bypass-mute), `GraphDragDropController` (FRO77 PR3, drag-preview + alignment guides + drag-and-drop targets). `GraphEditor` holds one instance of each and is a **thin owner, not a facade**: new API for one of these concerns goes on the collaborator only, and callers reach it via `getMacroController()` / `getSmartConnections()` / `getDragDropController()` (all three accessors exist, FRO254) — never add a new `GraphEditor` forwarder. FRO254 migrated every call site off the legacy one-line forwarders and deleted them, except `MacroGroupController::changeMacroPortColour` (real logic beyond pass-through, stays on `GraphEditor`), the three `SmartConnectionEngine` methods that satisfy `GraphCanvasHost` pure virtuals `GraphDragDropController` calls polymorphically, and `GraphDragDropController`'s `DragAndDropTarget`/`FileDragAndDropTarget` overrides (JUCE resolves a drop target by Component identity, so the override can't move off `GraphEditor`). → [`docs/architecture/graph-editor.md`](../../docs/architecture/graph-editor.md#new-api-goes-on-the-collaborator-not-grapheditor)
- **A track header never sees the graph — its channel comes through one seam** — `TimelineTrackHeaderComponent` stays graph-free and headless-testable against a stub host; everything it knows about the mixer CHANNEL its track plays into (the channel chip's name/meter, a linked track's rename/colour fan-out, and the M/S that drive the strip instead of note gating) arrives through `synth::ui::TrackChannelLinkSurface`, handed back by the single non-pure `TrackHeaderHost::getChannelLinkSurface()`. Every "not linked" answer is false/null and the header falls through to its existing behaviour unchanged, so the link can never half-apply. The real implementer is `TrackChannelLinkController`, owned by `MainComponent`. → [`docs/mixer/mixer.md#channels-follow-audio-not-tracks`](../../docs/mixer/mixer.md#channels-follow-audio-not-tracks) · [`docs/timeline/tracks.md`](../../docs/timeline/tracks.md#the-channel-chip)
- **A menu whose options a background thread can mutate resolves clicks against a build-time snapshot, never a re-run collector** — the Instrument -> Plugin picker's known-plugin list is mutated by `PluginScanService::runScan` off the message thread, so `TimelinePanelComponent::applyAddTrackMenuChoice` indexes `instrumentPluginMenuSnapshot_` (captured in `buildAddTrackMenu()`), not a fresh `collectInstrumentPluginMenuOptions()` call — a scan finishing mid-menu can otherwise resolve a click against a plugin the menu never showed there. → [`docs/timeline/add-track.md`](../../docs/timeline/add-track.md#menu-options-resolve-against-a-build-time-snapshot)
- **Any mixer UI object holding a parameter or module pointer unbinds through `MixerPanelComponent::unbindAllColumns()`** — the fader, the pan attachment, the EQ thumbnail, (FRO15) every `MixerSendList` row's `sendNLevel` attachment, and (FRO133) the MIDI Learn registry's raw `juce::RangedAudioParameter*` entries are live pointers into graph nodes, and `GraphEditor::onBeforeDetachAllModuleComponents` is the one seam every graph-replacing path (undo/redo restore, New Patch, Load, AI patch apply) AND every single-node removal command — `GraphEditor::deleteSelection()` (a canvas "Delete", `deleteMacroAndMembers`), `requestDeleteModule()` (a card's own delete button / "Delete Module") and `replaceModule()` ("Replace with...", FRO103) — reach BEFORE they free them — the latter has no rebuild of its own to lean on (`reconcileTimelineBindingsOnly()`, its only guaranteed post-apply hook, deliberately never rebuilds the mixer), so a stale binding could sit until an unrelated later graph edit finally destroys and dereferences it. A new bound control in a column means a new line in `MixerColumnComponent::unbindFromGraph()`, not a hope that rebuild order saves it. → [`docs/mixer/sends-and-buses.md`](../../docs/mixer/sends-and-buses.md)
- **A single `graph.removeNode()` frees its processor synchronously, same as a full graph-replacing restore** — a live single-node removal outside `onBeforeDetachAllModuleComponents`'s reach (today: `MixerInsertList::removeRow()`'s own row "Remove") has no equivalent built-in hook, so a UI object holding a raw pointer into that ONE node must either get a caller-side pre-removal unbind (`MixerInsertList::onBeforeNodeRemoved`, fired from `removeRow()` before `removeNode()`) or check the node's own liveness before dereferencing (`MixerEqThumbnail::detachListeners()`'s optional graph/NodeID) — a defensive check beats chasing every present and future single-node removal call site with its own hook. → [`docs/mixer/panel.md#the-eq-curve-thumbnail`](../../docs/mixer/panel.md#the-eq-curve-thumbnail)
- **No file over 1,000 lines** — `GraphEditor.cpp` is this directory's cautionary tale (9,000+ lines before the guard); a class that outgrows one file is split by concern into its own directory (root `CLAUDE.md` § Code structure). `Source/UI/` holds only area directories — `Graph/` (GraphEditor, ModuleComponent, cables, selection, minimap, mod matrix), `Timeline/` (panel, clip lanes, ruler, headers, transport, automation lanes, edit tools), `PianoRoll/`, `Library/` (module library), `Macros/`, `ModuleViews/` (per-module visualizers), `Settings/`, `Assistant/` (AI chat + account), `Chrome/` (toolbar, status bar, welcome, export, shared popups), `Layout/` (layout/focus/animation primitives), `Theme/`, `MidiRemote/` (the shared right-click MIDI Learn menu/badge/armed-outline helpers every learnable surface calls into, `MidiLearnMenu.h` — FRO133); a new file goes into its area, never back into this directory. → [`docs/development/file-size-guard.md`](../../docs/development/file-size-guard.md)
- **A per-module card's own gated Timer is the playhead pattern, not a new independent one** — `ModuleComponentEnvelopeCard.cpp`'s envelope graph (FRO112) drives `CurveEditorComponent::setPlayhead` from `ModuleComponent`'s EXISTING gated 15 Hz `timerCallback` (only while the graph section is visible), reusing the same per-module visualizer-timer category `FrequencyResponseComponent`/`ScopeComponent` already established, rather than arguing for a third exception to the two-exception time-bounded-animation rule above. A function already at `scripts/function-size-baseline.txt`'s ratchet ceiling (`ModuleComponent::createControls`, `::layoutDefaultContent`) gets new call sites by extracting a sibling named step first (`layoutKnobGrid`), never by growing the ratcheted function itself. → [`docs/layout/visualizers.md`](../../docs/layout/visualizers.md) · [`docs/modules/modules.md#adsr-envelope-module`](../../docs/modules/modules.md#adsr-envelope-module)
- **Every learnable control on a module card goes through ONE call, `ModuleComponent::registerMidiLearnable`** — never a new bespoke identity-scan loop per control kind; it is the single registry the right-click menu, the MIDI-mapped badge and the armed breathing outline all read. Every surface's menu block/badge dot/armed outline itself is built from the SAME shared, surface-agnostic helpers (`Source/UI/MidiRemote/MidiLearnMenu.h`'s `appendMidiLearnMenuItems`/`paintMidiMappedBadge`/`paintMidiLearnArmedOutline`/`RightClickSafeButton`) rather than a second implementation per surface — `ModuleComponent`, `MixerColumnComponent`/`MixerMasterColumn` and `TimelineTransportBar` each keep their OWN small registry (a parameter or, for the transport bar's action targets, an actionId), since what a registry entry keys on differs per surface, but never re-derive the menu/paint shapes. **The pick-target overlay (`Source/UI/Graph/PickTargetOverlay/`, FRO135) is entered from the MIDI Remote panel only, never a global key** — it reads each surface's `collectPickCandidates()` rather than a shared registry, is parented on `MainComponent` (the mixer and transport bar are not canvas children), and ends on Esc, on a click that hits nothing, and from `GraphEditor::onBeforeDetachAllModuleComponents`. → [`docs/control/midi-remote-ui.md#right-click-midi-learn--coverage`](../../docs/control/midi-remote-ui.md#right-click-midi-learn--coverage) · [`docs/control/midi-remote-ui.md#assign-from-the-panel-control-first-learn`](../../docs/control/midi-remote-ui.md#assign-from-the-panel-control-first-learn)
- **A split class's header declares; its units document** — for a class spread over `<Class><Concern>.cpp` units, the header keeps the class-level comment, the `// ---- ---- ` section banners, and per member only what a *caller* can get wrong from outside, one line each: nullability, thread affinity, call-ordering preconditions, units, ownership. The *maintainer*-facing rationale — why it is built this way, the threading/ordering argument, the edge case that forced the design, the invariants the body must preserve — lives beside the out-of-line definition in the owning unit, where the edit that invalidates it will land in the same diff hunk. A one-line forwarder into a collaborator (`macroController_`/`smartConnections_`/`dragDropController_`) is defined out-of-line as well, so the header does not recompile every includer when a body changes. This is what brought `GraphEditor.h` under the cap (FRO91, 1,489 -> 944) and clears the last ratchet entry. → [`docs/timeline/piano-roll.md`](../../docs/timeline/piano-roll.md#source-layout)
- **Hosted-parameter UI binds per parameter, hops threads with an `AsyncUpdater`, and unbinds on the instance-gone edge** — a hosted plugin's knobs (`HostedParameterAttachment`, FRO128) listen with a `juce::AudioProcessorParameter::Listener` on THEIR parameter only, never an instance-wide `AudioProcessorListener`; `parameterValueChanged` can arrive on the audio thread, so it only stores the value and calls `triggerAsyncUpdate()` and NEVER touches a widget. The listener points into the plugin instance, which `HostedPluginModule` frees synchronously (retire, destructor), so the card unbinds from `HostedPluginModule::InstanceObserver::hostedInstanceGone` (fired while the instance is still alive; a 15 Hz poll cannot win that race) and from `detachFromProcessor`, reaching the module only through a `WeakReference`. A node delete / "Replace with..." frees the module before the card's `detachFromProcessor` runs, so the module's own gone edge is the only thing that unbinds there. → [`docs/control/plugin-card-layout.md`](../../docs/control/plugin-card-layout.md#instance-lifetime-and-unbinding)
